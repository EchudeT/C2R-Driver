# 后续优化研究：减少错误路线与重复调查

## 本轮结论

优先级应从“减少历史 token”调整为“减少沿错误前提继续工作的调用”。上一轮六次诊断回放都识别了外壳实现，却都没有明确核实设备中断模式。这意味着删除历史没有修复共同的知识缺口。继续增加同类回放样本，信息增益预计小于检查原始接口与设备实现。

本轮没有新增付费模型调用，没有改变原 e1000 workspace，也没有新增验收门禁。已实现两个程序化改进：交接携带有来源的观察变化，以及费用报告中的缓存敏感性分析。默认 persistent 和既有三次不变观察保护保持原策略。

## 1. 源码核实揭示真正需要补足的证据

本轮只检查与原运行一致的冻结 revision，摘录、行号及完整文件哈希保存在 [审计记录](audits/context-followup-2026-09-26.json)。

| 层 | 冻结源码观察 | 能支持的结论 |
|---|---|---|
| Linux e1000 | `e1000_request_irq` 使用 `IRQF_SHARED`，对 `adapter->pdev->irq` 调用 `request_irq` | 源驱动依赖共享 PCI IRQ 路线 |
| QEMU e1000 | `pci_e1000_realize` 设置 `PCI_INTERRUPT_PIN = 1`；中断更新使用 `pci_set_irq` | 所选模拟设备存在 INTA 信号路径 |
| Asterinas PCI | `acquire_msix_capability` 返回 `Result<Option<CapabilityMsixData>>`，说明要求设备 capability 存在 | 这个 API 的存在不能证明所选设备可用 MSI-X |

这些是直接代码证据，不是对整个目标内核能力的否定。尚未建立的链条是：所选机器 PCI pin 的路由、控制器/GSI/向量映射、目标 IRQ 注册、共享与电平触发语义、设备屏蔽/确认和回调生命周期。不能只因没在 PCI crate 找到函数就宣称全系统没有 INTx；需要对相关平台路由做一次有界调查。

**通用改进方式**：每次选取高影响 API 时，在原有报告中用几行说明“设备实际机制→目标 API 前置条件→适配证据→最小验证”。适用对象还包括 DMA mask/一致性、缓冲区所有权、MMIO 顺序、回调上下文和移除生命周期。不是为 e1000 增加规则，也不是让所有驱动都执行 IRQ/DMA 检查。

发现机制不匹配时，应先调查或实现必要平台适配。诊断性的 polling 实验可以帮助分离 DMA 与中断问题，但如果冻结范围要求 IRQ，polling 不闭合该义务。阶段允许保留 PLANNED/UNKNOWN，不必在第一轮就完成所有行为；只有开始依赖某能力时才集中核实它。

## 2. 交接需要保留事实变化，不能把历史结论升级成事实

原实现的 continuation ledger 保存 detail 和 receipt 路径，结构化观察主要存在于即时反馈中。新会话容易看到过期报告，却缺少可直接比较的新旧观察。

本轮新增：

- 新 continuation 事件持久保存 controller 产生的 observation。
- 交接包读取同一修复周期最近两条事件，携带 event sequence、receipt、fingerprint 和 observation。
- 仅比较两条均存在的字段。例如 `qemu_observed: false→true`、`runtime_bound: false→true`；同时保留 `logs_observed: false`。
- 历史事件缺失 observation 时保留未知，不跳过它与更老事件比较；阶段已通过或显式 reopen 后不跨周期比较。
- 最多检索 32 条相关账本事件、携带两条观察；不复制运行日志，不额外调用摘要模型，不要求 worker 填新表。

这是“观察变了”，不是自动声明“旧诊断已推翻”。输入、collector 版本、环境可能同时变化；一次观察成立也不意味着当前代码或全部义务成立。说明明确要求按来源与当前输入核对。原始事件受现有账本完整性机制保护，packet 受 CAS 保护；不把可变 receipt 路径本身当成新的不可变证明。

老 e1000 的账本没有这些字段，本轮只在研究记录中提取旧 receipts，未重写其历史。新机制从新 continuation 开始生效。它也不尝试读取报告文本并自动标记“错误归因”。语义上的已否定假设仍应保留在原报告的简短连续性说明中。

## 3. 缓存使“短上下文更便宜”成为条件命题

对原 e1000 implementation 的 16 次调用重新汇总：13 次有 usage，3 次未知。已知输入 8,728,085 token，其中缓存 8,105,472，命中比例约 92.87%；已知估算费用 $6.1143208。

按相同 token、模型、服务层与计价版本，仅取消缓存折扣，估算为 $35.29402；差值 $29.1796992。**该差值不是实际节省账单，也不是重置会话的代价**：新会话会减少输入，同时引入规则/代码重读、摘要或工具输出，输出 token 与未来缓存也会变化。

新的 `context-report` 在总计、policy 和 epoch 分组中提供 `cache_cost_sensitivity`。只纳入当前计价函数能完全复现原 quote 元数据的调用；未知 usage、无法计价、历史不同费率不混算。无可比较调用时金额为 null。

官方 OpenAI 文档同样建议统计 cache-hit、延迟和总成本，并在压缩前后比较总输入成本：[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)。本轮核对该页面，未更改仓库计价表，也未据此承诺中转商费用。

重置决策可使用如下研究模型，而不是新增强制阈值：

```text
重置的预期净收益
= 减少无效调查/重复修复的预期费用
+ 后续上下文输入的预期净减少
- 交接与重新检索成本
- 失去有效局部推理所引起的返工风险
```

目前数据不足以估计这些项，因此不应按累计 token、调用数或缓存比例自动切换。累计 usage 也不是实时上下文占用。

## 4. 下一轮实验如何避免重复上一轮的偏差

上一轮把旧报告从交接组移除，却要求它明确纠正旧报告里的归因；材料差异影响了 rubric。接下来的实验应把“诊断所需的信息是否可得”和“历史长度”分开：

| 对照 | 两组相同的信息 | 唯一主要差异 | 回答的问题 |
|---|---|---|---|
| 完整历史 vs 紧凑观察交接 | 当前代码/契约/receipt；同一条旧归因及其出处；未决义务 | 重复旧日志与对话是否保留 | 冗余历史是否影响诊断成本与准确性？ |
| 通用 API 资料 vs 加入机制证据 | 相同上下文策略与任务 | 是否提供冻结设备/目标接口摘录 | 失败是记忆问题还是缺少关键证据？ |
| 实际持久会话 vs CAS 交接新会话 | 同一可恢复代码 checkpoint、相同功能验收和工具权限 | 原生会话策略 | 生产策略能否降低真实修复成本？ |

先做前两项开发集实验筛选，再做原生会话实验。无需立刻展开全部因素组合。至少增加一个非网络设备开发案例，正式评测应按设备机制分层，不能以同一个 e1000 checkpoint 的多次调用冒充跨驱动样本。

判定质量时使用两组都可获得的信息，分别报告：正确诊断、遗漏义务、无依据假设、重复调查、可执行修复与共同功能 oracle 结果。成本包含失败、检索、重读和人工介入；未完成/未知不能算零。诊断分数不是迁移成功率。

中转上限字段未确认的问题仍在，未绕过上一轮的实验执行器保护启动付费调用。20 美元授权不变，本轮新增估算模型费用为零。后续真实实验需先确认可执行的输出/调用预算控制或采用可核对计费的执行通道。

## 5. 后续实施顺序

1. 在新运行中收集结构化 observation，检查紧凑交接是否减少重复归因，不增加 gate。
2. 针对当前最昂贵的能力不确定性做有界 source/target/QEMU 核实，保留引用与适用 revision。避免把全部源文件和日志灌入上下文。
3. 从相近历史成果提取平台构建/启动 recipe，按 revision/容器/工具链验证一次；保持设备行为证据独立。
4. 对真正运行的候选比较最小局部修复成本与完整迁移成本，用共同 oracle 衡量质量。
5. 只有得到跨设备结果后，再考虑自动上下文调度、模型路由或新的义务门禁。

本轮没有实测新交接提高模型质量或迁移成功率。已实现的变化是信息保存和可观测性改进；效果需要上述实验验证。
