# 统一实现阶段与重复工作削减

新任务将 `target_framework_enablement` 和 `driver_implementation` 合并为一个真实的
`driver_implementation` 阶段，覆盖目标框架适配、驱动、集成、公开测试与实现自检。
用户实验关闭 analysis_review 时，原 13/14 两阶段合为第 13 阶段。
默认开启两项可选审查的开发任务为 17 个账本阶段，关闭两项后为 15 个；benchmark 另加一项。
账本阶段不等于模型调用：已有完整交付可以直接进入后续程序验收。

## 责任与验收

- 同一工作者可以修改框架与驱动的共享路径；不在二者之间冻结中间源码或交接。
- 一个工作报告，框架与驱动的六项兼容产物由控制器生成并在同一事务登记。
  两组快照必须绑定相同 worktree、文件集合及报告，不能先通过半份实现。
- 源码快照、运行前置检查、功能 smoke、制品身份、公开 QEMU 与配置的 benchmark 仍保留。
  模型的 `done` 或自检声明不能取代实际执行证据。
- 新建开发任务默认启用 `behavior_scheduling`：每轮只推进一个有意义功能，continue 留在当前功能、
  done 最多推进一个；连续会话和依赖协调保留。全部功能完成才进入实现验收。
  可通过 `--no-behavior-scheduling` 建立无调度对照；旧配置不变。
- 审查仍按现有配置启停；此次没有新增 reviewer。

## 框架适配随行为完成

仅合并阶段不够：默认提示仍要求一次做完整交付，会把整个框架研究塞进同一次长调用。
现在 `port run` 和 developer 模式的 `init` 默认启用控制器逐行为调度；盲评模式保留原协议。
底层 `ProjectConfig` 的调度开关仍显式传入，便于测试与历史协议构造。

正常实现路径是：

1. 首个实现回合从已有分析提议粗计划，`driver_checks.plan` 返回当前项后立即编码，无额外规划回合。
2. 当前项包含必要框架修改、驱动接入、失败清理、对应刺激与局部验证；不另立框架/探测功能项。
3. `continue` 留在当前项，`done` 最多前进一项。控制器保存源码检查点，继续同一模型会话。
4. 全部行为完成后组装已有交付，执行剩余必要验收；身份一致的收据复用，不重新研究平台。

例如设备注册行为需要目标注册接口调整，就在注册行为里补齐并验证；后续通知行为需要一个
源语义规定的触发入口，就在通知行为里完成。不要先开发一个“全部目标能力可用”的框架原型。
小驱动允许一个完整行为；不要为了调度把 helper、错误分支拆成大量功能项。

探测不是一律删除，使用条件必须具体：待确定什么事实、不同答案如何影响当前行为或必需断言、
读取哪个定义/观察什么结果可以解决。已有证据足够则直接实现；解决后停止同一问题的调查。
通用 Docker、构建和 QMP/串口由[平台执行层](../platform/PLATFORM_EXECUTION.zh-CN.md)提供；驱动特定刺激、
断言和必要框架适配仍由实现模型完成，不能用平台启动 PASS 代替驱动验证。

完成协议和回合 objective 都取自当前行为，修复提示不能覆盖成“立即提交整个阶段 PASS”。
每项没有新增报告或 reviewer，不要求每项重复全量公开套件。工作说明持续更新同一报告。
程序约束进度和最终验收；是否只修改相关代码、调查是否必要仍依赖模型执行，不能声称硬性杜绝越界。
64 次进度交回是停机保险，不是正常预算；达到上限后的完整交付仍可验收，不能变成错误阻断。

## 哪些重复工作被去掉

| 浪费 | 实现方式与边界 |
|---|---|
| 框架阶段做完驱动，后续再交接或补一轮报告 | 移除新 DAG 中的框架阶段，统一提交及失败修复 |
| 为框架、驱动生成两份重复模型报告和源码清单 | 一份报告、共用一次采集的文件集合；保留各自验证器及一致性检查 |
| 已有可运行产物与 harness，包装阶段再叫模型 | 沿用 prepared-delivery 身份收据；控制器直接验证和登记 |
| 已运行并已观察公开实验，验收时再运行/再解释 | 仅在执行身份一致且模型明确确认同一实验收据时复用；没有确认则仍需自检 |
| 仅修改解释文字却重新构建或跑 QEMU | 实现 smoke 与实验缓存按源码、脚本、制品、依赖和执行策略匹配，报告文字不作为执行输入 |
| 反复研究已确认 API、压缩后重新猜构建命令 | 独立 delivery 提示词要求从当前决策、原文引用和成功命令继续，遇到具体缺口再调查 |

后两项的内容身份缓存此前已经实现，此次让合并路径使用它们并验证其边界。
提示词约束不能保证模型一定不重复阅读，不宣称已消除所有重复操作。
不能仅因文件名、驱动名相同就复用；源码、运行依赖或验收策略改变必须重新匹配/验证。
失败记录不删除，不当作成功缓存；不存在为了节省时间降低标准的路径。

## 兼容与恢复

新建配置 `unified_implementation=true`；历史 JSON 没有该字段时恢复为 false。
旧 DAG、阶段枚举和服务保留用于原任务续跑；不改历史实验的冻结 controller 或状态。
下游按配置解析框架证据实际所属阶段。合并阶段失败保留源码，继续同一工作会话。
针对框架或驱动的返修都回统一阶段；后续制品或运行证据仍按依赖失效。

## 验证与限制

`tests/test_unified_implementation.py` 使用合成源码和模拟模型，运行真实控制器、
本地脚本执行器、CAS 和账本。覆盖开发及盲测 DAG、旧配置解释、开启/关闭最终审查、
首次 smoke 失败后同会话恢复、完整交付免额外包装调用和重新打开账本。
`tests/test_behavior_scheduling.py` 同时检查旧/新 DAG 的单功能推进边界。
这些不是实际驱动验证；QEMU fixture 使用明确标记的本地模拟命令。
旧 pvpanic 实验的规则未被热修改；2026-10-03 按用户要求显式停止，保留其源码、运行失败和日志。
用户随后授权干净重跑；实验目录为 `../experiments/pvpanic-behavior-sol-medium-20261003-01/`，
模型为 gpt-5.6-sol medium，关闭两个可选 reviewer，冻结控制器、提示词、共享快照和显式 KVM/官方镜像路线。
启动后只观察；本文件不预报实验成功或成本改善。30 分钟是完整报告的工程目标，不是隐含超时或成功条件。

本轮全量离线回归 354 项通过、1 项旧提示词字面断言失败；将该断言改为检查实际审查阶段后，
相关实现/平台 16 项复测通过，行为/提示词 13 项复测通过。新增 KVM 容器权限回归包含在平台复测中。
完整日志与配置在实验目录的 `checks/` 和 `experiment.json`；上述数字不可当作真实驱动实验结果。
Ruff 的行为调度/MCP/平台模块及相应专项测试检查通过；全仓仍存在既有 lint/格式欠账。

## 2026-10-03：实现中发现平台前提错误

pvpanic 实验显示，仅合并框架阶段仍不足以避免昂贵回退。现将统一逐功能开发中的
`rework target_platform_study` 留在当前功能，保留已完成项、源码及同一会话；
具体问题冻结留痕，不复用为语义正确性证明。同一输入重复请求有界停止。
`driver_checks.progress` 提供无需模型报告的短交接，完整自检报告仍在交付时提交。
合同/环境/证据范围的真正变更保留显式修复边界。机制、验证和限制见
[局部适配与成本优化](LOCAL_ADAPTATION_COST.zh-CN.md)。
