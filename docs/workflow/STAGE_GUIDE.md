# 路线驱动的阶段职责

当前开发分支按三个宏观阶段组织：分析、连续实现、验收。账本检查点不是模型调用次数。
新开发任务默认关闭两个可选模型审查，开启逐行为调度和统一实现；不兼容旧冻结任务。
旧实验目录不改写，审计旧结果请使用其原代码版本。

| 检查点 | 宏观阶段 | 工作及结束条件 |
| --- | --- | --- |
| 01–05 初始化、请求、候选、范围、envelope | 分析 | 程序保存身份、范围、版本约束；有实质歧义才询问 |
| 06 `repository_acquisition` | 分析 | 导入或受控获取固定版本，保留原始来源 |
| 07 `evidence_closure` | 分析 | 选择源入口、直接依赖、公开测试、可能的目标接入入口及必要资料；记录材料缺口。后续可以直接查看固定仓库中的其他定义，无需重跑采集 |
| 08 `environment_recovery` | 分析 | 托管平台验证所选镜像、OVMF、加速器下的基线构建/启动，提交后直接绑定收据；不要求模型额外写设备探针。不支持托管执行的其他平台仍须提供最小环境运行路径及其限制 |
| 09 `knowledge_base` | 分析 | 程序准备带来源的检索入口和共享库快照，无强制模型预读 |
| 10 `target_platform_study` | 分析 | 一次联合分析：源义务 → 粗路径 → 关键前提 → 原文或必要探测 → 契约与行为计划 |
| 11 `migration_handoff` | 分析 | 程序生成上游引用交接，不重写研究总结 |
| 12 `migration_contracts` | 分析 | 程序将同一份已接受分析登记为契约与测试依据，不另开模型任务 |
| 13 `driver_implementation` | 连续实现 | 分析计划直接调度；每轮一个完整行为，框架适配、测试、失败和清理随行为完成；持续复用实现会话 |
| 14 `artifact_preparation` | 验收 | 使用当前源码对应的制品，必要时构建，执行已有身份/存在性检查 |
| 15 `public_qemu_validation` | 验收 | 运行规定的公开断言，保存真实结果；必要修复交回原工作者 |
| 配置的 benchmark | 验收 | 执行固定测例，不能由模型报告替代 |
| 可选审查、封存和审计 | 对应分析/验收 | 仅按明确配置执行；关闭审查不关闭运行验收 |

07 只准备材料，08 只验证环境，10 决定如何迁移。设备操作探测必须服务于 10 中一个会改变
路线的明确问题；源码已足够回答时不探测。探测结果和平台启动都不是迁移正确性证明。

只有一份 Markdown 正文和一个 `.route.json` 引用索引。模型不手写哈希，不另建知识总结、
逐函数报告或第二份实现计划。源义务和判别断言保持冻结；普通源码修改不触发路线续证。
发现具体反证时，工作者可以修改路线/前提及其行为关系，控制器保留其他进度和全部源码。
改变契约本身走显式联合分析修订；不会只改实现路线来弱化验收。

每轮 `continue` 保持当前行为，`done` 最多完成一项；行为完成不等于交付通过。
阶段宏观分组不把普通局部实现修正变成前置阶段返工。跨阶段源要求或环境变更仍遵守已有
开发修订/封存规则。具体接口、验证与局限见 [路线分析规格](ROUTE_GUIDED_ANALYSIS.zh-CN.md)。
