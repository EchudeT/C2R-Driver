# 07 证据采集恢复边界（2026-10-03）

## 实际故障

`pvpanic-behavior-sol-medium-20261003-02` 在 `evidence_closure` 连续进入恢复回合，
不是反复重启整个控制器。提案把整个 Linux `tools/testing` 作为 `test/source_tests`
的来源；该冻结目录展开为 5,418 个条目，包含 12 个空文件。采集策略将空内容判为
`FAILED`，随后缺口归因只返回笼统的 “successful or transiently failed retrieval…”；
模型因此修改缺口说明和 basis，未解决失败路径。

第二个问题是采集未完成时（`artifacts: null`），提交工具仍接受 Markdown `report/pass`。
后续采集入口需要 JSON，导致新的解析失败和更多修复回合。旧实验最终由原恢复门禁暂停；
旧日志、调用和费用均保留，不能把这次失败从成本统计中排除。

## 修复规则

1. 缺口归因统一由 `gap_reason` 供采集器和重新打开项目时的验证器调用。
   `FAILED` 返回 facet、失败数量和前八个具体路径及原因；必须修复输入/工具，
   或移除与任务无关的选择，不能用 `gap.basis` 覆盖实际失败。
2. 原文成功采集但覆盖有限时，保留原文和显式缺口，由受控 facet 的 basis 支撑。
   真正的 `NOT_FOUND` 等获取缺口继续由实际获取结果支撑。不能在读取前仅凭
   `repository_paths` 就要求所有缺口附加 basis：路径可能确实不存在。
3. 提案阶段没有 captured outputs 时，提交工具当场拒绝 `report/pass`；
   工作者可在同一回合改交 JSON，或报告 blocker。拒绝不占用该 job 的提交收据。
   已采集输出的解释、前置修复和真实 blocker 保留原协议。
4. 获取阶段对同一输入及问题允许两次修复：第三个不同工作者响应仍失败时暂停，
   不发起下一次付费调用。控制器重放同一个响应不增加次数。
   提案的 `rationale`、`impact`、`repair_trigger` 文案不重置计数；来源选择、basis
   等输入变化仍可以触发真正的修复。该限制针对相同输入失败，不是整个阶段总调用上限。
5. 提示词明确先搜索相关测试文件/引用，再选择原文。不能为声明“未找到专用测试”
   而纳入整个跨驱动测试树。不设任意文件数量上限，也不把未命中搜索冒充不存在证明。

这些修改不新增 reviewer，不减少验收测例，不把失败采集改写为成功，不改动正在运行的冻结实验。

## 验证和实验边界

`tests/test_evidence_repair_boundaries.py` 是离线合成回归，检查成功原文与有界缺口并存、
失败路径诊断与故障解除后恢复、缺口依据、错误提交的同回合纠正，以及跨重开的重试计数。
配合已有证据复用和端到端恢复测试，针对性检查 27 项通过。

完整测试和静态检查记录见 `docs/audits/evidence-recovery-2026-10-03/`。
这些记录验证控制器边界，不代表 pvpanic 已翻译或实际驱动行为已通过。
新实验使用独立冻结代码、独立 Python 绑定和新模型会话；沿用相同知识库种子、
本地原始仓库、官方 Asterinas 镜像及 KVM 路线。启动后不人工修改候选、测试、提示词或状态。
