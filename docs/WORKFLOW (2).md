当前 developer-evidence 模式一共有 17 个阶段。它把 Skill 中较粗的 0～11 阶段拆成了更容易检查、回退和留存证据的步骤。阶段定义见 src/driver_port_factory/orchestration/migration.py:127，Skill 原始流程见 /home/unix/.codex/skills/knowledge-guided-driver-port/references/workflow.md:5。

先解释四种执行者：

  - static：控制器程序完成，通常不调用 Luna。
  - hybrid：Luna 负责判断、报告或脚本，控制器负责下载、执行和验收。
  - codex：Luna 工作线程负责主要工作，程序负责状态和产物校验。
  - independent：独立审查会话，只审查，不直接修改实现。它可以仍使用 Luna 模型，但与工作者会话隔离。

  ## 第一大阶段：范围与基线

  ### 1. project_init：建立项目

控制器初始化本地 Git 工作区、项目配置、运行模式、角色、Skill 路径、阶段图、状态数据库和内容寻址工件库。它把“这次实验是谁、在哪里、按什么流程运行”固定下来。

失败时不会调用 Luna 猜测修复；配置冲突、数据库损坏或已有项目参数不同会直接停止，修复环境后继续。

  ### 2. request_intake：记录原始需求

记录源平台、目标平台、驱动名，以及“C 转 Rust、用 QEMU 验证”的完整请求。后续阶段不能悄悄换成另一个驱动。

缺少必要字段会停止。已经记录过的请求不能重复覆盖。

  ### 3. driver_candidate_resolution：确认驱动候选

只使用轻量目录和本地元数据，把用户给出的名字解析成候选驱动，并记录：

  - 规范驱动名、源码入口；
  - 设备系列、总线类型；
  - PCI 或其他设备 ID；
  - 可能对应的 QEMU 模型；
  - 匹配是精确还是模糊；
  - 元数据来源。

虽然阶段标记为 hybrid，当前普通路径实际上由程序解析器完成，不需要 Luna。此时也不会下载完整内核仓库。

找不到唯一候选不算技术失败，而是进入下一阶段向用户确认。

  ### 4. scope_confirmation：确认具体范围

如果只有一个精确候选，程序自动确认。存在多个驱动、总线或设备变体时，保存一个合并后的问题并进入 WAITING_FOR_USER，要求用户选择一次。

用户回答后从原状态继续，不会重新问同一个问题。这里的等待不属于 BLOCKED。

  ### 5. migration_envelope_freeze：冻结迁移边界

固定规范驱动、源文件入口、设备和总线、包含范围、排除变体、设备 ID、QEMU 模型和确认依据。可以理解为给后续所有工作画出边界。

后面如果发现选错了驱动或总线，不能自行改写。由于它属于已经封闭的第一大阶段，需要明确重新打开该大阶段。

  ### 6. repository_acquisition：选择并取得三个上游仓库

Luna 只负责选择一套源内核、目标内核、QEMU 的官方仓库和版本。控制器负责：

  - 下载或复用本地缓存；
  - 把 tag/ref 解析成完整 commit；
  - 验证远端来源；
  - 固定源、目标、QEMU 修订；
  - 保存仓库计划、修订清单和来源记录；
  - 创建唯一可写的目标工作树；
  - 检查选中的源驱动身份与阶段 5 一致。

提案格式错误会返回 Luna 修正。网络、Git 或权限故障会保存失败 attempt 并停止控制器，环境恢复后可继续；不会伪造一个成功下载结果。

  ## 第二大阶段：证据与设计

  ### 7. evidence_closure：收集够用的原始材料

Luna 判断本次驱动需要哪些材料，覆盖六类：

  - 源驱动、共享核心、头文件、构建配置；
  - 目标内核 API、类似驱动、构建和打包路径；
  - QEMU 设备模型及测试接口；
  - 硬件手册、寄存器和勘误；
  - 源测试与测试框架；
  - 工具链、镜像、容器和启动脚本。

控制器负责真正读取或下载、计算哈希、记录来源，并生成材料清单、覆盖清单、检索账本和缺口表。Luna 只选择材料，不在这里做 C 语义分析、目标 API 设计或实现。

材料无法取得时必须记录明确缺口及影响。错误路径、网页错误页、来源不足或哈希问题会要求修正；不能把“搜索不到”当作“不存在”。

  ### 8. environment_recovery：先找到一条真的能运行 QEMU 的路

控制器先盘点本机工具、缓存、镜像、容器和可能的制品模式。Luna 再选择成本最低的可复现方式，并编写：

  - 环境报告；
  - environment-smoke.sh；
  - 制品模式；
  - QEMU 入口和恢复路线。

控制器实际运行脚本并跟踪进程。验收要求真实执行 qemu-system-* 实验、没有超时、脚本返回成功；只执行 --version 或 --help 不算。

失败后 Luna 应换一个有因果区别的方案，例如本地 runner、官方容器、预构建镜像、注入或重打包、CI 命令、直接 QEMU 模型测试。缺少完整构建文档本身不能成为 BLOCKED 理由。

  ### 9. knowledge_base：建立本项目知识库

这是程序化阶段。控制器根据阶段 7 的受控材料：

  - 构建本地检索索引；
  - 生成查询命令和查询契约；
  - 生成本项目专用的知识库 Skill；
  - 保存索引完整性和就绪报告；
  - 保证查询结果可以回到原始文件行号或文档页码。

这里不让 Luna填写语义结论。具体目标 API 是否适用，由下一阶段判断。

  ### 10. target_platform_study：研究目标内核怎么接驱动

Luna 阅读目标内核原版源码和文档，完成：

  - 目标架构和驱动框架概况；
  - 每个拟用 API 的定义、调用点、可见性和配置条件；
  - 初始化、注册、匹配、资源取得、IRQ、并发、错误和清理规则；
  - 所有权、生命周期、执行上下文和安全要求；
  - 至少一个类似驱动从注册到打包启动的完整调用链；
  - 目标构建、组件、镜像和 QEMU 启动路线；
  - 是否需要修改已有目标文件，以及修改是否必要；
  - 知识库搜索结果与原始源码行号。

Linux 到 Asterinas 的导航 Skill 在这里是可选辅助资料，结论仍必须回到本次冻结的原始内核源码。

未知 API 必须继续查证、明确标为 UNKNOWN，或提出有边界的目标改动，不能凭记忆发明接口。其语义质量随后由阶段 13 独立审查。

  ### 11. migration_handoff：冻结设计阶段输入

控制器把已经确认的范围、仓库修订、材料清单、环境路线、知识库接口和目标平台研究绑定成一份交接记录。

它的作用是让后续 Luna 明确使用哪一版输入。缺少工件、哈希不一致或依赖未通过时不能生成交接。

  ### 12. migration_contracts：分析 C，并先写清楚怎么翻译

Luna在写 Rust 前完成三类工作。

第一类是源代码闭包：

  - 找齐函数、回调、共享核心、宏、头文件和配置分支；
  - 确认编译器、ABI、defines、include 路径和生成头文件；
  - 检查结构体布局、位域、宽度、符号性和条件编译；
  - 分析寄存器访问、volatile 效果、状态、资源和清理；
  - 分析 TX/RX、ring、IRQ、锁、错误恢复和生命周期。

第二类是迁移契约：为设备匹配、资源、复位、收发、IRQ、并发、错误、恢复、注册和清理等行为建立稳定 ID，分别引用硬件、C、目标 API、QEMU 和验证方式。

第三类是测试计划：逐个检查源测试的刺激和断言，决定保留、适配、排除或保留为受阻项；新测试必须标为 NEW_MIGRATION_TEST。

缺失原始材料可回退阶段 7；环境事实回阶段 8；目标 API 问题回阶段 10；C 语义、契约和测试来源问题在本阶段修复。不能把未完成的编译、布局或测试来源检查推迟到实现阶段。

  ### 13. analysis_review：实现前的独立审查

这是第一次双 AI 验证。独立审查会话检查阶段 10 和 12 的结果，包括：

  - 引用的原始文件和行号是否真实支持结论；
  - C 核心行为是否闭合；
  - 目标 API 是否确实存在并可访问；
  - 类似驱动调用链是否成立；
  - 契约是否覆盖关键功能和安全要求；
  - 测试刺激、断言和来源是否准确；
  - QEMU 能否观察计划中的行为；
  - 哪些结论是 VERIFIED、INFERRED 或 UNKNOWN。

审查者必须一次返回所有已发现问题，每个核心结论和问题都要引用精确位置。它使用只读 Python locator，避免模糊路径和错误行号匹配。

发现问题时可在当前大阶段内回退到 7、8、10 或 12，并只重做受影响部分。通过后，“证据与设计”大阶段被封闭；阶段 14 开始以后不能自动回到这里。

  ## 第三大阶段：实现与交付

  ### 14. driver_implementation：实现 Rust 驱动和公开测试

Luna根据已冻结的目标研究和契约：

  - 实现寄存器、状态和硬件访问抽象；
  - 实现有界复位和初始化；
  - 实现设备注册、匹配和资源管理；
  - 实现发送、接收、IRQ 和延迟处理；
  - 实现锁、所有权、错误、恢复和清理；
  - 适配源测试并补充必要的新公开测试；
  - 添加最小集成和构建配置；
  - 审查 unsafe 的范围和理由；
  - 检查格式、API、架构、锁顺序、生命周期和错误语义；
  - 生成实现快照、合规报告和目标改动清单。

编译、测试或实现缺陷由同一个 Luna 在本阶段修复。若发现前一大阶段的契约根本错误，程序不会自动回退，必须显式重新打开已经封闭的大阶段。

  ### 15. artifact_preparation：把代码变成 QEMU 真能使用的制品

Luna按阶段 8 选定的模式完成构建、注入、overlay、组件打包或镜像重打包，并创建：

  - .dpf-output/runtime-artifact；
  - 可执行的 check-presence.sh；
  - 必要的运行变体；
  - 驱动进入最终制品的证明；
  - 基础镜像、驱动载荷和最终制品哈希。

控制器执行 presence checker、检查普通文件和权限、记录制品身份，并确认当前实现而非旧缓存进入了制品。

打包或身份问题在本阶段修复；行为代码确实改变时回到阶段 14。若只是同一 Luna 已完成并自检过的打包接线修改，控制器可重新绑定实现快照，避免再付一次实现模型调用。

  ### 16. public_qemu_validation：运行公开 QEMU 验证阶梯

Luna 编写 public-qemu.sh、辅助脚本、刺激和 oracle，并通过工具请求控制器执行。控制器负责实际运行、超时、进程跟踪、QEMU 命令捕获、运行制品绑定、日志和退出状态。

验证内容按适用性包括：

  1. 静态和格式检查；
  2. 驱动确实在制品中；
  3. 正确设备枚举、匹配、资源和 probe；
  4. 单次 TX/RX；
  5. 真实中断、确认和后续继续工作；
  6. 保留和适配的公开测试；
  7. 长度边界、错误输入、超时和恢复；
  8. reset/reboot、重复操作和冷启动回归；
  9. 负控制，证明不是错误设备或错误路径产生的结果。

控制器执行后把不可修改的 receipt 返回给同一 Luna。Luna必须查看实际日志，更新同一报告并完成自审。运行失败通常保持阶段 RUNNING：先判断是驱动、测试、harness、打包、目标
API、QEMU 模型还是环境问题，然后最小修复并产生新 attempt。旧的 FAIL attempt 不会被改成 PASS。

  ### 17. public_repair：最终独立证据审查

名字保留为 public_repair，实际职责是最终审查，不是自己修改代码。独立审查会话重新对照：

  - 原始范围；
  - C 行为和迁移契约；
  - 测试矩阵；
  - 当前 Rust 代码；
  - 目标修改；
  - 制品身份；
  - QEMU 脚本、日志、抓包和 receipt；
  - 每个能力的实际状态和限制。

审查者必须一次给出全部问题并引用报告、源码和日志位置。缺陷按最小责任范围回退：

  - 代码问题回阶段 14；
  - 打包和制品身份回阶段 15；
  - 未改制品的 harness、oracle 或运行证据回阶段 16。

修复后阶段 17重新审查。若代码、测试、制品、运行证据和审查规则均未变化，可以复用先前通过的审查；任一绑定哈希变化都要重新审查。通过后当前开发者流程结束。

  ## 失败处理

失败分成六种，不是一律重跑：

  1. 当前阶段可修复错误
     编译、脚本、测试、打包和普通配置错误由当前 Luna 继续修复。阶段保持 RUNNING，有效成果继续复用。

  2. 控制器检查发现问题
     程序保存精确诊断和候选输出，再交给 Luna 判断。Luna可以修正，也可以用证据解释检查器为何误判。程序诊断不会被偷偷改写。

  3. 需要前置阶段返工
     AI通过提交工具指定 rework 和明确阶段。只允许回到同一大阶段内、已经通过且确实是数据前置的阶段。目标阶段变为 READY，受影响的下游阶段变为 PENDING，未受影响证据保留。

  4. 跨大阶段问题
     自动回退被拒绝，并进入 WAITING_FOR_USER，说明需要重新打开哪个已封闭大阶段及原因。不会发生阶段 17 自动跳回阶段 7 的情况。边界规则见 src/driver_port_factory/core/
     phases.py:35。

  5. 真正外部阻塞
     只有缺少外部资源、权限或用户决定，必须改变封闭前提，或者因果修复已经穷尽时，才能提交 blocked。一次失败、仍有下一种修法、编译错误或脚本错误都不算 BLOCKED。阻塞解决
     后由正式命令带原因重新打开。

  6. 反复无进展
     相同前置修复请求在实质输入没有变化时不会无限循环；第二次相同修复指纹会触发耗尽保护。相同 checker/执行请求反复出现也会暂停，避免持续产生付费调用和后台进程。修复文
     件或记录外部条件变化后再恢复。

所有状态改变都必须经过提交工具和控制器。Luna 的最终聊天文字不会改变阶段状态。PASS 只能在规定产物经过校验并绑定后由程序写入；失败 attempt、日志和退出码均作为不可变历
史保留。相关协议在 src/driver_port_factory/orchestration/protocol.py:79 和 src/driver_port_factory/core/checker_decision.py:28。
