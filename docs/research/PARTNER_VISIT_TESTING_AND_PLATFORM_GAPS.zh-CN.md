# 驱动迁移的实验验证与目标内核能力适配

合作方视察补充材料｜2026 年 10 月 12 日｜配套[主汇报](PARTNER_VISIT_BRIEFING.zh-CN.md)与[v3 设计说明](PARTNER_VISIT_V3_MECHANISMS_AND_QA.zh-CN.md)

本项目将驱动迁移定义为：在固定设备与功能范围内，依据 Linux 驱动及相关框架的行为，在星绽中实现可运行的设备服务。实验评价围绕**实际设备功能、源行为保持和目标系统集成**展开；迁移产物包括驱动以及实现这些行为所必需的框架适配。

## 一、驱动如何测试，测试如何构造？

### 先区分源驱动、迁移驱动与测试代码

**源驱动是 Linux C 代码，迁移后的驱动是星绽 Rust 代码；测试代码按运行位置选择语言。** 用户态设备测试使用 C，内核行为测试使用 Rust，网络场景使用 shell 脚本组织 iperf3；宿主 Python 运行器负责启动、调度和收集结果。

| 测试对象 | 测试代码与来源 | 怎样编译或准备 | 实际运行位置 | 怎样调用被测驱动 |
| --- | --- | --- | --- | --- |
| RNG、VirtIO Block、NVMe | 星绽上游的 **C 回归程序**，例如 hwrng.c、nvme.c | 在固定开发容器中用 GCC 编译为静态用户态程序，打包进启动文件系统 | QEMU 内的**星绽用户态** | 设备文件或文件系统操作进入内核，最终调用 Rust 驱动。 |
| VirtIO 网卡；igb 的 TCP／UDP 场景 | **shell 脚本 + iperf3 可执行程序** | 准备现有脚本、iperf3 及运行依赖 | **星绽用户态与宿主对端** | 使用 socket，流量经过星绽协议栈、Rust 驱动和 QEMU 网卡。 |
| evbug、NE2000；igb 的设备控制场景 | 项目固定的 **Rust 内核测试代码**，例如 evbug_public.rs、ne2k_public.rs | 固定测试模块与 Rust 驱动一同编译进完整星绽内核 | QEMU 内的**星绽内核态** | 调用真实输入框架或设备操作，检查事件、帧、回调和生命周期。 |
| 启动、外部对端及结果核对 | **Python 运行器 + JSON 场景定义** | 实验方准备固定工具与判据 | **宿主侧**，部分工具在宿主容器中运行 | 启动 QEMU、发送执行命令、提供网络对端并核对实际结果。 |

**C 测试在开发容器中编译，得到的程序在星绽里运行。** Rust 内核测试在构建阶段进入星绽镜像，运行时与被测驱动处于实际内核环境。测试来源与编译方式分别记录，便于复现。

### 路径一：C 用户态测试怎样执行？

#### 原理

准备阶段将已有 C 测试编译并打包；迁移者将 Rust 驱动及必要适配编入星绽；运行器启动最终镜像，在星绽 shell 中执行测试程序。

C 程序通过 open、read、write 等操作进入系统调用、文件系统或设备框架，触发 Rust 驱动与设备。返回结果由 C 程序中的原断言检查；宿主运行器进一步解析各函数的断言汇总和退出状态。

```mermaid
flowchart LR
    C[C 测试源码] --> G[GCC 编译为用户态程序]
    G --> U[打包并在星绽用户态执行]
    U --> K[系统调用与文件或设备框架]
    K --> D[迁移后的 Rust 驱动]
    D --> Q[QEMU 设备]
    Q --> R[操作结果经内核返回]
    R --> A[C 程序中的断言]
    A --> H[宿主收集测试结果]
```

#### 例子 A：NVMe 的 C 程序如何判定正确

上游 nvme.c 编译成用户态程序后，在星绽中挂载设备上的 ext2 文件系统，写入 64 KiB 数据，再读回来。**C 测试代码自己执行比较：**写入和读取长度须符合要求，读回内容须与原数据逐字节相同，打开、定位及关闭也须满足原断言。

同一份 C 程序可以检验不同 Rust 驱动实现，因为它依赖的是用户可见的设备服务。

#### 例子 B：RNG 的 C 程序如何调用驱动

上游 hwrng.c 在星绽用户态打开随机设备文件，执行并发读取、短读、大读及阻塞／非阻塞操作，原断言检查返回长度、错误和数据表现。实际执行会经过调用方缓存、完成通知及迁移后的设备驱动。

### 路径二：Rust 内核测试怎样执行？

#### 原理

实验方预先提供 Rust 测试模块和 JSON 场景定义。实施者将测试模块接入内核，并提供薄的触发入口；运行器向指定 proc 文件写入场景名称，入口转调固定 Rust 测试函数。

Rust 测试函数负责构造输入、调用真实操作及执行内核断言。宿主按固定 JSON 场景核对串口输出和外部对端观察。**proc 接口负责触发测试，Rust 断言和宿主观察负责判断结果。**

```mermaid
flowchart LR
    S[宿主 Python 运行器读取 JSON 场景] --> P[向星绽 proc 入口写入场景名称]
    P --> T[执行已编入内核的固定 Rust 测试函数]
    T --> D[真实输入框架或迁移后的设备驱动]
    D --> O[产生事件或实际设备收发]
    O --> A[Rust 内核断言与宿主观察器共同核对]
```

#### 例子 A：NE2000 的测试代码如何检查收发

ne2k_public.rs 在内核中构造以太网帧，调用真实设备发送操作。迁移后的驱动经 QEMU 网卡送出帧，宿主 Python 对端检查发送数据并按固定规则回复。Rust 测试等待设备接收引发的回调，再取得回包，断言长度和内容符合预期；恢复场景实际调用停止／启动，再完成帧交换。

#### 例子 B：evbug 的测试代码如何检查事件

evbug_public.rs 创建合成输入设备，注册到星绽真实输入框架，提交已知事件，再撤销观察者。Rust 断言检查处理器数量与引用释放；宿主比较实际日志中的事件类型、编码、值、顺序，以及撤销后的静默。

### 路径三：shell 和 iperf3 怎样测试网卡？

上游 run.sh 在星绽中启动 iperf3 服务端，宿主 host.sh 启动客户端，UDP 场景按固定脚本选择方向。数据实际经过星绽 socket、TCP／IP 协议栈、Rust 网卡驱动及 QEMU 网卡，与宿主对端交换。

宿主运行器检查脚本结果和发送／接收统计，要求两端有非零传输。igb 的 TCP／UDP 场景使用网络程序，队列与恢复场景另由 Rust 内核测试触发和观察。

### 为什么这种测试组织合理？

**测试语言跟随观察层次。** 用户态 C 程序检验外部设备服务，Rust 内核测试直接构造注册、设备状态和生命周期操作，shell 与 Python 组织运行和外部观察。被测驱动都以 Rust 实现在星绽中运行。

**测试与实现分别控制。** C 回归程序和原生网络脚本来自星绽上游，Rust 内核测试来自项目预先固定的公开夹具。两种方法使用相同测试；迁移者修改驱动与必要适配，实验方保持测试源码、输入及断言固定。

**入口与判断分开。** 系统调用、设备接口和 proc 文件负责发起操作；数据比较、事件序列、回调与状态断言决定结果。内核触发入口只接入固定测试函数，不提供替代测试逻辑或自行生成成功判定。

**测试代码不随驱动语言转换。** 这里复用的是星绽已有 C 用户态测试，并补充固定 Rust 内核测试。Linux C 驱动是迁移输入；测试则独立规定操作与预期结果。追加评价保持封存的 Rust 驱动固定，改变测试输入后重新执行。


### 1. 评价对象：完整目标内核中的设备服务

#### 原理

我们采用**受控的跨平台系统级评价**（controlled cross-platform system evaluation）。实验单位是一项冻结的驱动迁移任务：固定源代码版本、目标代码版本、设备型号、功能范围和执行环境，对迁移后的完整星绽内核进行构建、启动及设备行为检查。

评价沿实际服务路径设置观察：用户或内核调用方发出请求，目标框架将其交给迁移后的驱动，驱动访问 QEMU 设备，完成结果返回调用方。软件输入观察者则通过真实的输入注册、分发与撤销路径接受刺激。

这种评价将设备协议、资源使用、中断进展与调用方接入纳入同一运行过程。成功的交付需要在完整内核中建立可用服务，并满足冻结测试的行为断言。

### 2. 测试构造：复用上游回归测试，补充固定的行为场景

#### 原理

测试分为两类，分别保留其来源和判据。

**上游回归测试复用。** 对 RNG、VirtIO Block、VirtIO Network 和 NVMe，我们复用星绽上游已有的 C 回归程序或网络测试脚本。实验准备负责编译、打包和执行，保留原测试逻辑与断言。这使生成方法面对预先存在的外部验收标准，验证迁移实现与目标调用方的真实兼容性。

**固定行为场景。** 对 evbug 和 NE2000，项目准备固定的内核测试夹具（test fixture），通过目标系统的真实接口构造输入、调用设备操作，再由内核断言和宿主观察器共同判断结果。夹具、输入和断言在该次翻译前固定，两种方法使用相同材料。更大的 igb 任务进一步结合设备控制夹具、原生网络流量与硬件队列观察。

这里，测试夹具承担刺激与观察，生成的驱动承担设备行为。实施者负责将真实操作接入固定入口，测试输入与成功条件由实验方控制。

| 任务 | 测试来源与构造 | 主要刺激 | 主要判据 |
| --- | --- | --- | --- |
| VirtIO RNG | 上游随机设备回归程序 | 并发读取、短读、大读、阻塞／非阻塞及设备文件操作 | 原 15 个测试函数的断言结果，包含返回长度、错误与读取行为。 |
| VirtIO Block | 上游块设备与 ext2 回归程序 | 文件读写、部分读写、跨边界访问与恢复 | 原三项程序、八个测试函数的断言与数据比较。 |
| VirtIO Network | 上游 TCP、UDP RX、UDP TX 脚本 | 通过实际网卡与宿主对端传输数据 | 脚本成功，发送端和接收端均有非零传输。 |
| NVMe | 上游直接 I/O 回归程序 | 在真实命名空间挂载文件系统，写入并读回 64 KiB 数据 | 原断言及逐字节一致性检查。 |
| evbug | 固定输入子系统夹具 | 既有／新设备、事件批次、边界值、注销与再注册 | 精确事件顺序与内容、连接／断开记录、处理器及引用计数、注销后的静默。 |
| NE2000 | 固定设备夹具与宿主网络对端 | 设备探测、多长度帧、突发接收、重复停启 | MAC 与设备状态、实际帧长度和内容、回调进展、恢复后收发。 |
| igb 多包实例 | 固定设备控制场景与原生网络脚本 | 单／双队列、RSS 多流、停止／重启、TCP／UDP | 设备和调用方均有进展，两个硬件接收队列及多流交付，完整六项场景。 |

测试来源与源语义依据分别记录：上游测试提供目标系统的验收判据，Linux 驱动与相关调用方提供迁移要保持的行为依据。本文中的上游回归测试复用，指复用星绽原有测试。

#### 例子 A：RNG——通过用户可见行为检验完整读取链

测试通过设备文件发起读取，覆盖多个读者、不同数据长度和阻塞／非阻塞模式。因此，实际检查会同时经过设备入口、共享调用方、缓存补充、完成通知和驱动队列。

历史 Codex 的一轮过程在多项检查通过后，缓存预热后的非阻塞读取仍出现返回长度不符。模型随后补齐共享调用方缓存。这一真实反例说明，现有测试能够暴露设备侧实现与上层读取之间的配合问题。[原始依据 C1](PARTNER_VISIT_EVIDENCE.zh-CN.md#c1)

#### 例子 B：evbug——构造可精确核对的事件与生命周期轨迹

夹具创建合成输入设备，将其注册到星绽真实输入框架，再提交事件。宿主观察器比较事件类型、编码、有符号值和顺序，内核同时检查处理器数量、设备数量及引用恢复。

生命周期场景先注册设备，再注册观察者，并继续加入新设备；撤销观察者后再次发送事件，确认该绑定停止输出。边界场景进一步检查空批次、整数极值与再次注册。

这些输入使连接、分发与撤销的结果具有明确的测试预言（test oracle）：预期轨迹由固定刺激和既定行为规则给出，而非由候选实现的输出反向确定。

#### 例子 C：NE2000——用真实对端验证帧与设备进展

测试经 QEMU RTL8029 网卡与宿主对端交换实际以太网帧。常规流量包含 96 次交换，使用 60、61、127、256、513、1514 字节六种长度，进一步执行 16 帧突发接收及三次停止／启动恢复。

接收端比较帧长度和内容，固定序号和数据变换使每次交换可追踪；测试也要求发送完成与接收回调在有界时间内取得进展。这样能同时检查设备收发、奇偶长度处理、中断和生命周期配合。

### 3. 执行控制：固定判据与同一最终候选

#### 原理

我们将测试定义与候选生成分离：公开用例在翻译前固定，实施者可以读取并用于开发检查，冻结的测试源码、断言和运行配置通过哈希及原文核对保持一致。最终结果由运行器从实际执行记录中提取。

开发阶段允许在当前工作包内运行相关用例以消化反馈；交付后，对**同一最终源码与运行产物**执行完整公开套件。完整批次覆盖所有必需场景，明确区分开发观察、工作包完成和最终验收。

C 回归程序按预期测试函数逐项解析：每个函数都必须实际产生成功断言，且失败数为零。设备不可用而跳过测试，不满足验收条件。网络场景要求实际传输，设备启动标记与功能结果分别记录。磁盘类测试使用共同种子的独立可写介质，使前一个场景的状态与后一个场景隔离。

测试准备还使用**正负控制**校准观察链。对具有原生参考驱动的任务，原始星绽实现作为正向控制；移除驱动后的可启动内核作为负向控制。二者帮助确认测试既能执行，又能识别设备功能缺失。原生参考由实验方持有，模型获得的是移除实现后的任务输入。

#### 例子 A：VirtIO Network——校准运行环境与功能判据

保存的原始参考记录显示，三项网络场景全部通过；移除驱动后，内核仍可构建与启动，但三项场景均因实际网卡不可用而失败。这组控制说明，设备功能是测试成功所需的条件。[正向记录](../../../experiments/native-suite-current-20261006/operator/virtio-net/positive.json)、[负向记录](../../../experiments/native-suite-current-20261006/operator/virtio-net/negative.json)

#### 例子 B：igb——将多包进展汇合为整体交付

单队列基础服务和双队列扩展分别完成后，控制器对同一最终候选执行六项公开场景，六项全部通过。最终批次中各项均为新执行记录，包内开发结果与整体验收分别保存。[实际记录](../../../experiments/intel-suite-unified-20261012/trials/dpf/igb/intel-medium-size-advice-20261012-m2-igb/run/.dpf/public-qemu/7407a3ecd5bd40af830740008e3d6b7a/attempt.json)

### 4. 追加评价：封存候选上的输入变种

#### 原理

为评价生成结果对同功能不同输入的适应性，我们在封存候选上执行**参数化追加评价**（post-generation parameter-variant evaluation）。变种由确定性生成器构造，改变输入实例、数据长度、既有并发数量或网络负载，保留原功能与通过判据。

执行前记录候选源码和产物哈希；评分结果不回传生成工作者，评分期间保持驱动实现固定。测试参数、派生测试文件、构建与运行记录均保留，使变种与原测试的关系可以核对。

不同任务采用相应执行方式：用户态回归程序替换测试介质中的程序，网络变种改变宿主流量参数；内核夹具变种从封存源码构建，仅改变测试夹具，并核对其余封存源码。公开验收与追加成绩分别报告。

#### 例子 A：RNG——改变读取长度与读者数量

追加组采用不同短读、大读长度及并发读者数量，继续执行原 15 个测试函数和相应断言。这检验同一驱动能否处理不同数据规模及既有并发功能的变化。

#### 例子 B：NVMe——改变传输规模与数据实例

原场景使用 64 KiB 直接 I/O，追加组使用 8 KiB 与 32 KiB，并改变数据种子，保留写入、读回和逐字节比较。它从相同功能的不同传输规模观察数据路径。

#### 例子 C：NE2000——改变帧长、数量与数据模式

追加组改变 MAC、帧长度组合、交换数量及数据模式，保留探测、实际收发与恢复判据。驱动必须处理这些真实输入，固定测试对端继续核对实际帧内容。

本轮追加评价采用 **开发者追加证据**（developer evidence）的学术定位，用于陈述封存候选在这些输入变种下的表现；论文与汇报沿用这一证据类别。

### 5. 对照与报告：保证比较对象及统计口径可追踪

#### 原理

每个配对任务中，v3 与 Codex 使用相同模型及推理强度、源／目标快照、设备与功能范围、共同环境资产及最终验收判据；各自工作区独立，方法特有的分析、调度和工具作为处理条件保留。

协议记录源码版本、设备配置、环境身份、测试来源和方法版本。结果按驱动与批次分别报告完整套件通过情况、单项功能表现、追加评价、总用时与模型费用，并保留全部尝试及重跑身份。不同历史配置按各自协议解释。

这形成清晰的实验链：**任务定义 → 测试来源与判据 → 固定输入和环境 → 候选生成 → 最终验收 → 封存后的追加评价**。每项报告结果能够回到具体候选、测试及执行记录。

### 6. 可直接用于 FSE 论文的实验方法表述

> 我们采用受控的跨平台系统级评价研究 Linux C 驱动向星绽 Rust 内核的迁移。每项任务固定源／目标版本、设备配置与功能边界，并在完整目标内核中执行生成驱动。测试体系结合三类执行路径：上游 C 回归程序经 GCC 编译后在星绽用户态运行，通过系统调用检查设备服务；固定 Rust 内核测试与驱动共同构建，通过真实框架及设备操作检查进展和生命周期；网络脚本组织 iperf3 在星绽与宿主之间通信。宿主运行器收集程序断言、内核观察及对端结果。最终验收绑定同一源码快照与运行产物，进一步在封存候选上执行确定性输入变种，保持驱动实现与功能判据固定。配对方法共享任务、环境与最终判据，公开验收、追加评价及资源投入分别报告，并提供版本、哈希和运行日志以支持复核与复现。

## 二、星绽存在底层缺口时，迁移怎样继续？

### 1. 研究对象包括已有框架上的驱动重建，也包括新设备能力接入

#### 原理

本项目包含两种互补的任务构造。

**已有驱动的受控重建。** 对 RNG、VirtIO Block、VirtIO Network 和 NVMe，从固定星绽版本移除对应驱动及直接注册，保留其余内核框架。这样可以用现有回归测试及原生参考校准评价环境，控制任务之间的输入差异，研究跨平台行为重建与实际集成。

**原目标尚未支持的设备迁移。** evbug、NE2000 以及扩展任务 igb／e1000e 的相应实现原本不存在于固定目标版本。任务从该原始目标开始，由迁移者实现新驱动并补齐必要接入与共享机制。

因此，选题覆盖了可控重建和新能力接入。**共同前提是固定平台能够运行目标任务的基础环境；所需设备服务及其具体框架适配，由迁移过程完成。**

### 2. 缺口处理：从缺失接口追到缺失保证

#### 原理

跨内核迁移首先需要明确源行为由什么条件保证。目标缺少同名接口时，分析继续核对现有机制能否在该调用场景下提供相应行为，然后确定适配层次。

| 情况 | 处理方式 | 对迁移的作用 |
| --- | --- | --- |
| 目标已有基础机制，表达与 Linux 不同 | 将源行为映射到目标原生的状态、同步与生命周期安排 | 复用目标架构，保持源行为所需条件。 |
| 现有框架缺少当前驱动需要的接入或资源能力 | 在驱动及相关框架／调用方中补齐具体能力 | 建立完整服务路径，让新设备被实际使用。 |
| 必需的底层能力涉及更大的平台依赖 | 在规划中明确依赖及其对功能范围的影响，组织前置能力建设或显式范围决策 | 将平台条件作为明确研究输入，保持任务与验收一致。 |

处理依据是范围内行为的实际需要。任务范围由实验方事先确定，实施方案围绕这些要求修正；必要能力进入当前完整工作包，或成为具有明确保证的前置能力。

对于系统级前置能力，先建立可复用保证，再实现依赖它的设备服务。例如，如果一个新任务需要的中断投递或 DMA 基础能力尚未建立，就将其作为前置平台工作明确输入、输出与验证方式，驱动随后接入这项能力。具体操作可以变化，源行为要求保持稳定；范围调整须形成显式任务定义，并据此安排评价。

因此，缺口可以在规划中被识别，也可以由设备运行提供新事实。两种情况下，都围绕相同问题推进：**补齐后由谁提供什么保证，哪些实现依赖它，怎样在真实调用路径上确认结果？**

### 3. 实际案例：必要的目标框架能力如何补齐

#### 例子 A：NE2000——为 PIO 接收补齐 CPU 可写缓冲区

星绽原有网络接收缓冲区面向设备 DMA 写入；NE2000 通过端口读取设备数据，再由 CPU 填入目标缓冲区，两者的访问条件不同。

实际迁移扩展了共享接收存储，增加适合 CPU 填充的路径，同时保留原 DMA 存储路径；缓冲区准备与分配时点随设备执行上下文一起安排。

这项修改位于共享网络框架。v3 将设备收发、中断、缓冲区适配与恢复放在一个完整工作包内，相关事实同步进入方案，最终探测、收发和恢复三项通过。[实际候选](../../../experiments/public-suite-info-20261006/trials/dpf/ne2k-pci/gpt6-sol-medium-premise-ne2k-20261011-01/run/work/target/kernel/core/comps/network/src/buffer.rs)、[过程与验收](PARTNER_VISIT_EVIDENCE.zh-CN.md#v3)

#### 例子 B：igb——补齐真实协议栈对新网卡的接入

原目标网络初始化按 VirtIO 的名称和具体类型选择设备。新 igb 驱动完成 PCI 探测与网络注册后，还需要让上层协议栈实际使用这张网卡。

实际迁移适配了网络接口初始化，使注册的 igb 设备进入真实 eth0。基础工作包同时拥有设备获取、收发、中断、资源回收、停止／重启与上层接入；后继工作包再实现双队列和 RSS。

最终同一候选的六项场景全部通过，硬件队列与上层多流均有进展。这展示了新设备驱动与目标调用方适配共同形成完整服务。[实际规划](../../../experiments/intel-suite-unified-20261012/trials/dpf/igb/intel-medium-size-advice-20261012-m2-igb/run/work/stage-work/target_platform_study/report.md)、[实际接入](../../../experiments/intel-suite-unified-20261012/trials/dpf/igb/intel-medium-size-advice-20261012-m2-igb/run/work/target/kernel/core/src/net/iface/init.rs)

#### 例子 C：pvpanic——用目标原生机制承担源行为

源驱动在终止前通知设备。目标终止处理器采用首次注册生效的机制，迁移因此选择在原生终止动作前插入通知，并统一安排非等待共享状态。

这里通过调整责任分配完成适配：既保留通知条件，也沿用目标原生终止路径。实际 panic、关机和生命周期运行，以及包含持锁场景的五项内核测试，提供了对应证据。[实际过程](PARTNER_VISIT_EVIDENCE.zh-CN.md#v3)

#### 例子 D：NE2000——用停止与安全持有表达生命周期

固定目标网络注册表没有设备撤销接口。实际迁移在停止时禁止收发、使设备和回调静止，并安全持有仍被注册表引用的设备状态；再次启动时恢复服务。

固定恢复夹具实际检查重复停止与启动、停止后的收发状态及回调计数，并在恢复后完成帧交换。它展示了接口差异的另一种处理：利用目标生命周期机制安排责任，以行为条件检查新的实现方式。[固定恢复场景](../../../driver-experiment-env/src/driver_port_factory/data/public-tests/ne2k-pci/ne2k_public.rs)

### 4. 缺口处理如何体现 v3 的三个特点？

#### 原理

**提前消化返工。** 在规划时核对影响接入、资源和同步的必要能力，尽早决定采用现有机制还是补充框架能力。先解决会改变方案的条件，再推进依赖这些决定的实现。

**从功能对齐推进到语义对齐。** 补充能力围绕源行为组织。例如，CPU 能写缓冲区之外，还要满足数据保持和执行上下文；网卡被注册之外，还要能被真实调用方使用并完成生命周期操作。

**单工作者以精简上下文完成完整机制。** 当前驱动所需的框架修改和调用方接入与设备实现一起处理，使上下层决定能够连续协调。较大的前置能力通过明确目标与依赖组织，后继复用已经建立的保证。

三个特点共同支持一种**以行为保持为目标的驱动—框架协同迁移**（behavior-preserving driver–framework co-migration）：以源行为确定适配目标，提前查证平台条件，在完整机制内补齐必要能力，并通过实际服务路径确认交付。

### 5. 可直接用于现场追问的回答

> 我们的任务同时覆盖已有框架上的受控驱动重建，以及原目标尚未支持的新设备接入。遇到星绽底层缺口时，先根据源行为确定缺少的是哪项保证，再决定复用目标机制、扩展共享框架或建立前置能力。NE2000 已实际补充 CPU 填充接收缓冲区的能力，igb 已适配原先绑定 VirtIO 的上层网络接入。v3 将这些必要适配与驱动作为完整机制连续实现，使最终交付包含真实可用的设备服务。
