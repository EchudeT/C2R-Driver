# 从 Linux 到星绽：让 AI 驱动迁移持续保留行为责任

合作科研项目进展汇报｜2026 年 10 月 12 日｜主线约 20–25 分钟，问答可按需展开

## 1. 我们发现了什么问题

**我们在多类驱动的实际迁移中发现：AI 能读懂源代码，也能修好测试中的故障，但源系统依赖的行为条件，未必能在跨框架适配、分析交接和后续修复中持续成立。**

本项目将 Linux 的 C 驱动迁移到星绽（Asterinas）的 Rust 内核。难点在于，一项设备行为通常由驱动、Linux 共享框架、调用方以及运行上下文共同保证。迁移需要重新分配这些责任：目标系统已经保证什么，驱动还要补什么，补充机制又在什么条件下有效。

我们首先看两个实际发生的问题。

**随机数驱动：设备能返回随机数据，上层读取仍可能不一致。** 一轮 Codex 实现把设备数据直接交给用户。短读后的非阻塞读取暴露问题后，模型追查 Linux 的共享随机数框架，才补上原来由调用方承担的缓存责任。另一个模型的迁移中，设备未真正接入，全部设备测试被跳过；模型随后找出接入遗漏并修复。这说明“设备侧代码已写好”和“完整调用链已实现”是两个不同的判断。[依据 C1](PARTNER_VISIT_EVIDENCE.zh-CN.md#codex)

**NE2000 网卡：接口能接受缓冲区，不代表缓冲区适用于当前执行方式。** Codex 迁移时先遇到目标接收缓冲区不允许 CPU 写入，修好收发之后又遇到中断上下文中的分配问题。v2 的另一轮迁移则长期将收发停滞解释为“中断没有送达”；取得 CPU 状态后发现，中断已经进入，却在等待被打断的发送路径持有的锁。这些问题都影响真实收发，涉及目标保证的适用条件。[依据 C5、V2-B](PARTNER_VISIT_EVIDENCE.zh-CN.md#v2)

模型后来修复了其中很多问题。我们要解决的研究问题由此更具体：

> **怎样把源系统的行为条件落实到目标承担方，并让这份责任在分析、实现、测试和修复中持续有效？**

费用是可能改善的结果。方法设计首先需要解释：哪些条件容易丢失，为什么现有过程不能稳定保留它们，以及我们怎样缩短“条件失效”到“取得有效反馈”的距离。

## 2. 从多个案例判断，哪些是主要问题

我们核对了随机数、VirtIO 网卡、NE2000、NVMe、输入事件和块设备的原始过程，保留成功与失败两面的证据。反复出现的问题可以归纳为三类。

| 主要问题 | 多案例中的具体表现 | 为什么影响迁移 |
| --- | --- | --- |
| **完整行为跨越源文件边界，读过的条件还可能在交接时丢失** | RNG 的调用方缓存和设备接入；evbug 在三项公开测试通过后，才补查目标事件表示是否覆盖源驱动接收的事件；v2 的 pvpanic 已读到“获取锁失败立即返回”，交接摘要却只保留“锁保护状态”。 | 正确移植某个函数，不足以保证调用方看到的行为；遗漏的触发条件也不会因引用了源码而自动恢复。 |
| **目标框架的保证有条件，共享状态贯穿正常、错误和并发路径** | VirtIO 网卡的设备读写权限与现代报文头条件；NE2000 的 CPU 写权限、分配上下文和硬中断锁；NVMe 恢复流程曾覆盖仍待重试的写入数据。 | 类型正确、单条路径通过，仍可能破坏跨路径的不变量。 |
| **运行反馈需要能区分失败原因，并对应当前候选** | Codex 网卡曾因观察错误日志通道而怀疑服务未启动；v2 NE2000 多轮重复“中断未送达”，直到取得 CPU 状态才定位死锁。 | 相同表象可能对应不同原因；连续运行和增加轮数不等于增加有效证据。 |

这些不是“Linux 和星绽天然不兼容”。例如，NE2000 可以通过调整状态与缓冲区归属实现真实收发；RNG 可以在目标调用链中重新安排缓存责任。问题在于能否识别必要条件，并解释新的安排如何提供相同的范围内保证。

我们没有把构建参数、报告格式、临时路径等偶发问题作为中心动机。它们影响工程效率，但不足以解释驱动迁移的研究难点。块设备的 Codex 过程就是一个对照：模型较早正确安排了请求缓冲区的持有时长，后来主要处理启动环境并完成测试，不能将它描述成语义迁移失败。[依据 C2—C7](PARTNER_VISIT_EVIDENCE.zh-CN.md#codex)

## 3. 先明确正确性依据，避免把预期效果当成正确答案

本项目保留的是**固定源版本、设备配置和约定功能范围内的行为**。判断依据包括源驱动及相关共享框架、设备协议、目标接口与实际调用上下文。测试用于观察候选是否满足其中的具体要求。

例如，pvpanic 的“不能取得锁就立即返回”来自源实现；目标可以更换同步方式，但不能把它改成等待，再以串行通知测试通过为理由宣布行为已保留。NE2000 的收发进展则依赖正常调用与硬中断可以共同访问状态，而不是任选一种锁就自然正确。

与此同时，目标不需要逐行复制 Linux。迁移范围可以事先排除某些设备变体或管理功能；目标也可以将责任分配给不同组件。必须说明排除依据和保证方式，不能因为测试没有覆盖、接口不好实现，就临时删除要求。

**公开测试通过只证明已执行场景的表现。** 未运行的失败、并发或生命周期条件，需要保留源码论证和验证边界，不能写成已通过。分析表完整、引用有效，同样不证明源行为没有漏项。

## 4. Codex：已有很强的迁移能力，为什么还需要专门的方法

我们的基线是 Codex 加持续任务目标，能够读取完整源／目标树，自主规划、实现、构建、运行和修复。基线提示已经要求保留源语义、阅读相关调用方、接入真实设备，并明确测试不是规格。因此，比较的出发点是：在这些能力之上，专门组织迁移责任是否仍有价值。

### 4.1 它能够自行发现并修复问题，但关键条件有时很晚才进入实现

RNG 的共享缓存问题在上层读取暴露差异后才被补回；VirtIO 网卡的接收、发送权限分别经过运行修正，现代设备报文头条件也在后续调试中才补齐。它们不是“模型完全不懂协议”，而是不同位置的条件没有同时约束最初的适配。[C1、C2](PARTNER_VISIT_EVIDENCE.zh-CN.md#codex)

evbug 的过程更能说明测试与源责任的关系：三项公开测试通过后，模型继续查源行为，发现目标原有事件表示只覆盖部分事件种类，于是扩展表示并重新验证。Codex 能做这项检查；我们希望将“范围内全部实际交付事件都要被观察”作为实施时持续可见的责任，减少依赖完成后的再次发现。[C6](PARTNER_VISIT_EVIDENCE.zh-CN.md#codex)

### 4.2 局部修复还可能引入跨路径问题

NVMe 的一轮过程在公开读写检查通过后继续补充恢复逻辑。恢复阶段借用了正常读写的数据缓冲区做设备识别，失败后重试写入又继续使用该缓冲区，因而可能把待写数据覆盖。模型随后发现并分离了缓冲区。这里核对到的是实际修改中的静态错误链；没有观察到注入故障后的磁盘损坏，不能夸大为已发生的数据事故。[C4](PARTNER_VISIT_EVIDENCE.zh-CN.md#codex)

NE2000 的 Codex 候选也多次在三项测试通过后继续源行为自查，补充错误与恢复路径；调整分配方式时又暴露中断上下文问题，最终再次修复并通过。这说明修复不是孤立的代码替换：它可能改变多个路径共同依赖的资源和上下文条件。[C5](PARTNER_VISIT_EVIDENCE.zh-CN.md#codex)

### 4.3 自主诊断需要可信的运行边界

一轮 VirtIO 网卡调试把缺少输出解释为初始化或服务未启动，经历修改、撤销和控制重建后，才发现应观察的输出在另一个串口日志中。修正观察通道后，低速流量完成 429 次收发。相关调查约跨越 20 分钟，包含合理排查和构建，不能全部算作浪费；它说明运行接口本身也是有效反馈的前提。[C3](PARTNER_VISIT_EVIDENCE.zh-CN.md#codex)

这些日志支持的结论是：**通用模型具有解决问题的能力；专门流程应帮助它更早保持必要条件，并使修复结果可核对。** 不能仅凭中间错误宣称 Codex 无法翻译驱动。

## 5. v1：用证据与阶段交付约束迁移，剩下的问题是反馈距离

v1 将迁移组织成源码与知识准备、目标研究、实现、产物准备和设备验证等阶段，固定范围与判据，并保存证据和阶段结果。它针对自主迁移过程不易核对的部分，明确“依据是什么、当前完成到哪里、还有什么未知”。v1 已经使用知识检索，不能把 v3 的进步解释成第一次引入知识库。

**NE2000 的实际过程展示了它的价值。** 前期知识索引缺失时，研究阶段请求修补；修补后可以查询原始定义，仍将 CPU 填充接收缓冲区、中断路由、锁与 I/O 条件列为未完全解决的设计问题。它区分了“资料已具备”和“目标已经支持”，没有把知识库就绪直接当成迁移成功。

但这轮日志也暴露了阶段组织的不足：

1. 研究准备完成后，实现仍因目标端口所有权限制调整数据传输方案，又发现访问设备前未启用 PCI I/O。
2. 实现阶段约 84 分钟后，编译、静态检查和辅助测试通过，却明确记录真实设备的探测、收发、中断与重复启动尚未运行。
3. 到产物阶段，才在真实设备路径上发现目标地址绑定限制，修补并重建后完成单次启动的 71 次收发；三次启动验证仍留给控制器。该产物阶段约 31 分钟。

这些时长不是浪费量，也不能与其他版本不同模型、不同范围的时长直接算加速比。它们具体说明：**广泛的前期调查无法预先解决所有实现前提，而阶段内完成不一定已经取得完整设备反馈。**

因此，v1 的贡献应保留：证据、范围和诚实的验证边界。后续需要改的是把框架适配、实现和必要运行反馈放得更近，而不是继续扩大前期调查。[依据 V1](PARTNER_VISIT_EVIDENCE.zh-CN.md#v1)

## 6. v2：轻分析与连续实现确实推进了迁移，但连续性还不够

v2 减轻前期研究，把实现、检查和修复放入持续工作，按能力目标推进。它针对 v1 的反馈距离，将具体 API 与设备问题留给实际实现过程解决。

### 6.1 改进确实有效：NE2000 从探测推进到收发和恢复

v2 的一轮 NE2000 按探测、收发、恢复推进，在同一实现会话中反复构建和检查。模型纠正了固件中断号与目标中断向量的区别，处理数据端口宽度、完成状态、环形缓冲区和奇数长度等问题，最终通过探测、实际收发与重复恢复的完整公开验收。

这比“先交付实现，再等待产物阶段才能触及设备”更直接。它也说明工作包、能力目标和持续修复并非 v3 才有。[依据 V2-B](PARTNER_VISIT_EVIDENCE.zh-CN.md#v2)

### 6.2 新问题一：压缩后的交接摘要可能丢掉决定性条件

v2 的 pvpanic 分析日志已经读到源驱动在锁获取失败时直接返回。交接摘要只写了状态由锁保护、通知串行执行；目标实现随之采用等待锁，串行事件与关机测试仍通过。测试通过没有覆盖被省略的竞争条件。

之后增加语义审查也不是稳定补救：一次审查读了源与目标，仍认为锁串行化得到支持；调整后的诊断才指出不等待条件被违反。这里确认的是源／目标的静态行为差异，尚无该 v2 候选的持锁动态复现。

启示是：分析不能只留下“用什么机制”，还需要保留“在什么条件下提供什么行为”，并直接交给承担这项行为的实施目标。末端审查可以补充，不能替代这条交接。[依据 V2-A、V2-C](PARTNER_VISIT_EVIDENCE.zh-CN.md#v2)

### 6.3 新问题二：连续会话可以连续重复错误解释

NE2000 的收发阶段，外部已经看到发送帧和返回帧，模型仍多轮判断“中断未送达”；其中两轮没有完成任何新的工具动作。经显式恢复并获得调试工具后，CPU 状态证明真实原因是中断回调等待被打断路径持有的锁。修正中断处理后收发推进，再修正逻辑帧长与传输填充长度，最终通过。

这轮最终成功值得保留，但不能写成无干预的一次自主成功。其教训是：**连续实现消除了部分交接，仍需取得能区分“未进入回调”和“进入后卡住”的证据。** v3 因此强调设计前提中的执行上下文，以及重复失败后的区分性观察；这属于指导机制，尚不能保证模型绝不重复诊断。

### 6.4 新问题三：分析更新与进度完成可能错位

后续 v2 已补充责任与进度管理。一轮 pvpanic 在实施中修订了责任正文并完成当前目标，但控制器把完成登记在旧依据上；更新后的同一目标被再次选中并要求检查。该轮随后还有独立的工具链下载失败，二者应分开解释。

v3 对此增加同一目标内的修订协调：实现依据变化但目标未变时，完成应对应修订后的依据；目标确实被替换时，不能借用旧目标的完成结果。[依据 V2-D](PARTNER_VISIT_EVIDENCE.zh-CN.md#v2)

## 7. v3：将源责任、目标前提与完整实施目标连成同一条链

v3 结合两轮经验：保留 v1 对证据与范围的要求，保留 v2 的连续实现，将分析、实施和修订使用的依据直接关联起来。

```mermaid
flowchart LR
    A[固定源版本、设备与功能范围] --> B[源行为责任与目标承担方联合分析]
    B --> C[核对会改变方案的关键前提]
    C --> D[完整工作包：实现、适配、检查与修复]
    D --> E[最终候选的完整设备验收]
    E --> F[交付代码、运行产物和证据]
    D -->|运行反证改变前提| C
    E -->|具体失败| D
```

### 7.1 条件不再只存在于调查记录中，而是直接约束实施目标

分析同时回答：源行为是什么；目标由谁保证；该保证依赖什么上下文；实施目标如何检查这项行为。实施接收相关分析的原文及来源，减少再次摘要时丢失条件的机会。控制器核对已声明责任是否有人接手、来源是否真实，模型仍负责语义理解。

**pvpanic 给出了完整的实际链条。** v3 分析明确保留“通知不能等待”，将通知、资源状态、清理和目标原生终止路径放进同一个实施目标。目标终止机制只接受首次注册，分析因此选择在现有终止动作之前插入通知，而不是另装一个可能不生效的终止处理器。

实现开始即采用非等待通知；在第一次构建之前，又检查到设备事件状态可能引入另一处等待，随即调整共享状态。随后原生 panic、关机和生命周期检查通过，后续五项内核测试也实际通过，其中包括持锁时抑制通知。源条件由分析进入实现，并得到针对该条件的执行证据。

这是对 v2 条件遗漏的具体回应。但两轮模型与功能范围不同，不能据此量化 v3 的整体质量提升或费用优势。[依据 V3-A](PARTNER_VISIT_EVIDENCE.zh-CN.md#v3)

### 7.2 前期优先解决“会改变方案”的前提，具体编码仍在实现中推进

v3 不要求提前调查平台的所有 API。优先核对的是会改变责任分配或接入方式的条件，例如硬中断是否被某种锁屏蔽、缓冲区是否允许 CPU 写入、框架是否真的会调用新的终止处理器。方法名、辅助类型和文件布局等选择可以在实现时解决。

**NE2000 的 v3 分析在实现之前明确识别：禁用软中断的外层网络锁不能阻止硬中断。** 实现据此分离硬件核心状态，并安排不会回头等待外层锁的中断路径。这回应了 v2 直到 CPU 调试才定位的上下文问题。日志证实该前提早于首次构建进入设计，尚不能证明所有类似驱动都会避免死锁。[依据 V3-B](PARTNER_VISIT_EVIDENCE.zh-CN.md#v3)

### 7.3 分析可能出错；新证据必须同时更新实现和后续依据

同一轮 NE2000 的初始分析仍误判了 CPU 写入接收缓冲区的权限。运行先暴露禁用中断时分配的问题，随后暴露 CPU 写入被拒绝。实现者移动分配位置、增加适合 CPU 填充的存储方式，再将平台前提修订为正确的权限与上下文要求。

控制器记录了该修订，将同一工作包绑定到新依据；它在当前实施回合完成，最终对同一候选重新运行探测、收发与恢复，三项通过，后续两组参数变种也通过。

因此，修复后的工作包同时拥有三个一致的结果：实现采用新的缓冲区与分配方案，分析解释这套方案为何满足前提，完成与验收记录对应修订后的实施。后续继续任务时，应读取这份修订，而不是沿用已经被运行推翻的初始结论。

**这个实例显示的优势是“错误能够被反证，并进入后续依据”，不是“初始分析不会错”。** Codex 同样修复过该缓冲区问题；v3 额外提供可追踪的前提更新与实施进度关联。原始分析文件还保留着旧判断，也说明只读一份报告会误判项目真实状态。[依据 V3-B](PARTNER_VISIT_EVIDENCE.zh-CN.md#v3)

### 7.4 一个工作包拥有完成能力所需的全部责任

工作包按完整能力管理，包含必要的目标框架适配、调用方接入、初始化、正常路径、错误处理和清理。内部可以多次阅读、修改、编译和运行；普通检查失败不是新的任务边界。

RNG 的真实计划将设备初始化、数据补充、完成通知、阻塞／非阻塞读取、调用方兼容和失败清理交给同一个包，并明确检查模块与初始化调用是否真正接入。这回应了 Codex 案例中“设备部分存在，完整读取链仍不成立”的问题。

NE2000 同样保持一个包，因为发送、接收、中断和恢复共同修改设备页、传输状态与环形缓冲区。把“锁”或“清理”单独拆包，会让依赖它们的目标在责任尚未完整时被宣布完成。已核对的 v3 RNG、Block、Network、NE2000 都只有一个包；不能用这些例子宣称多包拆分已产生收益。[依据 V3-C](PARTNER_VISIT_EVIDENCE.zh-CN.md#v3)

### 7.5 验收对应同一最终候选，知识保留适用条件

开发阶段可以复用已取得的观察；最终验收使用同一源码与产物运行完整公开套件，避免把不同修改时点的单项通过拼成最终成功。现有运行接口统一构建、启动与日志位置，有助于减少重新搭建观察通道的工作，但尚无单独消融结果量化这部分收益。

任务内分析直接服务实施。跨任务经验另保留源版本、目标条件与原始依据；新任务需要重新核对适用性。本轮对照关闭外部共享知识库，所以费用或质量观察不能归因于跨驱动知识积累。当前也默认不启用独立模型审查，不能把成绩归给“多模型审查”。

## 10. 面向 FSE，接下来要证明什么

论文中心假设是：**显式连接源行为、目标责任、设计前提与连续实施，能减少跨边界条件遗漏，并使修复保持一致。** 下一步需要将已观察到的机制实例转化为可重复的实验证据。

| 要检验的主张 | 下一步证据 |
| --- | --- |
| 比通用 Codex 更可靠 | 固定方法版本，多次配对运行，记录所有失败、中断和重跑；增加独立设计的留出场景。 |
| 收益来自提出的机制 | 在同样输入、工具与预算下，消融责任交接、关键前提分析、修订协调；运行工具和外部知识另做控制。 |
| 工作包划分合理、局部修订有效 | 人工抽样核对责任漏项和隐含依赖；纳入真正需要多个包的驱动，测量改动影响和重复工作。 |
| 保留了测试之外的重要条件 | 增加错误、并发、生命周期与协议边界检查，分别报告动态观察和源码论证。 |

已有反例提示这一步不可省略：早期 NVMe 的两种候选都通过较长读写，却在两页长度的追加测试中失败；核对发现均遗漏了源实现的一项地址映射分支。我们的分析机制同样可能漏掉条件，该反例尚未完成修复后的因果复验。[依据 Q1](PARTNER_VISIT_EVIDENCE.zh-CN.md#limits)

## 讨论准备

### 工作包怎么划分，为什么这样分？

先看完整能力需要共同维护的状态、接口、失败与清理责任。RNG 的数据补充和上层读取相互依赖；NE2000 的发送、接收、中断与恢复共用设备状态，因此真实 v3 计划都保留为一个包。多个入口或多个测试不自动意味着多个包。只有分别管理目标有实质帮助，且各目标有安全的中间状态，才适合拆分。

### 同一个驱动中的包肯定互相影响，改一个为何不重做所有包？

我们不假设无依赖。包可以共享责任与前提，也可以声明依赖；循环依赖合并执行。结论变化时，引用它的包及已声明的下游依赖会失去旧完成依据。未变化的进度可保留，但最终仍需完整回归。未声明的共享影响不会自动被发现，需要补查并扩大修复范围。当前真实案例主要是单包，还不能证明多包影响分析充分。

### 局部修订是不是把代码回退，然后假定其他部分不受影响？

不是自动代码回滚。它修订目标方案与前提、重新绑定实施依据并判断进度；实现者负责相应源码修改。源要求和验收判据不能在局部修订时被削弱；如果目标确实更换，就不能拿旧目标的完成结果充数。

### 引用检查、审查和测试能够保证正确吗？

引用检查保证来源与关系可核对；模型分析仍可能错误或漏项；设备测试只覆盖实际场景。现阶段默认没有独立模型审查。v3 NE2000 的初始权限判断和早期 NVMe 的边界遗漏都是提醒：需要检查反证和验证范围，而不能将报告齐全等同于正确。

### 相较 Codex，最值得汇报的贡献是什么？

从真实迁移困难出发，提出一套使行为责任在分析、适配、运行与修订中持续有效的方法。pvpanic 展示条件如何进入实现并接受针对性验证；NE2000 展示上下文前提如何影响方案、运行反证如何修订依据。工作包和知识库本身不足以成为贡献，还要用对照证明这套组织确实减少遗漏或重复工作。
