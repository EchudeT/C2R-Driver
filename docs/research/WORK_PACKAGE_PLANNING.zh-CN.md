# Factory 工作包：定义、划分过程、依赖与修订协调

本文用于科研汇报及 FSE 论文的方法部分，解释工作包是什么、如何划分，以及修订时如何确定影响范围。描述依据为 Factory 实验使用的代码版本 `3df3c9fbac899d8b43b7a62ecae42f1264843e46`，2026-10-10 核对。

本文是现有机制的展开说明，不新增阶段、模型调用、提交表格或实验规则。正文区分模型遵循的语义规划准则与控制器实际执行的结构检查，不将提示词要求视为已经得到程序证明的性质。

## 1. 工作包的定义与研究动机

工作包是具有完整实现目标和明确源行为责任的调度单元。它将同一目标所需的代码迁移、框架适配、状态与资源管理、错误处理、清理和局部检查组织在一起。一个包可以涉及多个源函数、目标文件、源契约和公开测试场景。

例如，RNG 的目标是实现并接入可工作的熵设备，包含注册、请求队列、DMA 缓冲区、完成通知、数据读取与补充、同步、失败处理及调用者连接。它不是一个孤立的读取函数，也不是将注册、初始化、通知和清理分别交给模型的任务列表。

设计针对两个具体问题：按函数或阶段机械切分会分散同一行为的生命周期责任；将全部前期研究重复交给每个执行者，又会增加上下文和交接负担。Factory 使用源义务、目标路径和关键前提描述完整目标，并保留按需查阅完整源码和知识库的能力。

### 1.1 四类分析对象

| 对象 | 含义 | 与工作包的关系 |
| --- | --- | --- |
| C：源契约 | 范围内、具有源码依据的行为义务 | 一个包可以承担多个 C；同一 C 也可被多个包引用 |
| R：目标粗路径 | 在目标内核中实现行为的接入方式和责任承担关系 | 一个包引用相关 R；R 内部步骤不会自动成为包 |
| P：关键前提 | 不同答案会改变实现策略或正确性结论的必要事实 | P 关联 R，引用该 R 的包获得相应前提 |
| B：行为条目 | 联合分析声明的完整实现目标及其依赖 | 无循环时通常直接成为执行工作包；循环依赖条目合并执行 |

论文中的“执行工作包”指控制器编译后的调度单元。需要讨论依赖合并时，应区分分析中的 B 条目与最终执行单元，避免把两者数量混用。

### 1.2 三个数量不能混淆

1. 源义务数量表示需要保持多少项要求。
2. 工作包数量表示有多少个完整实现目标。
3. 执行回合数量表示模型完成这些目标需要多少次交回。

一个包可以关联多项义务，并在同一会话中继续多个回合。`done` 表示当前选中包已实现，不等于驱动已经通过最终验收。

## 2. 从驱动输入到工作包的完整过程

过程为：冻结任务范围 → 提取源义务 → 建立目标粗路径 → 确认关键前提 → 组织完整目标 → 声明依赖 → 控制器检查并合并 → 生成执行工作包。

前面的分析操作在同一份联合分析中完成，不能理解为八个独立模型阶段。分析允许依据新发现回到相关结论，但没有要求每个操作交回控制器、重写报告或重新开展平台研究。

### 2.1 第一步：确定此次翻译的功能范围

**输入。** 操作者指定的驱动身份、固定版本完整 Linux 源码、目标内核、功能范围、环境配置和公开测试接口。

**操作。** 从源入口确认设备及调用边界，明确此次必须保持的行为与目标接入方式。驱动入口是源码检索起点，不是可读取内容的边界。

**标准和条件。**

1. 驱动身份明确：确认设备族、总线和源入口，避免混淆同名设备的不同实现。
2. 功能边界由操作者配置决定：默认 `source-driver` 包含所选驱动的外部可观察行为、被调用的共享驱动核心、控制路径、生命周期和错误路径，除非有明确排除。
3. `explicit-subset` 只要求声明的行为子集及其必要依赖；不能将默认模式中的空 `required` 列表解释为没有义务。
4. 接入方式明确：`target-kernel` 要求真实目标调用和插入路径；`callback-harness` 只允许声明的模拟调用边界，并仍遵守配置的设备执行要求。
5. 测试没有覆盖某行为，不构成排除该行为的授权。
6. 目标 API 缺失不构成排除理由：需要说明适配方式，或提出具体前提／范围问题。
7. 保持范围内行为，不要求复制 Linux 内部结构：目标平台可以采用不同的数据结构和执行机制，但需要说明行为责任如何保持。

**产物。** 在同一分析报告中说明功能边界、必须实现的结果、保留或适配的调用入口、排除项及其依据。没有独立范围报告。

**进入下一步的条件。** 明确迁移对象和功能边界。此时固定的是任务范围；具体源契约由后续分析形成，在联合分析被接受后成为实现阶段不能自行降低的要求。

### 2.2 第二步：从源码提取行为义务

**输入。** 已确定范围、源入口及可按需读取的完整源内核。

**操作。** 阅读相关代码，提取“什么条件下必须发生什么，或不能发生什么”。沿影响行为解释的调用和定义读取必要上下文，不建立每个函数一条义务的机械清单。

“存在完成回调”描述代码结构；“设备完成请求后，驱动必须发布完成结果，并遵守缓冲区访问条件”描述行为义务。后者才适合作为契约。

**标准和条件。**

1. 每项契约具有实际源代码依据，不能仅来自模型经验或通用安全检查表。
2. 明确触发条件和结果，例如调用、设备事件、资源获取失败或关闭，以及对应的数据、状态、返回或进展要求。
3. 保留有行为意义的提前返回、短读、拒绝、错误传播和失败清理，不能仅提取成功路径。
4. 调用者或共享核心决定行为时，读取相关上下文；不因一个相关调用扩展为全面内核阅读。
5. 一个义务可以跨多个函数：注册、提交、回调和释放可能共同建立同一保证。
6. 一个函数也可以承担多项义务：正常读取、非阻塞返回和错误处理可能需要分别说明。
7. 义务来源与验证能力分开：源码确定要求，测例或有界源码论证支持实现结论；公开 PASS 不能替代源义务分析。

**产物。** 报告中的 C 段落及索引中的源位置。每段说明源义务、重要目标适配及已有测试解释，或有界源码论证与验证限制。

**进入下一步的条件。** 有足够明确的源行为要求，可以据此选择目标承担方式。这里识别的是语义责任，尚不把每项 C 变成一个工作包。

### 2.3 第三步：建立目标粗路径

**输入。** 源义务、固定目标源码及已提供的框架和环境信息。

**操作。** 为范围内行为确定端到端接入方向：设备如何发现和注册，请求如何进入驱动，状态和资源由谁持有，事件如何返回调用者，失败与结束如何处理。

**标准和条件。**

1. 存在真实调用链路：不能停在无人调用的 Rust 模块，需要说明目标内核的设备发现、注册和上层调用路径。
2. 明确责任承担者：重要适配需要说明驱动、框架或双方分别保证什么。
3. 使用已提供的目标机制：保留总线、transport、queue、DMA、IRQ 等框架，在需要它们的目标内完成必要适配。
4. 以行为效果判断映射：同名 API、相似类型或锁守卫本身不能证明语义保持。
5. 包含必要生命周期：正常运行、初始化失败、资源存活和清理应形成完整路径。
6. 不预先解决全部局部细节：方法拼写、辅助类型、文件内部组织和普通构建编辑可以留到实现阶段。
7. 路径步骤不会自动成为工作包：注册、初始化、请求、完成、清理可以共同属于一个完整目标。

**产物。** 报告中的 R 段落，说明目标接入、责任分配、必要适配及条件。

**进入下一步的条件。** 有一个可以实施的粗路径，并能指出其中哪些未知事实会改变路径。

### 2.4 第四步：识别和解决关键前提

**输入。** 粗路径、未确定事实、原始定义以及可按需检索的知识材料。

**操作。** 将影响设计的未知与普通编码细节分开。优先查阅相关定义；有具体知识缺口时检索；只有必要事实确实需要执行观察时才探测。

例如，注销是否等待回调退出会影响资源释放策略；一个辅助方法的准确名称通常可以在编码时解决。

**标准和条件。**

1. 前提真假会改变接入策略、要求结果或正确性结论，才需要作为关键前提持久记录。
2. 问题具体：说明需要确定事实 X，以及成立和不成立分别导致什么后果。
3. 优先查看最近的原始定义或相关调用者，停止于能够回答该问题的证据，不开展全面平台调查。
4. 知识检索服务当前缺口；已有证据足够时不强制检索，也不预取整个目录。
5. 复用经验需要检查适用版本、条件及原始引用；历史结论不是当前正确性的证明。
6. 源码不足且事实需要观察时，采用能区分答案的最小探测，不设置固定探测数量。
7. 源码支持、运行支持和未解决假设分开；未运行、失败或未知不能写成成功观察。
8. 没有穷尽运行测试不自动阻塞；但直接决定行为成立的必要事实未知，需要解决或报告具体阻塞。

**产物。** P 段落中的事实、路径后果、证据和限制。执行探测时，由控制器保存收据，模型引用短 ID。可复用且已有依据的发现可通过现有知识机制沉淀，无需另写学习报告。

**进入下一步的条件。** 不存在未解决、且会改变要求结果或接入策略的关键前提。局部编码细节和未运行的计划测试不因此要求更多前置研究。

### 2.5 第五步：组织完整实现目标

**输入。** 源义务、目标路径、已支持的关键前提和公开测试接口。

**操作。** 模型提出 B 条目，将共同建立同一目标的责任组织在一起。优先保留内聚目标；只有较大或相对独立的工作需要单独管理时拆分。

**适合合并的条件。**

1. 多项内容共同建立同一个完整目标，例如注册、请求处理和完成通知共同使设备可用。
2. 共享紧密关联的状态、资源或生命周期责任，例如同一队列或缓冲区的建立、使用和清理。
3. 需要共同适配才能形成有意义的实现，只完成其中一个片段还不能形成目标路径。
4. 拆分仅沿函数、文件、API、契约或测试场景边界，没有独立完整目标的依据。
5. 工作仍适合在一个持续目标中管理；同一包内允许多次源码查询、编辑、编译、检查和修复。

**适合拆分的条件。**

1. 存在不同的完整目标，每个目标都可以描述要求结果，而不是列出几项辅助函数。
2. 目标确实较大或相对独立，分别管理有实际帮助；一条路径可以单独观察，本身不足以拆分。
3. 各目标仍包含其必要生命周期和清理，不能把初始化、锁或清理机械分成独立交接任务。
4. 跨目标前置关系能够解释；存在依赖时说明需要前一目标提供什么能力或决定。

这些是当前提示词中的语义规划准则，不是新增的四项逐项提交门槛。当前没有按代码行数、函数数量或 token 阈值执行最优分区算法，也没有要求固定工作包数量。实现存在保护性的调度上限，但该上限不是驱动划分策略。

**B 段落需要表达的内容。**

1. 完成什么行为或能力。
2. 接入哪条目标路径。
3. 承担哪些源义务。
4. 包含哪些必要适配、错误处理、清理和局部检查。

**产物。** 报告中的 B 目标说明及对应引用。没有额外拆包论证表，也没有每个源函数一个报告。

### 2.6 第六步：声明包间依赖和共享依据

**输入。** B 条目、目标机制、源义务和关键前提。

**操作。** 模型判断一个目标是否需要另一个目标提供的能力或决定，并通过 `depends_on` 记录前置关系。单包驱动的内部步骤在包内处理，不建立跨包关系。

**声明前置依赖的条件。**

1. 存在具体前置能力，例如请求处理依赖另一个包提供的队列接口。
2. 存在具体状态或资源约定，例如完成处理依赖前一包确定的缓冲区所有权规则。
3. 前置目标的决定变化会使后继目标需要核对，能够说明实际影响。
4. 依赖来自行为成立的前置关系，不能只因为习惯上先写某段代码就添加依赖。
5. 共同编辑文件不自动构成依赖，代码组织与行为前置关系不同。
6. 共同调用稳定框架接口不自动构成依赖，两个目标可以分别使用现有机制。

**共享依据的表达。**

1. B 直接引用相关 R 和 C。
2. P 关联 R，因此引用同一路径的 B 获得相关 P。
3. 多个 B 可共享路径、契约和前提，不复制多份解释。
4. 共享依据的修订可影响多个 B，即使它们没有直接函数调用或 `depends_on` 边。

**产物。** `depends_on` 前置关系，以及 B—R、B—C、P—R 引用。依赖发现是模型的语义判断；控制器不会从任意代码编辑自动推导完整影响图。

### 2.7 第七步：控制器检查并编译计划

**输入。** 一份 `report.md` 和同名 `report.route.json`。Markdown 保存语义解释，JSON 保存 ID、段落定位、源码位置和关系。

**操作。** 控制器检查引用和证据，接受联合分析，并将依赖中的强连通分量合并为执行单元。

**实际程序检查。**

1. ID、段落定位及引用有效，所引用的对象必须存在。
2. 每个 B 关联目标路径，正式进入实现时也需要关联源契约。
3. 每项已声明 C 都有至少一个 B 引用，不允许出现没有实现目标承担的契约。
4. 源契约包含源仓库引用；引用路径和行号能够解析到实际源码。
5. 关键前提有支持依据；准备完成的分析不能保留 `open` 的设计关键前提。
6. 探测引用满足已有收据检查，不能将失败或不适用的观察伪装为支持。
7. 前置 B 必须存在，列表和关系满足索引规则。
8. 相互依赖的 B 合并执行，避免形成无法按前置顺序推进的循环。

例如，声明 B1 依赖 B2、B2 依赖 B1、B3 依赖 B2，则最终执行单元为 `{B1, B2}` 与 `{B3}`，后者依赖前者。当前实现通过图上的相互可达关系识别强连通分量，并重建分量间依赖。

程序检查证明结构一致、引用可解析和声明责任有承接目标，不证明模型已经发现全部源义务，也不证明正文中的语义映射正确。可检测的提交错误在同轮修正，不要求重启平台分析。

**产物。** 已接受的分析绑定、执行工作包及依赖图。结构检查成功不是驱动验收通过。

### 2.8 第八步：生成当前执行工作包

**输入。** 已接受的计划、完成状态和当前活动目标。

**操作。** 控制器直接选择可执行单元，生成当前目标及其关联上下文；不增加第二次实现规划任务。

**调度和交付条件。**

1. 前置单元完成后才允许选择后继单元。
2. 当前活动单元仍可执行时优先保持；否则选择计划顺序中的第一个可执行单元。
3. 工作包提供当前目标所关联的 R、C 和 P 正文，减少无关分析内容的重复交接。
4. 完整源码、原始报告及知识检索仍可按需读取；工作包不是源码阅读白名单。
5. 当前目标内允许连续查阅、编码、构建、检查和修复，不要求内部步骤逐个交回。
6. `continue` 保持当前目标及已有代码，后续回合使用持续会话。
7. 一次 `done` 最多完成当前选中的一个执行单元，不能越过调度边界完成多个独立目标。
8. 工作包进度与验收分开；最终控制器在同一个最终候选上运行完整公开套件。实验私有评分不反馈给实现模型返修。

**产物。** 当前执行目标、关联分析上下文及控制器记录的进度。最后工作包完成后进入已有交付和验收流程，不新开一轮撰写工作包报告。

## 3. 包间影响关系与局部修订

### 3.1 关系的来源

包间影响由两部分表达：模型根据源码和目标定义声明前置依赖；分析引用表示各包共享的路径、契约和关键前提。控制器处理这些声明，不能声称获得了完整静态代码影响分析。

| 关系 | 意义 | 修订后的作用 |
| --- | --- | --- |
| B → 前置 B | 后继目标依赖前置目标提供的能力或决定 | 前置进度标识变化向依赖者传播 |
| B → R | 目标采用某条接入路径 | 路径正文变化影响引用该路径的目标 |
| B → C | 目标承担某项源义务 | 建立责任关联；本地路径修订不能改变冻结 C 正文 |
| P → R | 前提支持某条接入路径 | 前提结论变化影响关联路径的目标 |

同一 C 被多个 B 引用只表示共同承担该义务，不自动建立它们之间的先后依赖。共同引用同一路径的影响范围也可能较宽，因此论文应描述实际的引用粒度，不能声称控制器总能得到最小语义影响集合。

### 3.2 进度标识的计算

控制器对每个执行单元计算标识。概念上：

```text
basis(B) = digest(关联路径正文、契约正文、关键前提结论及其相关字段)
key(W) = digest(W 中的行为定义、各 B 的 basis、前置 W 的 key)
```

行为定义包括目标正文、契约关联和依赖等。前置标识递归进入后继标识，因此前置依据改变时，后继不能直接继承旧的完成标识。哈希用于识别内容及关系变化，不判断自然语言语义是否等价。

`bases()` 不将新增契约源码引用或前提探测收据本身纳入设计依据；相关正文不变时，这些证据元数据补充不单独导致实现进度失效。正文改写即使只是措辞变化，也可能改变标识；当前没有语义等价判定器。

### 3.3 修订后的处理规则

1. 普通代码修改不自动触发计划修订；已引用目标文件变动也不单独触发工作包重新调度。
2. 只有具体路径、前提或目标需要纠正时，执行者显式提交分析修订。
3. 控制器检查修订并重新计算包标识；未受影响的完成状态保留，受影响的包重新成为待处理目标。
4. 保留全部实现代码，重新处理不等于删除代码或从头翻译；可以检查现有实现并只解决实际影响。
5. 当前行为定义和前置关系不变、且仍是当前选中目标时，路径／前提修正可以在原回合完成，控制器更新本回合选择标识。
6. 目标或边界改变时，原回合不能凭旧选择直接完成一个不同目标，需要按更新计划选择。
7. 本地路径修订不能修改冻结源契约正文或删除原源义务引用；不能通过修订路径降低要求。
8. 最终验收独立于工作包完成标识。程序不以计划闭合、引用检查或模型 `done` 替代测试结果。

这里的“重新处理”是计划进度协调，不是对每次代码编辑强制重跑测试。开发检查保留已有观察；最终完整公开验收由既有控制器逻辑执行。

## 4. 已有实验中的具体例子

下表核对的是 DeepSeek V4 Pro/high 已运行分析文件中的声明，不是对全部历史实验的统计。

| 驱动 | 联合分析中的 B 数量 | 关联源契约数量 | 组织方式 |
| --- | --- | --- | --- |
| VirtIO RNG | 1 | 7 | 熵设备实现、请求与完成、调用者接入及生命周期共同完成 |
| VirtIO Block | 1 | 6 | 协议、队列、请求处理、注册与相关清理共同完成 |
| VirtIO Network | 1 | 5 | RX/TX、设备注册、网络接口连接及相关清理共同完成 |

RNG 来自批次 `deepseek-v4-pro-high-20261009-rng-01`；Block 和 Network 来自 `deepseek-v4-pro-high-20261009-remaining-01`。分析位于各 Factory trial 的 `run/work/stage-work/target_platform_study/report.md` 及 `.route.json`。这些批次标识用于证据定位，不是新机器的使用入口。

### 4.1 RNG 的八步对应

| 步骤 | 实际目标或材料 |
| --- | --- |
| 确定范围 | 恢复真实 VirtIO 熵设备与保留的 `/dev/hwrng` 调用路径 |
| 提取源义务 | 设备发布、队列与完成、读取与控制行为、失败及清理等 C1—C7 |
| 建立粗路径 | 在现有 VirtIO 框架中新增熵设备，连接 transport、queue 与调用者 |
| 确认前提 | 在报告中支持关键接口和路径事实，记录证据及限制 |
| 组织目标 | 注册、请求、完成、读取、补充、同步和清理共同构成 B1 |
| 声明关系 | B1 引用 R1 和 C1—C7，没有第二个 B，因此无跨包依赖 |
| 编译计划 | 检查引用、源码依据和前提，生成单一执行单元 |
| 连续实现 | 在该目标内完成代码、适配与检查，随后进入独立最终验收 |

该例支持“一个完整目标承载多项源义务，并避免机械拆分”的方法描述。它不支持复杂多包依赖协调的效果结论。多包合并与修订传播是现有实现能力，相关离线测试是控制器机制证据，不能写成真实驱动实验的收益。

## 5. FSE 论文的解释与主张范围

### 5.1 为什么划分不是任意任务清单

1. 范围来自操作者输入，不能因测试或成本自行缩小。
2. 目标关联源义务与源码位置，不仅是模型生成的待办事项。
3. 路径和关键前提解释目标为何可实施，以及谁承担行为责任。
4. 共同建立一个目标的生命周期内容优先保留，避免按函数和步骤机械拆分。
5. 依赖编译、选择和进度协调由程序执行，模型不能仅靠对话声明跳过当前目标。

划分是受规则约束的模型规划决策，不是唯一或全局最优分区。同一输入重复运行可能产生不同的合法计划；报告、索引和事件保留实际决策，固定提示词、模型配置和输入用于复现实验协议，不能声称重复运行必然得到同一划分。

### 5.2 与通用 agent 的具体区别

通用 agent 同样可以自主规划、读取源码、实现和测试。Factory 的区别应限定到已实现的约束和表示：一份联合分析把源义务、目标责任、前提和实现目标关联起来；控制器据此选择完整目标、保持继续状态、处理显式修订，并将进度与最终验收分开。知识检索提供有条件和来源的信息复用，而不是把历史成功当作当前验收。

不能仅以存在任务分解或 reviewer 作为创新，也不能仅凭架构说明宣称比通用 agent 更优。当前对照实验可用于报告整个系统的质量和成本；没有对应消融时，不能把整体差异单独归因于工作包划分。

### 5.3 可直接用于方法部分的英文表述

> Factory employs obligation-guided, coarse-grained work-package planning. During joint analysis, the model derives behavioral obligations from the pinned source and its relevant kernel context, identifies target integration routes and design-changing premises, and groups related responsibilities into complete implementation objectives. Lifecycle, synchronization, failure handling, and cleanup remain within the objectives that require them. Packages are split only when separate goals help manage substantial or relatively independent work. The model declares prerequisite dependencies; the controller validates references, merges strongly connected components, and schedules eligible execution units. Route revisions reconcile progress through package-local bases and recursive prerequisite identities while preserving implementation code. Package completion records implementation progress rather than acceptance, which is determined separately by the final public suite.

### 5.4 证据边界

1. 契约均有关联目标，只证明已声明集合的结构承接，不证明全部源语义覆盖。
2. 源引用、探测收据和知识来源证明可追溯性，不自动证明模型解释正确。
3. 依赖来自显式声明和共享分析依据，不是完整静态影响图。
4. 哈希追踪分析内容变化，不具备自然语言语义等价判断能力。
5. 单包案例可以说明粒度选择，不能测得多包协调收益。
6. 公开测试通过支持已观察场景，不证明完整语义等价；私有测试成绩按实际协议单独报告。

这些边界限定论文主张，不要求修改现有实验或重新运行已有数据。
