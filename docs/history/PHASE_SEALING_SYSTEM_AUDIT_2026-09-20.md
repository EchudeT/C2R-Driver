# 阶段封闭、修复与重启：系统调查

日期：2026-09-20。范围：当前公开迁移流程，不含盲测实现。此次只读调查程序及实际运行记录，
仅新增本文；未修改代码、测试、运行状态、工作者报告，也未向工作者发送消息。
调查时 audit-01 控制器 ACTIVE，实现修复 RUNNING。运行会继续产生新记录，以下为调查快照。

## 结论

当前程序没有“阶段封闭”的实现。现有290项测试通过，不证明该要求成立。
问题不是允许倒退的步数太多，而是任务、阶段、证据版本、修复工单共用节点状态，
使一份 REWORK 报告直接获得重开任意前置节点的能力。

最近的 composite repair 是减少模型交接的优化，不是阶段封闭；不能再把它描述成已经解决
跨阶段回退。只限制退一步也不足以解决：连续退一步仍能越过所有边界。

Skill 的 workflow 引言允许回到最小受影响证据门，第9节要求归因、局部修复和受影响回归。
Skill 没有要求每个证据门都是独立模型任务，也没有要求自动重开任意历史阶段。
用户新增的“完成阶段不准自动重开”是更严格的调度要求：跨封闭阶段问题必须升级决策，
不能忽略缺陷强行通过，也不能以 Skill 的修复原则为自动跨阶段回退授权。

## 调查方法与实际证据

- 枚举全部 `retry_from`、`retry_prerequisite`、`PrerequisiteRepair`、`ImplementationChanged`
  调用及 `DPF_REPAIR_STAGE` 提示来源。
- 阅读状态持久化、依赖传播、当前任务调度、报告验收、准备收据、QEMU复用、审查策略、
  状态统计和对应集成测试。读取本地迁移 Skill 及 workflow 全文。
- 从当前 workflow 构造可回退目标矩阵；只读查询 audit-01 账本，未试触发真实回退。
- 本轮未重新执行付费模型或全量测试，也未重新审计历史每条模型消息。
  “代码可达风险”不等于“实际已经发生”；本文明确区分两者。

## 问题清单

### A01 / P1：缺少阶段身份和封闭状态

证据：`core/models.py:110` StageSpec只有节点依赖/产物/角色；StageStatus没有阶段封闭；
`orchestration/migration.py`仍构造19个检查点。没有 phase_id、封闭版本或重开授权记录。
因此“过了阶段就不能退回”目前无法在程序底层表达。应先定义阶段，再实现单调推进和封闭。

### A02 / P1：底层重试API授权范围过大

证据：`core/store.py:186`只检查目标PASS、触发者RUNNING、位置更早、角色和依赖关系；
不检查同阶段、最大范围或用户重开许可。`codex/cli.py`由全部已通过祖先生成 repair_targets，
`port.py:317`接到合法标记立即执行回退。提示收窄不能阻止其他调用绕过；必须在持久化API守住。

### A03 / P1：失效、调度和任务重新开放绑在一起

证据：`core/store.py`把根及全部后代重置READY/PENDING，推进artifact_boundaries；
`port.py:200`选择最早可执行节点。结果是更新旧证据必须回到旧节点执行，无法表达
“当前交付阶段内产生新版代码/镜像/测试证据”。应分离阶段状态和证据有效性。

### A04 / P1：多个自动入口可绕开未来的提示级限制

证据：`port.py`通用REWORK入口，以及打包、QEMU、自检/审查前的ImplementationChanged处理，
都调用retry_prerequisite；升级工具另有直接retry_from。只修改审查路由会漏掉漂移入口。
升级是显式维护操作，应与工作流自动重开区分，不宜为了兼容维护而放宽运行协议。

### A05 / P1：审查意见直接改变执行状态，核实发生太晚

证据：`_materialize_codex_report`调用`_report_outcome`，审查REWORK即抛出路由异常；
通用门随后失效旧节点。工作者核实反馈范围/反证的要求放在回退后的OBJECTIVE中。
因此即使意见被反证或超范围，也已经产生失效、交接和潜在重建。
应先在当前阶段分派反馈处理，不把“审查者提出问题”等同“已批准重开历史阶段”。

### A06 / P1：封闭阶段重开没有结构化授权

证据：`wait_for_user/resume_after_user`只有问题/任意answer和角色，不绑定重开阶段、输入版本、
影响范围；当前REWORK也不调用它。用户确认必须绑定具体重开请求，不能用普通续跑回答授权。
当前已有继续运行授权不能解释为允许未来任意跨封闭阶段回退。

### A07 / P1：复合修复准备不是原子提交，存在中断窗口

证据：`port.py:749`先snapshot_worktree（含PASS提交），再record(REPAIR_PREPARED)；
打包同样先capture PASS再record。若二者之间中断，恢复后根节点已PASS而准备收据不存在，
优化路径丢失，调度回普通打包/运行准备模型轮次。
这是代码可达风险，本轮未注入崩溃复现。应原子登记或由已提交产物确定性恢复准备状态。

### A08 / P2：准备收据过于整体化，局部变化退化为普通任务

证据：`repair_execution.identity/prepared`把源码、镜像、检查器、脚本、helpers、报告绑成一个
整体，任何差异返回None；调用者不能区分“从未准备”和“只有脚本变了”。
应分开实现、打包、运行证据身份，并返回具体失效原因，保留其余有效准备。

### A09 / P2：准备收据不绑定完整语义前提

证据：identity只有文件和脚本；无契约、测试计划、工具/环境版本、修复请求ID。
prepared通过后续implementation/artifact RETRIED间接排除旧前提。现有图中许多上游修复会
传播这两个事件，因此不能断言已存在实际陈旧接受；但身份正确性依赖传播副作用，无法支撑
将来“阶段封闭、证据局部更新”的架构。需显式绑定真正前提。

### A10 / P2：存在两条修复交付协议，CLI入口不完全一致

证据：修复OBJECTIVE在port._implementation/_artifact_preparation传入；
codex.cli独立依据active注入repair_execution，但直接`codex run`默认objective仍取manifest。
protocol.describe的completion也仍按普通节点生成。该组合可能同时告知“完整准备”和“仅完成
当前节点”。应由同一任务描述生成目标、可用操作、完成条件，所有入口统一。

### A11 / P2：准备失败的恢复协议仍依赖调用栈

证据：静态capture失败后，`preparation_error`只存在局部变量，composite布尔经lambda传到
验收；根节点此时已PASS，gateway的active未必提供repair_execution元数据。
准备检查错误有attempt证据，但“当前执行哪类修复任务”不是持久状态。应把恢复状态记录为
同一修复事务的一部分，而非通过异常入口临时拼装。

### A12 / P2：反馈解决状态只是根节点PASS，不是问题闭环

证据：`core/store.py:164`在失效事件之后找到根PASS且当前仍PASS即返回RESOLVED。
此时镜像/运行/审查可能尚未通过。当前文案多处正确称“prerequisite repaired”，但统一字段
RESOLVED容易被理解为整个问题解决。应区分修复提交、证据复验、审查关闭；别再增加模糊布尔。

### A13 / P2：重试限制不是阶段或问题预算

证据：retry_from仅限制相同target/trigger/progress指纹3次；文件或路由变化即新指纹。
`_codex_gate`纠错3次/操作续接2次是进程局部变量，重启重置。没有修复工单累计调用、耗时、
费用或进展记录。会同时出现“有实际进展却因两次操作上限暂停”和“跨路由反复消耗不触发限制”。
不应简单降低阈值；应对同一问题/阶段持续记录进展与停止原因。

### A14 / P2：审查触发粒度与差量复审粒度不一致

证据：review_policy每次对冻结upstream作全量改动分析；rust_risk按名称近似依赖，明确允许
同名过度关联。reusable_review要求整份输入和decision相同，并只复用PASS意见；REWORK中已
关闭问题没有机器记录。新增previous_review有助于模型延续，但不等于差量审查协议。
实际351号报告明确把若干内核unsafe依赖列为扫描误报，同时提出F1/F2具体时序风险及F3克隆
行为问题。不能据误报否定全部审查，也不能据报告口吻认定F3在冻结范围内。
应对上次审查版本提供改动差异、未闭合意见和可核实反证；审查失败不直接控制阶段重开。

### A15 / P2：范围传递间接，缺少“范围争议”出口

证据：handoff保存migration_envelope的upstream引用，非直接展开设备子集；审查新增handoff
输入但没有强制把每项问题关联到当前范围。路由只有PASS、REWORK、BLOCKED，没有独立的
范围争议/需授权决策语义。应程序提供简短冻结范围及原件路径；用自然文档阐明争议，不新增
模型填表。F3是否必须修复属于待核验事实，本文不替工作者/用户扩展支持范围。

### A16 / P2：复用键包含报告字节，可能造成非功能性重跑

证据：PublicQemuService.run_script的PASS缓存条件包含request_report.sha256和全部inputs，
review_inputs也包含整个runtime和helper身份。注释/报告变化可能改变键，当前没有按物质性
变化分类。必须保留测试计划/阈值/oracle变化使结果失效，不能简单忽略所有报告；需要将
真正执行前提与叙述分开。此项为代码设计风险，不声称本轮发生了报告修改导致的重跑。

### A17 / P2：用户看到的耗时、尝试与任务数量混在一起

证据：statistics.stage_times在controller停止但stage RUNNING时仍累计时间；CLI展示累计
attempt，静态刷新也会增加attempt。已有脚注明示，但主界面不能区分当前操作、历史返工和
人工暂停。新增repair行仍不能显示封闭阶段或本次修复剩余工作。
应展示阶段、局部操作、实际活动耗时、累计返工及原因，不能仅靠解释“不是又回退”。

### A18 / P1（验证缺口）：测试仍在证明旧状态模型

证据：test_task_protocol主动允许实现→目标研究、源码→证据；test_repair_execution从
18→15的retry_from开始；相关集成测试证明产物检查和调用数，却没有封闭阶段不变量。
另外缺少A07事务中断窗口、跨阶段明确授权与拒绝后状态不变、相邻多次退回越界、
审查反馈被反证无需失效、只改脚本不丢打包准备、直接CLI/Port提示一致等场景。
增加字符串快照无助于补齐；需要少量真实状态迁移测试和故障注入。

## 各段应如何划分（建议，尚未实现）

| 建议封闭阶段 | 现有检查点 | 阶段内修复 | 进入下一阶段后 |
| --- | --- | --- | --- |
| 范围与基线 | 1–7 | 身份确认、固定版本及获取 | 范围/基线改变需明确重开许可 |
| 证据与设计 | 8–14 | 环境、目标研究、源码事实、契约相互补全 | 新材料可追加；推翻冻结设计须升级，不回旧节点 |
| 实现与交付验证 | 15–18 | 代码、打包、测试、反馈处理在同一工作上下文迭代 | 验收后封闭；新变更作为新任务/版本 |
| 交付审计 | 19 | 机械收集、验证身份和完成条件 | 发现缺口停止交付，不静默重开前阶段 |

这不意味着研究阶段可以随意推翻用户范围，也不意味着交付阶段必然追加独立审查。
若仍保留子节点，“最多回相邻节点”必须叠加所属阶段边界；更合理的是修复作为阶段内操作，
子节点只是证据检查点，不再调度反向遍历。环境工具故障在交付阶段可以局部恢复，只要不改
冻结的环境/平台结论；改变结论才需要跨阶段升级。

## 实施顺序和验收条件

1. 先定义阶段/封闭版本/跨阶段请求语义，在持久化层禁止无授权重开；不先改UI或提示。
2. 分离修复任务与证据有效性，封闭阶段保持历史PASS；当前交付版本使用新版有效证据。
   CAS/账本保留，禁止手工把旧测试标为适用于新代码。
3. 统一所有模型和异常入口，删除可自动跨阶段的旧路由；提示从同一协议生成。
4. 准备/提交/执行/自检/反馈处理形成可恢复事务；按实际受影响对象复验，不要求全套重做。
5. 封闭阶段遇到根本错误，展示原因、影响和具体重开版本；没有明确授权保持暂停。
6. 验证：18无法自动回8/11/13/14；阶段内实现修复不重新调度研究；相邻回退链不能越界；
   所有入口都遵守边界；每个提交间中断可恢复；脚本改动不要求无关重建；未解决真实问题不能PASS。
7. 升级现有运行时只导入已验证有效证据并记录版本迁移，不伪造阶段完成或删除旧失败。

## 本轮不作的结论

没有证据支持“审查必须取消”或“全部审查意见都必须修”；没有证据支持当前运行已结束。
没有重新复现每个中断风险，不能声称已经证明无遗漏。以上是此次覆盖范围内的完整问题清单，
不是无缺陷保证。下一轮应按此状态模型整体实现，而非再往OBJECTIVE追加事故提示。
