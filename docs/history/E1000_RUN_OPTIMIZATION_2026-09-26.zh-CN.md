## 关键发现：配置的交接没有发生

框架调用 `aabd586f-7e89-4c57-b4bb-520b91f56dc9` 的实际策略决策是
`preserve / continuation_preserved`，线程仍为分析 worker。全运行只有两个 fresh
会话（worker、reviewer）和 23 次 resume，没有 handoff 或 session_reset。

根因：分析审查曾要求重做契约，控制器给下游留下 retry 状态。契约修复完成后，
框架首次启动时 `retry_feedback` 已是 `RESOLVED`，但 worker 入口把任何非空
retry 对象都当作正在续修，从而跳过一次性交接。提示本身正确注明已解决，只有
会话决策错误。修复改为仅未解决的 retry 阻止交接；显式续接、checker 反馈、
已有执行记录和已消费交接的保护保留。

集成回归覆盖真实控制器的“分析审查退回契约/目标研究 → 修复 → 复查 → 首次框架”
路径，分别验证 analysis-handoff 获得新线程及事实交接，persistent 继续原线程。
现有中断、重启、正在修复和只交接一次的测试继续运行。

**这次不能作为 analysis-handoff 已生效的成功样本，更不能证明清空历史更便宜。**
每个线程只取最后保留快照去重，worker 有 9 个原生 compacted 记录、reviewer 有
2 个；25 份清单全部存在，快照完整性检查通过。原生快照不是服务端请求抓包。

## 可避免的流程返工

evidence_closure 六次调用中有五次 recovery，依次涉及：facet 名称含空白、HTTP
403、镜像字节摘要不一致、不同 URL 实为同一发布者、把目录当作文件提交。前者和
最后一项暴露出提交提示不明确：原文只称 facet 为 descriptive name，未说明不许
空白；未明确 repository_paths 是文件。

已修改提交协议，直接说明 token 命名、文件路径、独立发布者和逐字节一致的镜像
要求。没有新增校验、自动接受不一致文档、全目录抓取、额外模型预检，也没有修改
合法证据的接受条件。403 等外部故障不可能靠提示保证消除；保留显式 gap 路径。

环境 smoke 的一次 recovery 来自未观测到 QEMU。最终审查也记录过容器检查竞争，
但当九个有效容器进程与 runtime binding 都成立时没有据此退回。因此尚无充分依据
进一步收紧或放松 collector；先保留原始证据，后续按具体复现处理。

## 轮询与可复用审计

worker 原生记录有 710 次外层 exec 和 4 次 wait；reviewer 有 65 次 exec。
worker 有 82 次精确重复外层调用。重复最多的几组是 write_stdin 轮询，其中有
1 秒请求间隔；也存在代码改变后合理重跑同一 smoke 命令。不能把这 82 次全部
算作浪费，更不能将快照中的累计 tokens 再求和。

执行指引建议健康长任务使用 10–30 秒等待、保留句柄及有界日志尾部；交互或故障
诊断允许短等待。不自动 sleep，不重启运行中的命令，不强制批处理依赖操作。

新增通用离线工具（不调用模型、不导出原始提示和工具参数）：

```sh
PYTHONPATH=src .venv/bin/python scripts/run-log-audit.py RUN > audit.json
```

它读取调用增量、按线程选最后保留快照并校验块/整体摘要，统计实际会话决策、
压缩标记、外层工具次数和精确重复，报告缺失/损坏日志；不把这些指标变成门禁。
嵌套 exec 内部工具没有逐个解析，重复不等于无效，统计不证明因果收益。
