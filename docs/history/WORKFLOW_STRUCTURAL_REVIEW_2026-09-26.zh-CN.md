# 对照 Skill 的工作流结构审阅与交付任务合并

日期：2026-09-26。范围：通用 C 驱动迁移，不是 E1000 特例。工作分支：`feat/e1000-run-log-optimization`。

本轮没有启动真实模型迁移，没有重跑 E1000。以下区分历史观测、代码确认、合成回归与尚待实验的假设。历史对照详见 [Skill 成本调查](SKILL_VS_FACTORY_COST_2026-09-26.zh-CN.md) 和 [对话审计](E1000_DIALOGUE_AUDIT_2026-09-26.zh-CN.md)。

## 1. 为什么这次要改任务结构

先前主要优化材料检索、输出长度、轮询和上下文交接。这些有价值，但不能解释或消除约两倍的费用差距。历史成功工程运行的主要消耗在实现及其修复，应该优先减少重复设计、跨阶段返工和过晚发现测试义务缺失。

| 观测 | 工程历史成功运行 | 原生 Skill 历史区间 |
| --- | --- | --- |
| 模型配置 | Sol medium | Sol high |
| 模型费用口径 | token 估算 $93.68 | 简化同费率估算约 $36.94；用户记忆账单约 $40 |
| 工具调用 | 779 | 434 |
| 工具输出字符 | 约 541 万 | 约 248 万 |
| worker / reviewer 压缩 | 9 / 2 | 原生会话 4 次 |
| 质量范围 | polling / 原始 Ethernet 等 | 还包含 IRQ、DNS、ring wrap、2 CPU、NE2K 共存等，报告记载 22 次运行 |

这些不是受控 A/B：源/目标版本、既有环境、缓存、推理强度不同，Skill 复用了早前 NE2K 的部分准备。不能把差额归因于单一机制，也不能将 Skill 便宜解释成验证更弱。估算不等于账单，原生会话 cache-write 口径存在不确定性。

工程运行中框架适配约 $11.52，驱动实现约 $45.95，合计约 61%。其中两次实现修复约 $32.43：一次补冻结矩阵要求的入口，一次修复独立审查发现的真实语义/oracle 问题。必要修复不能删除；应把相关义务提前带入一个连贯的交付任务。

## 2. 与 Skill 的结构差别

| 工作环节 | Skill 链路的可取点 | 原工程的额外负担 | 本轮处理 |
| --- | --- | --- | --- |
| 框架、驱动、注册与公共测试 | 同一个实现任务连续修改相关代码 | 多个任务重新说明范围、约束和当前状态 | 首个交付任务覆盖框架、驱动、集成、测试入口与打包准备 |
| 共用集成文件 | 围绕功能修改 | 框架和驱动按整文件划分冻结归属 | 过程快照保留，最终交付快照覆盖所有变更源码 |
| 打包和测试准备 | 实现期间准备 | 后续任务重新理解产物/测试关系 | 完整准备时机械捕获、执行；缺失才进入补充任务 |
| 修复 | 同一负责人处理相关改动 | 接口与驱动问题可能在阶段间转交 | 源码类修复统一交给实现任务，包含框架和集成 |
| 检查 | 围绕行为和可运行结果 | 风险在于把格式/归属误判为缺陷 | 本轮没有增加报告格式或启发式阻断门槛 |
| 可追溯性 | 报告与工具记录 | 工程有更强的独立证据账本 | 保留账本、独立审查、源码及运行证据绑定 |

旧代码确实强制过整文件归属；但尚未证明它造成了历史 E1000 的某笔费用。去除它是消除已确认的结构限制，不应虚构历史因果。

## 3. 已落地：一个交付任务，多个证据检查点

保留现有阶段账本标识，改变默认模型任务分配：

```text
冻结分析与独立分析审查
        ↓
交付任务：框架 + Rust 驱动 + 共享集成 + 测试入口 + 产物准备
        ↓
控制器记录过程检查点
        ↓
控制器执行实现 smoke，冻结全部变更源码
        ↓
控制器捕获产物、执行 presence 检查和公共测试
        ↓
worker 核对实际执行证据
        ↓
独立最终审查 → 有实质缺陷才定向修复
```

`target_framework_enablement` 现在是交付任务入口，其名称仍是账本标识，不再表示模型只能修改框架。默认提示、协议、执行规则和审查路由同步调整。该阶段保留为真实过程检查点，没有用空快照冒充完成。

具体实现：

- `port.py`：首个交付任务完成后记录完整准备回执；实现节点可以直接执行正常快照及 smoke，无须再调用模型重新规划。
- `repair_execution.py`：回执绑定源码、runtime、presence checker、smoke 脚本、公共脚本、helpers，以及当前 handoff、contracts、test matrix 和交付检查点。检查点、实现或打包重试后失效。
- `implementation.py`：schema 2 的最终实现快照包含**全部**相对冻结 upstream 的变更，包括原有框架路径、新增路径、删除与 executable 状态。旧的路径排除机制移除。
- `target_framework.py`：schema 2 明确标记为 `delivery-checkpoint`；修复时不再禁止修改旧 driver 路径。
- `artifact_preparation.py`：检查完整实现快照，而不是要求当前文件仍等于更早的框架检查点。旧快照仍是不可变历史证据，不会被改写。
- 默认协议删除 NE2000 的固定设备身份示例，要求从当前项目的冻结证据获取身份和环境，避免把通用要求变成某个设备的模板。

“准备完整”只是允许控制器尝试验证，不意味着 PASS。缺文件不会引入新的拒绝门槛，会走已有补充实现/准备路径。公共测试后的 worker 核对和独立最终审查仍保留；没有拿实现报告冒充看过尚未发生的执行结果。

本轮不提供 schema 1 文件归属语义的兼容层。历史账本可保留供审计，不能据此承诺旧运行可无缝用新代码续跑。

## 4. 已修复的其他确定性问题

### 环境与提示矛盾

提示允许复用已恢复的 Cargo 环境，但 gateway 原先强制设置新的 `CARGO_HOME`。这可能隐藏已安装的 cargo 子命令并丢弃热缓存。移除强制覆盖，保留环境恢复阶段证实可用的设置；没有删除依赖阶段的网络配置。

### 真正的框架修复没有被进展检测看见

旧恢复指纹未覆盖框架任务的 target worktree，容易把实际源码修复当成“输入没变”。现在覆盖源码与 `implementation-smoke.sh`；只改报告描述不会刷新可执行修复进展。

### 复用可能复活过时分析

target study 的复用身份新增实验路线、缺口登记、查询协议和相关规则。只考虑最新相关回执，不再在最新结论失效后向前搜索一个恰好匹配的旧结论。

### 规则身份漏掉实际执行规则

prompt policy digest 新增适用的 `execution.md`、`repair.md` 及修复额外使用的 QEMU 文档。只纳入相关阶段，避免全局任意文档变化使所有审查失效。

## 5. 离线验证与能说明什么

回归使用合成 Git 仓库、合成源码/镜像和本地模拟执行，不调用真实模型，不认证 E1000 或其他驱动行为。

验证结果：全量 164 项通过；随后新增的重启/回执失效测试和规则依赖测试各自通过，并复查最终审查规则复用。当前共 166 项测试。修改文件的 Ruff F 检查及 `git diff --check` 通过。

重点覆盖：

- 完整交付路径、准备不完整的补充路径，均最终经过独立审查。
- 框架和实现修改同一个集成文件不再被旧归属规则拦截。
- 合并交付时实现、打包和公共测试准备不各自新增规划调用。
- 最终快照仍检测内容修改、新文件、删除与 executable 状态变化；旧排除字段不能隐藏漂移。
- 框架真实修复改变恢复输入，纯报告编辑不改变。
- 最新分析回执否定时不会复活更早的匹配结论。
- gateway 不再强制覆盖已恢复的 Cargo 环境。

合成成功路径的交付段 worker 调用：旧分拆 5 次 → 先前合并准备版本 3 次 → 本轮完整交付 2 次（完整准备 + 实际执行后的核对）。独立分析/最终审查不在这个分母中，仍正常执行。

成本归因也随任务合并改变：更多 token 会计入 `target_framework_enablement`。后续必须比较整段交付与全程总费用，不能用“driver_implementation 费用归零”宣称工作已消失。

**这不是总 token 减少 60%，也不是总费用减少 60%。** 单次交付任务会承担更多工作。预期收益来自少重复理解、少交接、少补遗漏及复用构建成果；是否抵消更长单任务的上下文和修复成本，尚待真实对照。

## 6. 审阅时发现的问题（后续状态见修复台账）

本节保留当时审阅记录。后续代码、逐项修复状态及新的验证结果见 [全面修复台账](SKILL_WORKFLOW_REMEDIATION_2026-09-26.zh-CN.md)，不要将下述旧状态当作当前实现。

以下未在本轮全部实现，不把“已发现”写成“已修好”。

1. **材料部分获取失败的显著性。** 一个 facet 有成功材料就可能标为 CONTROLLED，失败 locator 留在 retrieval ledger，分析输入导航却主要指向材料和缺口。后续应把失败摘要与 ledger 指针带入合并分析，先让模型判断是否影响义务，不新增“任一下载失败即重试”的门槛。
2. **回执与任务实际读取的规则。** 当前部分准备回执基于接受时的状态；任务运行期间修改规则的竞争条件、接受后事件写入前崩溃，仍需专项处理。应绑定 job 实际规则版本，恢复时使用已记录证据；不能仅扫描报告文字宣布跨阶段完成。
3. **旧 study 复用与合并分析回执。** 旧报告复用路径尚未自动重建完整合并回执，可能保守地多跑 contracts。不能只为省一次调用，把旧的目标研究报告当成已涵盖所有 source/contracts 的新报告。
4. **检查器裁决的类型。** 目前 worker 裁决可以覆盖较宽泛的 validator findings。应区分不可豁免的输入/运行绑定与可解释的语义提示；设计前先清点实际误报，不扩张启发式硬拦截。
5. **控制器缺陷与可修复实现缺陷。** 泛化异常可能进入付费 recovery。应按明确异常类型路由环境/控制器问题，避免让模型反复修 driver 来解释控制器 bug，不宜用报错文本关键词拼凑分类器。
6. **执行核对是否可与独立审查合并。** 本轮仍保留 worker 看实际结果，避免删除语义责任。未来可研究结构化 oracle 输出直接供独立 reviewer 消费，失败才回 worker，但要先明确公共测试真实性与归因契约。
7. **单调用内部的浪费。** transport 已有 idle/total timeout，不能说“没有超时”；但仍缺少按实际进展工作的高层预算/停滞观测。外层少调用并不能防止一次调用内重复 build、全文读取和短轮询。
8. **实验复现配置。** reasoning effort、实际 provider/model 配置应作为不含密钥的运行元数据明确记录；cache-write 和实际计费仍需区分。

## 7. 上下文策略与后续实验

保留“分析完成后交接干净材料、实现期保持连续上下文”的方向。清空的是早期探索轨迹，不是证据、未决问题与失败观察。框架与驱动已经由同一交付任务承担，不应再在它们之间机械清空上下文。

独立 reviewer 保持独立；worker 的失败证据通过带来源的回执交给 reviewer，而不是复制全部试错过程。只有在实质目标变化或历史污染明显时考虑新的工作会话，不按每个账本节点强制 reset。

正式对照前，先完成离线回归、重启/失效审阅及提示一致性检查。实验需要冻结源/目标版本、契约与公共测试范围，记录初始环境和缓存，固定模型/推理设置；至少报告总成本、首次交付通过率、语义缺陷/修复次数、工具输出与重复执行。比较纯 Skill 时保留同样质量义务，不能只比较调用数或最终 PASS。

当前结论是：结构优化已经可运行并有离线证据；尚不能承诺接近 $40，也不能用本轮合成回归宣布真实驱动迁移质量等价。
