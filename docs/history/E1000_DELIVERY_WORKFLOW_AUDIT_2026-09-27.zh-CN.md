## D14-01：已关闭的修复报告仍以当前任务出现（高优先级）

**事实。** E3 明确写 AR-001～005 已关闭。实际第 14 步输入却仍含 `reference_material.repair_task`，来源是上述旧报告，正文包含 `Verdict: REWORK`，指令为 “This report triggered the current repair”。同一输入的 `delivery_essentials` 又说明这些问题已修正，状态是 `READY_FOR_IMPLEMENTATION`。`repair_task.state.status` 为 `PREREQUISITE_COMPLETED`。

**问题。** 先前修复正确地禁止“上游 PASS 自动等于 finding 关闭”，但缺少“后续正式审查已确认关闭”的终止传播机制。新旧证据被同时呈现，却没有足够明确的取代关系。

**因果限度。** 已确认输入冲突；未证明模型因旧报告而重复修复，也未证明它造成运行挂起。不要将时间损失全部归于此项。

**修复方向。** 用已有审查结果、修复事件及其绑定输入建立 repair episode 的关闭/取代关系。普通依赖完成仍不能关闭 finding；有明确复审结论时，只向后续任务提供当前未结事项和最新结论，旧报告保留为历史引用。部分关闭时保留剩余事项，不能粗暴隐藏整个报告。

**验证。** 离线覆盖：仅上游 PASS、复审全关闭、复审部分关闭、新报告替换及手工反馈无绑定报告。断言当前语义和引用准确，不要求某句固定英文。重点入口：`core/store.py`、`codex/cli.py`、`codex/repair_handoff.py`。

## D14-02：精简后的上下文没有保证关键决策可用（高优先级）

**事实。** 实际提示词要求先读 handoff 和相关权威分析；E1 工具轨迹未见读取这两个完整对象，模型直接搜索目标源码。内联 `delivery_essentials.text` 被截断，`truncated=true`，末尾停在 “The wrapper records ”。完整分析/测试要求仅以引用提供。

**问题。** 提供路径不等于读取；告诉模型“必要时再读”也不能保证它知道遗漏了什么。当前输入对交付契约有较多摘要，对最可能推翻实现的未解假设则缺少同等直接的呈现。模型说会检查 handoff 不能作为实际读取证据。

**边界。** 模型已经收到内联内容，不能称为“完全没带上下文”。未见文件读取也不能证明它没有理解任何相关要求。

**修复方向。** 在固定总预算内组织一个自足的交付启动包：当前决策、关键 API 前置条件、最多几个会改变方案的未解问题、完整但精简的义务导航、已验证命令。删除过时修复材料腾出空间；按语义段落截断，不把命令或前置条件切半。细节保留可直接定位的源码片段与引用，不增加多轮拼接工具链。

**验证。** 用本次冻结输入离线生成新旧启动包，比较长度、遗漏的关键决策和引用完整性。不要加“必须读过 N 个文件”的硬门禁，也不要求机械复述分析报告。

## D14-03：关键 API 不确定性未在最早的低成本点解决（高优先级）

**事实。** 模型最初声称 PCI interrupt-line 可经 `IrqLine::alloc_specific` 映射；首次 managed run 后承认该字段是 legacy pin，而接口需要 CPU vector，随后参考 UART/PIT 改为分配 vector 并映射 pin。E1 的 item_44～item_51 记录了失败、查证和修改。E3 已保留 IRQ 路由为待运行确认项。

**问题。** 原本要求“检查定义和真实调用点”的策略没有有效落到实现顺序。这里至少一部分错误属于可静态查明的参数语义，不需要靠完整 QEMU 启动发现。

**修复方向。** 对已有分析标出的关键不确定性，启动包直接给出接口参数语义和一个匹配调用点；明确区分“静态已知”与“实际路由仍需运行验证”。先修静态误用，再做必要的最小运行探测。不为每个 API 新建模型节点或测试。

**验证。** 用现有源码检查能否直接暴露此次 pin/vector 混淆；同时用非网络任务输入确认不会凭空生成 IRQ 检查。无法根据本次日志量化节省金额。

## D14-04：超时后资源清理不充分，且手工清理范围过大（高优先级）

**事实。** item_52 的 managed run 超时；item_56 下一次运行出现 UDP 19000 转发绑定失败；item_57～58 查询端口/容器并停止一个容器。之后多次使用 `docker ps -q --filter ancestor=asterinas/dev:0.18.1-20260805 | xargs -r docker stop`。

**问题。** 此序列支持“超时后仍有相关容器占用资源”的判断，但还需审查实验管理器与脚本的清理责任边界。按镜像清理可能影响其他相同镜像的实验，不能成为通用修复。

**修复方向。** 通过 job/experiment 标识或 cidfile 记录本次拥有的容器，退出/超时后只清理这些资源，保留退出结果和日志。端口可按运行隔离配置，不通过杀掉无关进程解决冲突。需同时处理控制器启动的实验和直接调试脚本。

**验证。** 用廉价本地进程及按需容器测试检查超时、正常退出、异常退出和并行运行隔离。无需调用模型或完整启动内核；无需扫描/停止所有同镜像容器。

## D14-05：超时反馈只有结果，没有足够的进展信息（中高优先级）

**事实。** 多次 managed run 返回 `TIMEOUT` 和 stdout/stderr 尾部，stderr 中有大量 TCG CPU 特征警告。模型逐次增加启动打印，以 80～150 秒不等的脚本超时重复启动，再回到 300 秒 managed run。item_61～90 可定位这一过程。

**问题。** 返回原始日志是必要的，但尾部不一定是最有价值的片段。构建、启动、设备初始化、首操作共用一个超时结果，模型难以判断下一次应改变什么。模型一度宣称定位到中断开启过早，但后续仍超时，因此该判断只能视为未完全验证的假设。

**修复方向。** 反馈保留总退出/超时事实，附本次命令生命周期、日志是否继续增长、有限的关键失败片段及完整路径；已有 harness 里程碑可选使用，不依赖固定 E1000 字符串。已识别的重复 warning 可压缩展示，原始日志不删。连续同类失败时，引导沿当前假设检查一个能区分原因的观测，不自动启动新审查或更多全量测试。

**验证。** 用保存的失败日志离线回放摘要：不能把 warning 当根因，不能把 silence 当死锁证据，不能漏掉端口绑定错误或 panic。不要为诊断而默认输出整份大日志。

## D14-06：合并交付目标与 PASS/续作语义不一致（高优先级）

**事实。** 实际 objective 要求首次完整交付，包含框架、驱动、运行插入、测试入口、产物和 harness。item_90 最后一次 managed smoke 仍超时；item_92 用 `--decision pass` 提交。报告明确写无 smoke PASS、无 ping 成功、public execution NOT_RUN，控制器把第 14 步记为 PASS，然后进入第 15 步。

**问题。** 如实提交未完成产物本身不应受罚，但“完整交付”目标、报告提交成功和功能验证成功没有清晰区分。当前 `delivery-task.md` 允许不完整准备进入普通 continuation，因此不能仅凭第 14 步 PASS 认定门禁绕过或最终错误验收。

**修复方向。** 明确区分产物已提交、工作待继续和功能验证状态。复用现有失败 receipt 将续作直接定位到未解启动问题，不能从头再实现；后续检查不应因文件齐全而消失，也不能因为首次试验失败就立即 BLOCKED。只有无可继续的实际外部阻碍才请求用户处理。

**验证。** 离线验证“报告提交 + smoke TIMEOUT”进入有上下文的续作，而非最终成功；已通过且输入未变的 receipt 可复用；不增加一次专门判断完成度的模型调用。还须跟踪本实验第 15～18 步，确认实际执行链，当前不作结论。

## D14-07：状态页面仍沿用合并前阶段名称（中优先级）

**事实。** `target_framework_enablement` 调用实际承担完整首次交付。模型写驱动并不是越界，但界面仍显示第 15 步 `driver_implementation PENDING`，容易让用户误以为一小时尚未开始翻译。

### 适用边界

- 启动包来自作者原文和可选标题，不把抽取程序当语义裁判。缺少标题不会触发门禁；超预算内容保留位置和明确截断标志。测试行导航只用于定位，不代替完整断言。
- 8,000 字符预算针对正文及索引标签，不包括 JSON 包装、路径等元数据。新输入包可能比旧的单一 5,000 字符摘要更长，但避免了旧修复报告和重复 Open decisions 的并存；不能据此承诺整体必然降本。
- 容器清理覆盖通过保留 PATH 的 `docker run/create` 调用；绝对路径 Docker、替换 PATH、特殊未识别 CLI 语法以及自定义守护进程启动不自动归属。不会用镜像/挂载目录推测所有权后停止容器。自定义脚本必须按自己的 CID 清理。
- 原生 Docker `stop --time 2` 的失败会进入 cleanup 证据并反馈，不扩大到其他资源；这不是容器守护进程不可用时仍能保证清理的承诺。
