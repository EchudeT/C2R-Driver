## 重要行为约定

- 仍是一个持久 worker；独立 reviewer 仅条件触发。20 个检查点不变。runtime 的受控执行前后
  使用同一 worker 两次交接，因此不能再将正常模型调用总数简单说成 9；没有额外总结角色。
- `DPF_RUN: PUBLIC_QEMU` 不代表 PASS。只有执行 receipt 通过且 worker 看过观察、完成自检后才接受。
- 辅助 harness 和可变 oracle 输入位于 `.dpf-output/harness/`，与主脚本、实现、镜像一起校验。
  report 和 runtime logs 不作为代码变化；被测试的输入不能在验收期间偷偷移到未绑定位置。
- `DPF_STATUS: BLOCKED` 不是异常重试。解决后操作者运行
  `dpf stage reopen PROJECT STAGE --reason '解决内容'`，再恢复 port。
- 上游 Skill 原文未修改。系统适配说明解释 state.py、KB 清单操作如何映射到控制器，
  避免同时要求模型维护另一套路由。参考了官方 Codex 提示指导的目标/上下文/交付边界划分，
  不按未经验证的“最佳提示词”改写迁移要求。

## 追加完成度复核（2026-09-20）

结论：**计划尚未全部完成**。上述表格是实现进展，不是 22 项全部关闭的证明。
本次复核不修改程序或提示词，不启动付费流程；以下两个新边界已用临时目录/本地子进程复现。

1. **F20 的 EOF 分支仍不遵守静默时限。** `codex/transport.py::_lines` 在 stdout
   EOF 后直接 `process.wait` 到总时限，不再检查 idle；异常为原始 `TimeoutExpired`，
   不是统一的 `WorkflowError`。本地进程关闭 stdout 后继续 sleep，设置 idle=0.1 秒、
   total=0.4 秒，实际约 0.4 秒抛 `TimeoutExpired`。默认配置下此分支可等到 6 小时，
   不是 1 小时；仍有总时限，不是无限挂死。应统一 EOF/非 EOF 的截止时间和错误出口。
2. **F14 的 harness 复用身份漏执行权限。** `_helper_inputs` 只记录内容 SHA256。
   同一 `helper.sh` 从 0755 改为 0644，返回身份完全相同；直接执行该 helper 的行为却会变化。
   `accept_self_review` 和独立审查复用均依赖此身份。应记录影响执行的文件状态，
   不能把“字节相同”写成“执行输入完全未变”。此复现验证身份碰撞，未冒充完整 QEMU 实验。
3. **F11 只有字节级重复保护，真实失败路径尚不足以验收。** `store.retry_from` 的
   fingerprint 包含完整 reason 和目标产物 digest；`port._structured_c` 的 reason
   包含每次分析的 report_path，source closure 报告含 validated_at。同一编译根因的
   重新执行因此可能得到新指纹，不触发三次保护。现有测试固定 reason 并复用原产物，
   证明持久化有效，但未覆盖这种生产路径。应拆开稳定失败身份和每次证据位置，
   以实质输入变化判断进展；不是单纯增加更多重试。

仍部分完成的原计划项：F15 的变更影响粒度；F05 仅提供独立同字节副本的 corroborated
路径，未提供通用 primary 来源绑定；F06 的补证会线性失效下游；F17 仍有自身索引哈希 I/O。
后两项是效率机会，不等同错误放行；F05 的缺资料显式 gap 也不应伪装成资料已验证。

  同一路径、同一实质身份允许三次回退，第四次记录 BLOCKED；换一种原因措辞不会重置。
