# 修复任务与证据检查点分离

## 原因和边界

此前解决了历史反馈过期，却仍将实现、打包、测试准备分别调用模型。一次真实缺陷会触发
多个交接和重新规划，成本与等待没有随失效范围缩小而有效降低。

这次按 Skill workflow 第9节、qemu-evidence 的要求，保留证据失效、产物身份、自检与
受影响回归，合并修复工作任务，而不是用 UI 编号不倒退来伪装完成。实现变化后，15–17
检查点仍须更新；它们不再必然代表三次模型任务。正常首次实现流程保持原有检查顺序。

## 修复协议

1. 实现或打包收到 OPEN 修复时，工作者在同一个任务中核实反馈、修复必要代码/测试、执行
   受影响检查、自检、按需重建产物并准备已有验证脚本。不直接照单全收审查意见；必须核对
   冻结范围、原始证据和当前代码。交付一份 delta 报告，不重新调查整个移植。
2. 控制器检查交付物存在、自检完成，并记录绑定源码、报告、产物、检查器、脚本与 helper
   内容的不可变 repair_prepared 事件。此事件不是 PASS。
3. 控制器用原有快照/产物检查器自动捕获打包结果。成功路径不追加打包模型轮次；真实检查
   失败才把具体错误交回工作者修复，不能用失败产物继续。
4. 控制器使用原有 QEMU 执行服务运行准备好的回归脚本，证明当前产物身份和实际执行，
   不追加测试准备模型轮次。执行结果交回持久 worker 会话做最终自检；机器退出零不能
   自动代替语义验收。
5. 相同输入的成功执行跨重启复用。失败执行跨重启不自动重跑，先返回证据进行归因。
   新源码/产物/脚本/helper、报告变化或新的失效事件均使准备记录不可复用。
6. 条件审查仍保留：再次审查明确获得上次意见与当前冻结输入，并提供 handoff 中的范围；
   用于核对修复及受影响路径，不拿旧结论冒充当前缺陷，也不将触发风险直接当缺陷。

默认修复目标由统一 repair_execution 模块维护，附带所需 QEMU Skill 参考；CLI 和提示说明
控制器将自动执行哪些动作。没有新模型表格、第二套旧兼容路径或私下 worker 指令。
状态显示 OPEN/RESOLVED、修复根和触发阶段，明确已有工作保留。

## 验证和限制

真实状态机测试覆盖准备→重开项目→静态捕获→控制执行→中断→复用→最终自检，以及
文件漂移、新失效和失败执行不自动重跑。此处 QEMU 是明确标注的控制器测试替身，不是
真实驱动功能证明。现有正常首次运行/条件审查全流程测试还检查减少后的模型调用数。

最终固定代码版本全量验证：290 passed，41 subtests passed，187.82 秒。
修复闭环专项：7 passed；未定义名称检查与 git diff --check 通过。
此前并行测试进程曾加载尚未更新的旧交付夹具；以上为修正后不再编辑代码的完整重跑结果。

运行 audit-01 已停止，原报告和源码未被监督者修改，历史回退不改写。新协议不会自动取消
审查提出的真实缺陷，也不能承诺未来没有实现错误或整轮低于某个价格。尚需真实运行验证。
