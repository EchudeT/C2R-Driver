# 约 40 美元纯 Skill 会话与工厂成本复核

此前预测优化后 $70–84 没有完整复测支持，撤回其作为预算依据的意义。不能把当前
工厂开销视作保质量的必要下限，也不能在未运行时承诺降到 $40。

## 找到的历史

Skills 移植 e1000，确认 82540EM；模型记录 `gpt-5.6-sol high`。成果位于
`/home/unix/file/C2R-Driver/.driver-port/e1000`。按 UTC 13:02:47 至 17:19:00 的
token_count 累计差分切出本次任务（包含开始请求及容量失败前后的片段，不把此前
NE2000 或此后 Skill 修改计入），得到：

| 指标 | 纯 Skill 历史 | 工厂成功运行 |
| --- | ---: | ---: |
| 输入 tokens | 61,624,021 | 105,793,475 |
| 缓存输入 | 59,558,743 | 93,838,080 |
| 未缓存输入差额 | 2,065,278 | 11,955,395 |
| 缓存命中比例 | 96.65% | 88.70% |

历史另报告 cache_write_input_tokens=2,063,114。其收费/包含语义没有核实，不能
套当前 estimate 冒充账单。若仅为量级检查，忽略单独 cache-write 计价、采用工厂
现有 short-context 标准费率作假设，结果约 $36.94，与用户记忆的 $40 接近；这
不是核实了实际支出，不能用来校准价格或断言中转倍率。

## 不能以“少验证所以便宜”解释

旧 final-compliance-audit 记录 22 个运行目录，包含外部 DNS/ARP、IRQ、环绕、
负身份、三次冷启动、SMP=2、NE2K 共存、TX 边界。仅从报告看，在 IRQ/IP 集成
维度比当前 polling/raw Ethernet 更广；其报告仍需独立验证，不能一概评为更差。

但并非冷启动公平对照：旧 target-changes 明确记录了 NE2K 及既有 manifests/
network interface 改动，源/目标 revisions 与新运行不同，旧会话携带先前迁移
经验和环境。当前实验另有独立审查及 PCI I/O BAR 框架扩展。不能直接从费用差
推出节点数量、reasoning effort 或清空上下文的因果效果。

## 当前费用究竟花在哪里

工厂 $93.676 的现有估算分为：未缓存输入 $47.82，缓存输入 $37.54，输出 $8.32。
因此输出报告少写一点不会自动解决主要开销；即使缓存命中，也要为大量累计输入
付费。减少有效工作所需的模型回合和上下文体积比单纯控制输出长度更关键。

按调用原因：stage_work $39.17；repair $36.31；recovery $3.14；独立审查及复查
合计 $10.78；execution_self_check $4.28。只取消审查不能从 $94 降到 $40，且会
丢掉本次确实发现的 RX 边界、诊断状态和测试 oracle 缺陷。

repair 中两轮 driver repair 约 $32.43：第一次补齐冻结矩阵的可测试入口，第二次
解决最终审查的具体语义错误。不能将它们全部删除，但若前移矩阵实现与断言设计，
可避免“先构建/冻结一个不完整版本 → 后续发现 → 再实现/构建/写报告”的成本。
stage_work 的 $39.17 本身也不是无返工理想费用，因为它包括长单次调用内部的
编译错误、命令失败、截断和重新定位；这反而说明仍有比预测 10–25% 更大的潜在空间，
但不能将所有上述费用列为可兑现节省。

## 进一步优化的优先级

1. **交付闭环以冻结矩阵为主线。** 先有最小真实设备操作，再在同一次实现任务内
   完成全部可运行义务需要的入口、边界与故障 oracle，之后才冻结产物。保留公共
   验证/独立审查作为证据职责，但不要把第一次完整需求发现推迟到这些节点。
   当前已补入口映射指引；下一轮需要观察它是否真正减少后续源代码返工。
2. **减少材料重读而不是盲目丢历史。** 已实现交接 bug 修复、按摘要去重导航、
   精确有界读取、环境/框架配方引用。旧纯 Skill 高缓存命中说明“历史一定有害”
   不成立；在尚有增量修复价值的执行会话中保持连续，不能每节点强制新建。
3. **明确平台复用实验与冷启动实验。** 可以建设绑定 revision/config/image 的
   平台运行配方、既有接口研究和构建成果复用，来源明确且失效可检查。不要把旧
   驱动答案注入基线或让新模型随意查别的实验；论文中分别报告首次平台成本与
   后续驱动边际成本，旧 $40 是后者的候选参照。
4. **再评估节点合并。** 物理合并编排节点不自动减少内部工具回合。优先让产物
   准备复用实现阶段产物、让报告式状态转换不触发重新研究。当前部分已做到；
   进一步自动接受必须依靠既有绑定回执，不能仅扫描 PASS 字样或删掉验收。
5. **不先降 reasoning。** 便宜历史是 high，当前是 medium，不能假定 lower effort
   总成本更低。用相同冻结输入测试到达正确闭环的总费用，而不是单步输出成本。

下一轮应以 $40 为有价值的竞争参照，保留所有成本而非人为截断费用，同时报告
是否达到同一功能范围。当前证据足以否定“工厂必须 $70–84”的暗示，但不足以
承诺某个新价格。先测这一分支在固定输入下的完整闭环，再决定是否合并更多节点。

## 本轮已落实的结构性改动

首次实现也可提交完整的可执行交付，控制器复用绑定回执完成产物捕获与公共运行，
省去独立的打包、公共运行规划模型调用。合成控制器测试中，该段 worker 调用
从 5 次降到 3 次，运行后自查及独立审查不变；未准备完整时走旧路径。
详细行为与失效边界见
[实现记录](DIALOGUE_OPTIMIZATION_IMPLEMENTATION_2026-09-26.zh-CN.md)。

这一改动针对历史运行中“较晚才补齐矩阵入口”和阶段材料重读的风险；尚未用真实
E1000 迁移证明它减少了返工。下一轮应同时记录实现阶段费用是否上升、总调用数、
首次公共矩阵通过率、源代码返工次数和最终独立审查缺陷，不能仅报告少了两个节点。

用 call_id 对应输出，区间内发起而稍后返回的输出也计入。只导出聚合量，不导出

| 可见交互指标 | 纯 Skill | 工厂成功运行 |

| 外层工具调用 | 434 | 779 |
| 含 write_stdin 的调用 | 74 | 149 |
| 上述调用请求等待少于 5 秒 | 2 | 93 |

### 模型不该负责枚举控制器已知的文件

工厂材料闭包共六次调用。原始选择包含目录，收集器只接受文件，先后出现“facet
无材料”和“混合选择中的目录被遗漏”。最后一次模型将 60 个仓库路径选择改写为
143 个明确文件。其他轮次还涉及 facet 标识符、下载失败、同文档与独立来源规则，
不能将六次调用都归为目录问题。

旧 Skill 会话明确采用固定 Git revision 的材料导出脚本。它也经历 Intel PDF
下载失败、构建命令和 cargo-osdk 环境错误，绝非没有失败；有价值的差异是模型
能够用脚本一次完成材料枚举，而工厂让模型承担了本可机械处理的表示转换。

现在所有仓库的窄目录选择都由控制器从冻结 Git tree 展开。每个仓库一次查询，
目录与显式文件重叠在同一 facet 内去重，不合并不同证据角色。使用 literal
pathspec，文件名中的 `[]` 等字符不作为模式匹配；不从当前工作目录 glob，不混入
未跟踪文件。原始提案与展开后的提案均有原有 ledger/CAS 记录，后续仍执行冻结
文件内容验证。缺失路径保留给原有检索/缺口处理，不把空结果直接判为成功。

对历史第 17 号提案只读回放：60 个仓库选择，加控制器注入的 source entry 及
5 个外部缺口 locator，展开为 213 个 locator（208 个 Git 文件角色引用）。其中
PCI 从 1 到 12，DMA/IRQ 从 8 到 35，网络参考实现从 5 到 24。见
[目录回放记录](../audits/e1000-directory-selection-replay-2026-09-26.json)。
回放没有访问网络、调用模型或完成材料验收，不是新一轮迁移成功证据。

**取舍：** 完整目录比后来人工缩小的文件选择包含更多材料，不能假定材料收集
成本必然下降。提示明确建议窄目录；只需要大目录的一部分时继续指定文件。新能力
减少文件清单重写，并防止原先目录静默遗漏；它不替模型判断哪些材料语义相关。

### 本轮没有采用的“省钱”方式

- 不因旧 Skill 便宜而删除独立审查；已有工厂审查发现了实质语义缺陷。
- 不自动接受不同版本手册作为字节一致的来源证明，也不凭链接标题放宽 provenance。
- 不强制每个节点清空上下文。已验证的分析交接、执行阶段连续修复和可引用报告
  更符合两次历史的证据；高缓存命中本身也不能证明旧上下文都有效。
- 不宣称省下所有失败成本。下一次真实对照仍须核算完整交付提前准备的费用和
  新材料数量带来的检索开销，并保持相同功能目标及版本条件。

复现 Skill 区间统计：

```sh
PYTHONPATH=src .venv/bin/python scripts/run-log-audit.py \
  --native-log /home/unix/.codex/sessions/2026/09/13/rollout-2026-09-13T16-56-26-01a099fb-6bca-7c81-8f75-7c77f42a30e6.jsonl \
```

## 第三轮：知识库返回重复片段与无关摘要

继续检查发现，材料的多个 facet 可以引用同一文件，索引为它们分别生成 chunk。
旧搜索直接取排名前 N 个 chunk，重复的同一来源/修订/行区间会占据结果名额。
此外，compact 摘要固定取每段开头 240 字符，命中的函数往往位于后半段，导致
模型仅凭摘要无法定位，需要继续展开。这是当前查询实现的可复现问题，不能据此
推断历史运行中每次额外读取都源于它。

改动如下：

- 在应用 limit 前合并内容及全部证据元数据一致、仅 record_id/chunk_id 不同的
  结果。`also_indexed_as` 保留其他 ID，`show` 仍可读取每个原始 chunk。
- 不合并不同路径、来源、修订、行区间、domain、authority 或其他元数据的证据。
  domain/record/path 过滤仍先执行，不改变检索范围。
- compact 摘要定位到查询原文；若没有连续原文，则定位到匹配 token。返回原文
  行区间与省略标记。保留原有匹配和排序方式，不把摘要当成完整证据或语义结论。
- 不重建或改写历史索引，也不绕过每次查询原有的内容完整性检查。

在工厂冻结 E1000 语料上选择五条诊断查询做只读前后回放，记录见
[检索回放](../audits/e1000-search-replay-2026-09-26.json)。两条具体符号查询结果：

| 查询 | 结果条数（前→后） | 不同片段数 | 摘要包含查询（前→后） | JSON 字符（前→后） |
| --- | --- | --- | --- | --- |
| e1000_clean_rx_irq | 10→5 | 5→5 | 0→5 | 8,084→5,097 |
| e1000_xmit_frame | 8→4 | 4→4 | 0→4 | 6,469→4,110 |

两个查询的输出字符各减少约 37%，保留了全部不同片段。**这不是迁移 token 或
美元成本下降 37%。** 另外三条多词查询输出反而增加：新的行号、别名元数据以及
更多不同结果占用字符；其中 `DmaStream sync` 的前十条不同片段从 9 增加到 10。
这说明目标应是每次读取的可用信息，而不能只追求响应越短越好。

该小样本是开发者选择的定位性回放，不是 held-out 相关性评测；未改变排序，
也未证明多词查询的语义相关性提升。下一次真实迁移应统计重复 chunk 展开率、
search 后 show/源码读取次数和最终证据遗漏情况，以验证是否减少实际模型回合。

本轮也检查了公共执行回执的复用：该链路包含源快照、镜像、脚本、变体和输入
绑定。没有足够依据把历史执行失败或跨修订运行全部视作可省成本，因此没有仅凭
“看起来只是改了报告”放宽执行回执匹配或审查要求。

## 第四轮：把同一批知识问题作为一次只读请求

历史 worker 原生行 635 在同一工具批次启动七条 target 查询，涉及 PCI、网络、
DMA、IRQ、组件、打包和安全。这已经是外层并行调用，不能宣称新接口把七轮模型
推理降成一轮；实际重复的是七次进程启动、语料校验、索引加载和来源信息输出。

新增可选命令：

```sh
PYTHONPATH=src .venv/bin/python -m driver_port_factory.cli knowledge search-batch RUN \
  --queries-file queries.json
```

`queries.json` 是问题列表，每项包含 `query`，并可带 `domain`、`record_id`、
`path_prefix`、`limit`。例如：

```json
[
  {"query": "DMA ownership", "domain": "target", "limit": 5},
  {"query": "interrupt teardown", "domain": "source", "limit": 5}
]
```

每批只校验和加载一次索引，在同一个已加载快照上查询；没有跨命令持久化校验
缓存，下一次请求仍重新验证。每题结果保留原排序、score、摘要、行号和别名；
hit 的 chunk_id 指向共享 evidence，再由 document_id 引用共享 documents 中的
来源、修订、路径、记录身份等信息。用这些表可逐条还原单独查询的完整结果。
`--full` 也支持同样的无损还原，原始 `show` 与单条 `search` 接口继续可用。

生成的项目知识库接口说明和 query contract 已接入该命令。旧四命令合同仍可验证，
search_batch 是可选扩展，不能因历史运行没有它而让旧成果失效。

### 实际七问回放

使用历史七条问题及原 domain/limit，在同一冻结 E1000 语料上交替运行单条组与
批量组四次；两组均包含第三轮去重/摘要优化。记录见
[批量检索回放](../audits/e1000-batch-search-replay-2026-09-26.json)。

| 指标 | 七次单条查询 | 一次批量查询 |
| --- | ---: | ---: |
| 索引校验/加载次数 | 7 | 1 |
| 返回命中总数 | 56 | 56 |
| 可无损还原原排名/引用/摘要 | 基准 | 是 |
| 格式化 JSON 字符 | 53,799 | 49,334 |
| 进程内耗时中位数 | 0.226 秒 | 0.089 秒 |

批量结果包含 50 个不同片段、30 份文档身份。输出字符减少约 8.3%，只减少重复
元数据，不削减每题候选。耗时不包含 CLI 启动与模型响应，只节省约 0.14 秒的本地
工作，不能把相对加速描述成整次翻译显著提速。

开发中曾只共享片段，输出反而增大，因为七题的片段重复很少；最终增加文档级
来源共享后才有上述收益。这也是不以“用了缓存/批量就一定省钱”为依据的例子。
命中几乎没有共同来源时仍可能增加封装开销；提示建议小批独立问题，依赖前一步
结果的追问继续使用单条查询。该接口没有新增模型调用、预检门禁或验收规则。

## 第五轮：以总迁移成本为目标合并分析任务

用户明确后续优化不受兼容性约束。此前检索字符减少 37%、批量输出减少 8.3%
都是局部量，不能相乘或外推为整个迁移的降价。后续优先修改模型任务分工和返工
路径，允许改变接口、节点与协议；保留的证据边界应服务于可验证质量，而不是
为了保持历史工作流形状。

本轮把首次目标平台研究和源语义/迁移契约/测试矩阵合为同一次模型任务。过去是
先研究目标 API，再在下一任务把源语义映射上去；现在要求在一个报告中从源行为、
目标 API 前提追踪到可执行断言，边分析边暴露不匹配。独立分析审查继续覆盖整份
分析。控制器负责衍生 handoff 和登记三个证据角色，不再为机械分阶段触发另一
次正常路径分析调用。

具体行为：

- target_platform_study 的任务范围扩大，读取双方材料及测试规范，提交一份
  完整分析；工作区仍用于报告和有界分析探针，不允许进入驱动实现。
