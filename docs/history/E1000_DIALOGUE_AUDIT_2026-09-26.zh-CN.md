# E1000 对话级审计：冗余与流程符合性

后续机制实现及真实短 QEMU 回归见
[优化落地记录](DIALOGUE_OPTIMIZATION_IMPLEMENTATION_2026-09-26.zh-CN.md)。

承接 [运行复盘](E1000_RUN_OPTIMIZATION_2026-09-26.zh-CN.md)，本轮进一步读取两条
原生会话中的可见消息、工具输入/输出及冻结回执，不解析 reasoning/encrypted
内容。每个线程只选最后保留快照，按 25 份 metrics 的调用起止时间分配工具记录，
以 call_id 匹配输出。原生行号指该线程最新快照 JSONL 的物理行；原始记录只在本地。
机器统计见 [对话审计 JSON](../audits/e1000-dialogue-audit-2026-09-26.json)。

## 结论

主要冗余不是简单的“历史越长越差”，而是大批读取截断、压缩后丢失可执行命令、
过短轮询，以及把当前报告做成不断追加的历史而增加重建状态的成本。独立审查和
多数运行失败后的重试有具体质量价值。还发现一次真实的容器进程采集漏检；这与
源代码错误应分开处理。没有证据支持取消所有审查、屏蔽所有重复命令或每节点清空。

### 大批读取与截断

目标研究仅 19 次工具调用，但六次发生截断，输出约 40 万字符。worker 行 650
同时读取 PCI bus、配置空间、MSI-X 和 Virtio 多个大段，每个子命令允许 15k–20k
tokens，而外层汇总截断。行 660 又读取 MSI-X 的 1–240 行，和前次 1–340 重叠；
行 752 再读 35–185。第一次和第二次相隔约 14 秒，第三次在压缩后。

这证明了重复请求的源码区间和截断，不证明模型三次都实际看到了完整区间，也不能
证明每次都无用。类似地，冻结契约初次分析 46 次调用出现八次截断，首次实现 128
次调用出现九次截断。把每个子命令上限调大并没有解决外层汇总上限。

优化已加入通用 job 指引：先搜索，再读取当前问题所需片段；并行任务仍可并行，
但按合计可见输出控制大小，返回简短标签/正文/退出码；截断后补缺失片段，不重复
整批读取。不新增截断拒绝器，不要求所有日志进入提示，也不硬删模型需要的证据。

### 可执行命令没有稳定跨压缩复用

框架阶段 worker 行 1493 记录 host rustfmt 缺匹配动态库，随后切到容器；行 1904
记录 ktest 从 crate 目录解析错误相对磁盘路径，行 1999 记录 EFI 镜像用 legacy
BIOS 启动失败，行 2086 记录过滤器导致 205 项测试全部被过滤。模型最终正确将
零测试标为 NOT_RUN，并完成了 PCI 测试和 OSTD 205/205。

首次实现经历多次压缩后的重新定位：行 2563 尝试普通 workspace cargo check，
因目标 features 不完整失败；行 2652 又遇到隔离 CARGO_HOME 中没有 cargo-osdk。
这些是命令/环境问题，不应导致驱动逻辑改写。行 2701 的另一次失败源于清理时移除
被 Pod derive 间接使用的 zerocopy 依赖。行 2860 才在最终 ELF 中发现驱动虽被
编译却没有实际链接，随后显式 linkage 修复。

已在原有报告指引加入“成功后立即记录可执行配方”：命令、cwd、必要环境、工具/
镜像身份及日志路径。压缩后先恢复该配方；输入变化则重新核验。已有执行指引补充
陌生 runner 的 firmware/filter/console/cwd 预检、首次产物即检查真实插入、检查
宏生成依赖、避免没有必要的晚期清理。这是工作顺序建议，没有新增格式校验门禁。

不能据此声称所有重建都浪费：最终修复六个 selector 镜像使用同一内核、不同启动
选择参数，日志里顺序执行 make kernel 并复制 ISO。构建系统可能已经增量复用；
要证明“编译六次”需另查构建日志。暂不替换受支持打包路线或引入跨配置构建缓存。

### 当前报告与历史混在一起

public_qemu_validation 的 `5b0f94d8…` 调用先读取历史 rework 报告，再追加大量新
证据说明旧结论被取代，最后还扫描尾部确认多个状态不会被误读。历史回执/CAS 已
保留旧版本；让当前入口靠最后一段来解释旧 verdict 增加读取和判断负担。

已建议在原报告顶部保留短的当前状态、未决义务、有效回执和历史记录位置；修复时
更新当前结论，保留原始失败日志及不可变旧产物，不复制整份历史进新报告。没有
另造一个必须维护的摘要文件，也不要求模型重新概括全部会话。

## 流程符合性

| 环节 | 审计结果 | 判断 |
| --- | --- | --- |
| 分析→执行会话交接 | RESOLVED retry 误阻止 handoff | 已在上一轮修复；本次成功不证明交接有效 |
| 材料阶段职责 | 选择材料、提交 proposal、处理原文/出处问题 | 观察到的工作符合职责；格式性返工可减少 |
| 环境 smoke | QMP 模型检查，与真实驱动运行分开 | 里程碑划分正确，但 collector 曾漏检 |
| 框架改动 | PCI I/O BAR/OSTD ownership 及枚举 payload 所需 consumer 调整 | 未把驱动实现塞入框架；框架 QEMU 回归合理 |
| 首次实现 | 真正 TX/RX 后提交；缺后续冻结测试入口 | 最小运行成立，但未完成所需可测试性，已补提前核对指引 |
| 制品准备 | 复用 ISO，强化嵌入 kernel/boot entry 的 checker，无额外 QEMU | 符合预期；checker 改动需新身份绑定 |
| 公共验证 | 缺入口时退回 driver；已有有效回执时只复查并提交 | 路由和复用符合预期 |
| 独立审查 | 初审两条语义发现，终审五条，复查接受修复 | 必要质量工作，不宜删除 |
| 末次证据审查 | 放过模板措辞、旧派生日志和不影响归因的 collector 诊断 | 未看到为这些非实质问题强制返工 |

上表是对可见动作和报告/回执的审计，不是完整 syscall 写路径证明。对工具输入做
历史项目路径、备用 state.py、破坏性 reset、子代理等简单筛查未发现对应命令，
但字符串筛查不能证明所有 shell/Python 行为都无越界。审查者可见文件写入指向
自身报告；不把这种观察扩大为强隔离认证。

框架阶段自己一度说 QEMU 不归本阶段，后又正确运行 driver-independent regression。
实际边界应是“不能实现驱动或执行驱动公共验收”，不是“不能用 QEMU”。因此没有
加一个禁止框架 QEMU 的规则，避免为了节点边界把必要验证推迟。

## 采集漏检：需要修机制，不能当驱动错误

环境恢复 `571caafd…` 的 worker 行 563 描述：模型 smoke 约 0.2 秒完成，controller
没有观测到 QEMU。行 576 的补丁向 QMP 输入流加入 1 秒和 5 秒 sleep，让同一有效
进程活到采样时刻；行 596 记录修后 6.2 秒通过。当前 ContainerTrace 顺序调用
docker ps/inspect/top，再等待 0.2 秒，确实存在短进程采集窗口；具体因果时长仍是
日志中模型诊断，未在本轮独立复现。

**这次 recovery 是可避免的采集开销候选，不是驱动质量提升。** 不推广固定 sleep，
也不直接把脚本 marker 当可信 process receipt。后续应单独复现短寿命容器/QEMU，
评估事件驱动发现、运行内可信 exec 记录与现有 host/container 绑定；即使事件捕获
容器开始也不自动证明其中 QEMU 执行。需要专门测试后再换采集机制，本轮保留当前
接受规则，避免用放宽归因来换取表面 PASS。

## 本轮交付与验证

扩展 `scripts/run-log-audit.py`：对完整调用区间进行 call_id 配对，输出截断、
轮询和字符统计；不导出工具参数/原始正文，不分析隐式模型状态，缺失记录显式记录。
增加合成回归验证跨调用归属、长短等待、缺失输出和隐私边界；真实运行离线回放
已生成上述审计文件。提示修改沿用原节点，没有增加模型检查轮次或新硬门禁。
验证完成：122 项全量测试通过；新增审计工具的静态检查与 diff 空白检查通过。

下一次复测要同时看截断次数、工具输出体积、构建路线失败、已知命令复用、
公共矩阵完整性和实际费用。减少输出/轮询不自动等于节省费用，尤其缓存占比很高；
本轮没有付费重跑，不声称节省比例。
