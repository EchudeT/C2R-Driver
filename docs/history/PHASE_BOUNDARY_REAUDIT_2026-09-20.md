## 发现的问题

### B1 / P1：源码阶段的输出要求先于其证据

位置：`data/prompt-packs/default/manifest.json` source_closure；
`port.py::_source_closure/_structured_c`；`orchestration/migration.py`。

原 prompt 要求完整 source-closure phase 和分支/回调/行为报告；控制器却在该报告提交通过后
才运行静态分析。原通用提示的“After C analysis”没有明确指向控制器检查点。
worker 将阅读源码理解为已经完成 analysis，错误并非不可理解。

临时 prompt 即使增加“不要查 c-facts”，仍保留 branches/callbacks 等分析要求，**未根治**。
需要一个内部闭环：编译输入 → 静态事实 → worker 理解/补闭包 → 源码分析完成。

### B2 / P1：工具没有区分未就绪与损坏

位置：`source_analysis/navigation.py::open_navigation`；`knowledge/cli.py`。

旧工具在缓存目录不存在时直接称 missing/stale/damaged，建议重建。
controller 仅在 structured_c_analysis PASS 后准备导航，二者缺少共同的可用性协议。

本轮临时修复已让 CLI 查询/构建先检查阶段并返回 C_FACTS_NOT_READY。
应保留这个状态区分，但在新设计里从内部分析产物的有效性生成，不依赖用户可见编号。
NOT_READY、损坏、提取失败、原始资料缺失必须对应不同处理路径。

### B3 / P1：回退按位置失效，不按实际输入变化

位置：`core/store.py::retry_from` 的 `WHERE position >= ?`；
`orchestration/specification.py::append_linear`。

选择最早 gate 后，代码直接把它后面的所有阶段失效。即便补的只是源码文件，环境实验、
目标平台研究也重跑。当前线性依赖图同样把执行先后误当作数据依赖；只把 SQL 改为图遍历
仍会得到相同的过大范围。

需要区分调度顺序与产物依赖，并按修复后的实际内容判断复用。没有证据证明旧结果有效时
才重做相应检查；不能用“都标 PASS”或全量跳过替代验证。

### B4 / P1：生成 KB Skill 与 worker 权限相冲突

位置：`knowledge/skill_generation.py::generate/_template_path` 和本轮生成的 KB SKILL.md。

生成器原样套用上游模板：每次 retrieval 前运行 status、缺失时直接改 manifest/rebuild。
通用 prompt 又说不需每次 status、禁止修改冻结清单，worker 的 workspace-write 也不含
知识库控制目录。上游 Skill 要求遵循本地 KB Skill，因此不能依赖一段 override 消除歧义。

应由本项目生成适配真实接口与权限的 KB Skill：查询自己验完整性，补证据走受控工具，
只要求 worker 指明所需原始路径和原因，不给不可执行的写操作。

### B5 / P2：已有的源码语料自动扩展能力未进入任务接口

位置：`source_analysis/closure.py::finalize_compilation_database/_extend_knowledge`。

提交有效 compile_commands 后，控制器已会发现编译依赖、绑定源码并扩展知识索引。
worker 却被通用指令引导为“required original missing → evidence_closure”，不区分
冻结仓库已经存在的编译依赖和真正需要重新取得的外部证据。

应把编译器发现的本地依赖并入源码分析工具内部；原仓库已有且可验证的文件不应强迫 worker
先回第8步。非编译依赖的手册/目标资料仍需受控补充，不能直接忽略。

### B6 / P2：实现/打包边界存在类似的刚性回退风险

位置：`migration/artifact_preparation.py::capture_codex_artifact`；
`migration/implementation.py::validate_worktree_snapshot`；`port.py::_artifact_preparation`。

第17步任务要求补齐实际 guest 测试入口与依赖，但第16步已冻结所有跟踪源码；第17步的必要
manifest/guest 配置修改也可能触发 ImplementationChanged，回第16步。这里检查漂移是必要的，
不能删除；风险在于把“哪个产物变了”粗化为“完整实现阶段重做”。

这是代码确认的可触发路径，**不是本轮已经发生的错误**。应把实现、构建/打包、执行作为
同一 worker 内可迭代的工作，内容变化只触发必要快照与对应自检；不能让打包修改逃过自检。

### B7 / P2：刚加的确认一次守卫不是结构性修复

位置：`port.py::_codex_gate` 中 source_evidence_repair_checked。

它在13请求回8时多给一次解释，再重复请求仍会回退。真缺证据也会多一次模型往返；
布尔标志不持久化。它只适合临时减损，不能保证杜绝错误路径，不能作为最终实现保留。
合并源码阶段、修正工具状态和依赖失效后应删除此特例及只服务该特例的测试。

### B8 / P2：旧的模型输出路径仍暴露第二套要求

位置：`target_study/cli.py`、`target_study/service.py` 对比
`port.py::_accept_target_study_result` 和 `target_study/validation.py`。

主流程接受一份 Markdown 并复用为 profile/API/trace/plan；CLI 仍暴露 profile-json、
api-table、analogous-trace、change-plan 四份 JSON 的完整服务。
这是实际代码中仍存在的双入口，不是主流程已多调用四次模型。没有实际使用需求应删除旧路径，
统一验收语义，避免 worker 从 CLI 帮助中发现另一套必须填表的要求。

### B9 / P1（验证缺口）：测试覆盖函数，却漏了完整任务协议

之前的离线测试未模拟：实际 Skill + 通用提示 + source_closure 任务 + 尚无事实的工具返回 +
worker 的 REWORK + 控制器依赖失效。新加的“确认一次”测试也只验证局部防线，不证明职责一致。

不能靠增加提示词字符串快照补救。应增加少量真实状态机集成测试，见后文。

## 统一的实现方向（尚未完成）

### 工作阶段与内部工具分开

推荐：源码分析是一个 worker 任务，内部执行顺序为：

```text
准备最小编译输入
  → 控制器验证依赖并生成事实
  → 同一 worker 读取事实、补闭包/修编译输入
  → 源码行为覆盖完成
  → 后续迁移契约
```

静态提取结果必须可恢复、可缓存、可按输入变化重算。事实提取失败在此闭环内修复输入，
不得绕到环境/目标研究。编译器/外部工具确实不可用时明确 BLOCKED，不无限重试。
不要为了界面少一个编号而把提取、验收、权限全部塞进模型，也不要保留两套新旧运行架构。
现有运行恢复需要显式迁移/导入已有有效产物，不能手工篡改数据库完成状态。

### 提示从一份阶段协议生成

项目维护的单一阶段定义应包含：目的、已存在输入、可用工具/权限、当前交付、完成条件、
合法修复出口。它是代码/配置，不是让模型填写的表格。

- 通用提示只放全程不变的约束：范围、证据可信边界、工作目录、复用/自检、状态协议。
- 阶段提示只放当前任务，不能让源码输入准备阶段承担尚未生成事实的分析结论。
- 工具帮助与错误从同一能力定义生成，明确未就绪/损坏/输入错误/外部阻塞。
- 本地 KB Skill 与同一权限协议一致，不再依赖“上游说 A、追加说明改为 B”。
- 静态产物自动收集；自然 Markdown、代码和脚本维持为 worker 的主要交付。
- 不向所有阶段反复注入“不要查询第14步”之类事故专用补丁。

### 恢复与缓存

区分执行顺序与真实依赖；只在实际消费的内容发生变化时使结果失效。新语料追加不等于旧
环境/目标结论错误；旧结果也不能无条件复用。机器产物检查身份，worker 只复查新材料涉及的
判断。修复进度按实际输入变化计算，不按报告路径/措辞/模型调用次数重置。

## 重新启动前的最小验收

1. 同一源码工作阶段完成输入→提取→读取→覆盖，期间不要求未来产物，不产生回8/9的事件。
2. 缺生成头/错误参数只修对应输入；已有源码阅读、环境和目标研究保留。
3. 补一个本地源码依赖不重跑 QEMU 环境；补目标 API 只复查关联判断。
4. 事实缓存缺失由工具重建；事实未生成触发内部执行；真实原件缺失进入受控补证据。
5. 打包必要配置变化不会跳过自检，也不会重做无关实现/环境工作。
6. 中断后从最近有效内部收据恢复，保持同一 worker 上下文；不重复已通过的命令。
7. 使用实际生成的 prompt/KB Skill 检查权限与交付一致，不只测手写理想输入。

在这些验收前，不把局部测试全绿等同于“已彻底修复”，也不再启动付费模型来替代离线协议验证。
