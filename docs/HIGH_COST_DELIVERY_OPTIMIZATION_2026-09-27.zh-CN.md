# 优先降低分析与交付返工成本

本轮围绕历史 E1000 的高费用环节修改默认工作方式，而不是继续增加通用工具。分支仍为 `feat/e1000-run-log-optimization`，未运行新付费迁移。

## 为什么优先改这里

历史记录 `docs/audits/e1000-dialogue-audit-2026-09-26.json` 中：

| 旧阶段 | 常规工作 | 显式修复调用 | 合计估算 |
|---|---:|---:|---:|
| migration_contracts | $5.9863 | $3.8815 | $9.8678 |
| target_framework_enablement | $11.5185 | — | $11.5185 |
| driver_implementation | $13.5175 | $20.9577 + $11.4748 | $45.9501 |

三者约 $67.34，占整次 $93.68 的约 72%；实现阶段约 71% 花在两次修复。第一次涉及冻结矩阵所需的实现/测试入口，第二次涉及最终审查发现的真实语义缺陷。不能将全部修复费用视为可消除浪费：其中含必要实现工作；目标是前移正确决策，减少重复理解、重新设计、构建与交付。

## 默认任务已改变

### 分析只做到足以支持完整交付

新增 `analysis-task.md` 作为目标研究/契约任务的简短主说明，重点为：必要行为、真实目标映射、可执行验收与会改变设计的未知点。编译、布局、预处理证据只针对确实影响义务且原文未解决的疑问；不默认穷尽整个驱动，不要求完整语义索引或固定探针清单。

目标研究和契约仍共用一个实际分析任务/报告，控制器登记不同证据角色。契约单独返工保留稳定 ID 和未受影响结论，不重新做全部平台发现。

### 将交付要点直接带入实现

建议在同一分析报告开头写 `## Delivery essentials`，按必要行为说明：契约 ID、可观察结果、已有或需增加的驱动入口、目标插入/产物路线、原始证据。共用机制可合并描述，不另建报告、数据库或规划节点。

`migration/delivery_brief.py` 从已接受契约的 CAS 字节直接取出该节，最多 5,000 字符，附原始路径、hash、起始行与是否省略。未采用此标题的已有报告照常使用原材料路径，不拒绝、不调用模型补摘要。

同一会话中来源 digest 不变时，后续调用只保留来源/位置，不反复内联正文；版本变化或上下文重置后重新提供。记录“此前提供”不代表模型已经读取或仍记得。

这不是控制器从 prose 推断出的完整性证明，也不会将缺失行判为不存在。片段外及截断部分的冻结义务仍需履行。它的用途是让模型在广泛编码之前就看到后续验证所需的源码入口，减少历史上“smoke 后冻结，公共验证再退回加入口”的风险。

### 框架与实现面向同一次完整交付

新增 `delivery-task.md`，作为框架入口和实现阶段共同主说明。框架、驱动、共享集成、必要测试入口、产物、公共脚本由同一个持续任务完成，现有证据检查点照常记录。

每个必要行为的实现与可观察性一起推进；只为具体目标能力缺口修改框架。优先沿用成功命令、cwd、features、镜像路线。不因存在某个工具就新增探针，不建立通用测试平台，不执行无关设备机制的检查。

公共实验通过 managed execution 在当前任务内取得权威观测，模型检查后可以显式 acknowledge 当前报告；后续阶段复用输入绑定回执。修正了旧协议中“把权威公共套件留到下游”的矛盾文字。必要运行身份、自检与独立最终审查没有移除。

### 修复有独立的窄目标

旧方式在完整初始任务上追加修复要求；现在实现/制品修复使用明确的“修复当前交付”目标和 `repair.md`：当前缺陷 → 最小因果修改 → 受影响验证 → 更新产物/当前报告。

保留正确代码、已验证接口、原有构建配方、契约 ID 和有效实验。环境/采集/未改变行为的 harness 问题不自动改写驱动；源码变化仍必须重建并验证相应产物。只有实际影响其他义务时扩大验证，不为可选清理或推测性改进延长任务。调用方显式指定的 objective 仍优先，不被默认修复文本覆盖。

## 不再默认注入整套 Skill 文档

Prompt pack 新增 `on_demand_documents`，必须是该阶段 documents 的子集。高费用任务嵌入简短主说明，原 Skill 文档以路径/hash 引用提供，模型针对问题读取相关章节。

- 原文仍纳入规则 digest，变更会使相关准备/审查策略失效。
- 引用始终标明按需阅读，不因为会话里出现路径就宣称已经读过。
- 任务约定明确：冻结需求决定行为范围，当前任务说明决定工作编排；参考 Skill 不自动增加阶段、报告或全清单执行。
- 独立审查仍检查真实行为和证据。减少默认注入不是允许忽略技术限制或只根据摘要判 PASS。

## 费用统计防止“搬家式降本”

`status` 的统计新增 `by_work_episode` / `WORK_EPISODE`，按 analysis、delivery、review、other 分组，再区分已记录的 stage_work、repair、recovery、自检等调用原因。常规工作在字段中命名 initial，表示调用原因分类，不保证它是因果意义上的首次尝试；无法从旧遥测推断的保持 unknown。

study/contracts 合并或 implementation 工作移到 framework 后，费用仍计入同一分析/交付组。metrics 同时记录已知 repair trigger/root/status，方便后续区分哪里发现缺陷、哪里支付修复成本。未知 usage 和未定价调用保留计数，不当作零费用。

这只是可追溯归因，不判断每次返工是否浪费，也不新增运行时预算拦截或模型监督调用。

已对历史成功运行只读重放新统计：[结果](audits/high-cost-episodes-2026-09-27.json)。交付常规工作 $27.6271、显式修复 $32.4325、自检 $4.2774；总计仍为 $93.675952，没有因分组而减少。

## 验证与边界

- 契约、上下文和恢复定向回归：27 项通过。
- 新增高费用策略与交付端到端回归：31 项通过。
- 新测试覆盖原文片段/截断、缺少导航节时正常回退、CAS 来源、引用不注入正文但仍使规则失效、任务更名不制造费用下降。
- 最终全量回归：212 项通过，耗时 235.22 秒；所有变更 Python 文件 Ruff F 与关键错误检查通过，`git diff --check` 通过。
- 验证期间一次 `/tmp` 下运行的临时目录与重定向日志消失，原因未确定，该次结果不作为代码验证结论。最终将 `TMPDIR` 与日志迁至 `/home/unix/.cache/dpf-highcost-validation/` 后完整重跑，得到上述通过结果。
- 没有启动新 E1000、没有付费模型调用。不能承诺省去历史 $32.43 的全部修复费，或达到 $40。

下一轮真实实验应比较整段分析与交付费用、首次完整公共验收情况、分析/实现返工的触发原因和独立审查缺陷。若提示更短但查找轮数增加，或首次交付遗漏变多，应按总成本与质量调整，而不是维护本轮提示缩减数字。

按问题提供材料也已增加 [单次调用的问题材料包](PROBLEM_EVIDENCE_PACKETS_2026-09-27.zh-CN.md)：一次返回相关契约、源代码、目标接口与测试依据，内部完成明确引用定位和相邻索引块拼接；不新增模型归并调用。
