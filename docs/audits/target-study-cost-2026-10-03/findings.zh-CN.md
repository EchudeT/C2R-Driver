# pvpanic 06 分析阶段成本调查

调查对象是 driver-port-factory 的 `pvpanic-behavior-sol-medium-20261003-06`，
`target_platform_study`，2026-10-03 15:03:04—15:15:08（北京时间）。
本次只读冻结代码、实际 prompt、命令事件、原生 rollout 的计量记录、阶段产物和项目范围。
没有调用付费模型、重放运行中项目的查询或修改实验。08 的开发改动仍未完成验证，不属于已证实降本。

## 结论与修正

不能将 $3.77 归因于“模型重复阅读”。主要已观察到的问题是：

1. 跨采集、环境、分析持续累积的上下文，遭遇低缓存命中时产生大额非缓存输入；
2. 冻结的是设备身份，功能兼容范围仍在分析中推导，且前置研究规则要求较完整的平台/API/接入设计；
3. 知识库有导航能力，但分析验收与固定 BM25 查询重放绑定，实际没有使用 RAG 正文或共享经验接口；
4. 多份仍带全面调查要求的 Skill 与合并分析任务并存，阶段合并没有完全收紧交付要求；
5. 工具批量响应截断、自动压缩后补读是部分重复的合理来源，不能一概视为浪费。

40.9 万字符是命令原始输出之和，不是模型实际完整看到的输入。7 个外层工具响应发生截断。
只能用 token_usage_record 和阶段差分计量计算费用，不能把字符数按比例分摊成美元。

## 计量核对

本地公开费率表为非缓存输入/缓存输入/输出每百万 token $4/$0.4/$20；不是中转服务账单。
22 条独立 token_usage_record 相加与阶段 metrics 的差分完全相符，未重复计算 token_count 通知。
一轮控制器任务内部有 22 次有计量的模型请求，不应把“阶段只调用一次”解释为只付一次上下文成本。

| 项目 | token | 估算美元 | 占比 |
| --- | ---: | ---: | ---: |
| 非缓存输入 | 655,931 | 2.623724 | 69.54% |
| 缓存输入 | 1,829,120 | 0.731648 | 19.39% |
| 输出 | 20,892 | 0.417840 | 11.07% |
| 总计 | 输入 2,485,051，另加输出 | 3.773212 | 100% |

首个请求输入 162,679、缓存 152,448。阶段 prompt 仅 43,248 bytes，说明会话已有大量前序上下文。
15:06:57 的请求输入 215,773、缓存 11,008；15:08:16 输入 218,998、缓存 7,808。
两次合计非缓存输入 415,955，费用 $1.7465664（含各自输出和缓存输入），占阶段 46.29%。
后一次紧邻原生 compaction 记录；压缩后首个请求降至 33,530 输入。
压缩前 8 次请求 $2.4710584；压缩后 14 次 $1.3021536。

能确认缓存命中低及大上下文放大了费用；本地记录不能确认原因是服务端淘汰、路由、前缀变化还是其他机制。
不得声称是“缓存坏了”，也不能把 $1.75 全部当作可以节约的费用。
缩短报告或修改某个命令只解决部分问题：整个阶段全部输出也只占 $0.418。

因此不能说“06 初始上下文更长”或“有压缩所以更贵”。06 初始更短，但后续请求数、检索/调查轨迹和缓存命中不同。
两轮费用差约 $2.00，其中非缓存输入费用差约 $1.50。尚未开展同条件重复对照，历史结果不是因果实验。

v2 示例明确排除了 Linux sysfs ABI、完整 panic/shutdown hook 接入、实际 kexec、热插拔与多设备，
且预置了目标 crate、public callbacks 和测试适配器。06 的请求是完整驱动迁移，身份冻结只包含
PCI 型号与设备族，`excluded_variants` 为空；没有同等功能范围排除。
06 报告设计了 `/sys/pvpanic`、终止 panic 路径接入、halt/poweroff 接入和 component 集成。
这些来自真实源行为，不应未经范围约定直接删掉来制造低成本对比；但身份冻结被当作功能冻结也不够严格。

## 知识库实际效果

实际命令为 5 次 knowledge search（4 个不同查询），没有 knowledge rag 或 shared-search。
当前索引为 BM25，226 chunks，target 82 chunks；向量索引未配置。这不代表没有检索增强，
但不能声称本次使用了混合检索或跨驱动经验复用。

按已交付 probes 逐条回查原始响应：

| 查询主题 | 最终引用命中排名 |
| --- | --- |
| PCI 注册/所有权 | 1 |
| BAR 与 byte MMIO | 1、2 |
| panic/poweroff | 1、2、4、5 |
| 类似 component 路径 | 1、4、5、8 |

这些查询已有效找到关键定义。不能将成本解释为“知识库查不到，只好重做”。
但是每个查询都要求 top20，5 次原始返回共 73,527 字符，其中一次查询重复。
生成的 KB Skill 推荐 limit5；analysis-task 则明确要求 limit20，验收器按 BM25 top20 重放。
最远有效引用在排名8，机械统一改成 top5 会漏掉本次使用的证据，需要按缺口继续检索。

RAG 接口提供有界原文，但 focused probe 验收重放固定 lexical top20，未保存/验证实际 RAG
算法与候选集合。模型按分析提示使用 search 是合理行为。应统一实际检索收据与引用验收，
而不是再在 prompt 增加“必须调用 RAG”的要求。

共享库快照只有 121 ORIGINAL 和 1 EXPERIENCE。唯一经验是保留 nonblocking try_lock；
其 source/target revision 与本轮不同，需要重新核对，不足以覆盖 PCI、systree、接入等设计。
当前数据不能支持“跑过一次就不用再研究平台”的主张；已有存储/检索接口不等于经验已积累完整。

## 前置设计要求与停止条件

analysis-task 要求一个合并报告并按需研究，但原版 target-platform-study 文档仍规定：
复制完整平台 profile、列出预期使用的每个 API/type、追踪类似驱动完整路径、UNKNOWN 触发研究。
实际报告有 Delivery essentials、source semantics、target profile、API evidence、contracts、
test matrix、target changes、packaging 等章节。它遵循了收到的要求，不宜归责于模型自发写长文。

当前 target study 服务接收 Markdown 并检查引用/检索 provenance，没有按所有这些章节实施结构门禁。
因此有空间在不删除行为要求和证据校验的情况下统一任务协议；不需要再添加一个 reviewer 或格式校验器。

实际研究得到的有效结论包括：单次 poweroff handler 已被架构占用、try_lock 必须保留提前返回、
BAR access 的类型与所有权、PCI 无通用 sysfs 发布路径。不能因驱动短就认定这些调查没有必要。
应明确区分必须在分析解决的行为/架构前提，与当前实现行为中可以边编译边确定的局部 API/文件细节。

## 上下文与接口缺口

- context_policy=analysis-handoff 实际在 analysis → implementation 才切换；08、study 都继续采集会话。
- study 实际 job 反复写“frozen scope”，但没有直接携带 request/intended_subset/exclusions/完整源入口清单，
  依赖历史或间接原件找回。这也是不能贸然只改成 fresh thread 的原因。
- platform_execution 在 reference_material 与 tool_runtime 各出现一次；大约 3.6 KB 的接口复制，
  还包含分析暂不需要的执行接口。它有实质可精简空间，但不是 $3.77 的主要直接解释。
- 部分需要的 chunk 被截断后，模型补读正确；按需读原文也是 Skill 明确要求。
- check-probes 成功时展开 33,254 字符，既是静态校验结果也是整批原文重印；可改成摘要+完整收据。
- shared experience、RAG、lexical、直接源码四条路径尚未形成统一的已查事实/引用交接，不能单靠禁止重复查询解决。

## 建议的改造顺序（尚未实施或验证）

1. **自足的分析输入与会话边界一起改。** 自动交付当前请求、功能范围/排除、源码入口、版本、环境收据、
   已有结论与证据位置。首次完整分析使用独立会话；同一分析的继续/返修保留会话；实现仍连续逐行为调度。
   不把采集、环境日志带入研究。检查丢失范围/前提的回归，不能仅测试 prompt 变短。
2. **功能范围与设备身份分开表达。** 同一份分析明确每个源行为的保留、替代、目标不适用依据和验收层级，
   对会改变任务的排除走已有范围修订机制。成本对照固定同一功能范围与平台配置；不偷偷换成 v2 子集。
3. **统一知识消费和证据收据。** 对当前问题返回少量相关原文与引用，必要时扩展到更深排名。
   查询方式、快照、版本和引用由工具记录；验收校验实际检索证据，不让模型复写检索历史 JSON，
   不把 RAG 结果强塞进另一套 BM25 top20 假定。保留直接原文阅读，不规定查询配额。
4. **统一前置分析职责。** 完成源行为、关键适配责任、必要前提、可执行验收设计；局部实现 API/文件选择由当前
   行为落实。单一正文保存每项决定，移除与它冲突的“所有 API 预先 VERIFIED/完整平台调研”指令，
   保留源义务、非阻塞路径、资源发布/清理和测试判据。未知关键前提不能包装成完成。
5. **最后再处理输出浪费。** 成功检查返回摘要；有界检索避免外层整批截断；报告通过证据引用去重。
   这项是配套，不能作为主要降本论证。

验证应固定同模型、同路线、同范围、同共享库快照，统计每请求上下文/缓存/费用及分析遗漏、后续返工。
先验证完整输入在新会话中可独立推进，再做小规模重复实验。测量前不承诺具体降幅或 $10 达标。
不采用更多审查阶段、强制知识库调用、缩小测试义务或直接关闭语义核对来降费。
