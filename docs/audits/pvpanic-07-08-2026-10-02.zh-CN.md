## 优化顺序与边界

### 1. 通用环境执行由控制器提供

把已验证的 Docker 挂载、工作目录、stdin、超时、日志和进程采集封装为稳定执行接口。
模型只提供设备操作及断言，不再反复发明执行包装。
接口保持设备无关，pvpanic 断言属于该设备的探针，不能硬编码为全框架通过标准。

共享配方按目标版本、镜像身份、工具版本和执行要求匹配；复用配方仍执行本次检查。
匹配不成立时说明具体缺口。不能复用旧 PASS 代替当前运行，也不能绕过归因检查。
环境设备探针与目标构建/启动能力分别报告，不把前者提升为后者。

### 2. 失败反馈直接给出已知原因

如果执行器已知缺少挂载，就输出这个原因、涉及的调用和证据位置。
保留原始记录与失败状态，不要求模型再从泛化 FAIL 反推已知事实。
程序可以修正自身确定性的包装；设备语义与断言仍需工作者判断，不能自动放宽。

### 3. 07 定位材料，目标研究按问题消费材料

07 负责固定原文身份、位置、适用范围和实际缺口；只读取判断相关性所需的内容。
目标 API 的行为、调用前提、所有权和失败路径分析在后续研究/实现中展开。
目标是减少重复研究，不是用任意文件数上限裁掉必要证据。
共享导航和历史经验仅作为定位线索；必须在本次固定版本核对。

### 4. 用结构化查询替代机器清单分页

直接提供各仓库角色、固定版本、基线和工作树路径等必要字段。
完整清单、哈希和收据继续落盘；模型通过短引用查询，不反复读取整份 provenance。
短引用能减少机械复制，但单独不足以消除 07 / 08 的主要耗时。
