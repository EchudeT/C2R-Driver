# 改革版全局审阅：以低成本、可验证的驱动迁移为中心

日期：2026-09-27。范围：实验分支 fix/delivery-workflow-audit-20260927。
本轮只梳理、研究和提出架构方案，不据论文直接改运行逻辑，也不启动完整 E1000。

## 1. 判断

改革版已经减少了重复所有权和重复材料，但还主要是“由阶段组织模型工作”的系统。
下一次有价值的大改，应转向“由当前未解决的行为与证据组织工作”：

> 用确定性工具建立可信起点；模型解决平台差异和语义不确定性；编译器与执行证据推动下一步；只让受影响的工作重新发生。

我们的竞争对象不是 skill 的 prompt 长度，而是完成同等范围、通过同等独立验证所需的总成本。
40 美元和 80 美元目前不能直接归因于工作流优劣：范围、模型、缓存计价、运行环境、完成标准与失败尝试都需要对齐。
“17 个节点”也不意味着“17 次模型调用”；机械节点继续存在，本身未必是成本问题。

改革版完整离线套件已通过 305 项；这些结果不证明真实迁移会便宜多少。
小型真实模型试验通过功能检查，却在首次检查前写完了小片段，没有证明持续交替实现/验证。
旧 E1000 已停止，最后有成功 smoke，但尚未完整验收。详见暂停与测试报告。

## 2. 现在实际怎样运行

### 2.1 执行图与模型工作不是一回事

开发证据模式，启用两次独立复审时共有 17 个阶段：

| 逻辑部分 | 实际阶段 | 主要工作与模型参与 |
| --- | --- | --- |
| 固定输入 | 1–6：初始化、请求、候选、范围、边界、源码获取 | 多数机械完成；歧义或获取异常可能调用模型 |
| 准备材料与环境 | 7–9：证据闭合、环境恢复、知识库 | 冻结材料、确定构建/运行路线、建立检索；缺口与环境恢复可能调用模型 |
| 一次联合分析 | 10–12：平台研究、交接、契约 | 第 10 步已同时拥有源语义、目标路线与首份契约/测试计划；第 11–12 步在准备结果有效时机械绑定同一报告，不能再称为三次独立分析 |
| 准备度审查 | 13：analysis_review | 独立检查关键前提和必需行为；不是把每个局部细节提前分析完 |
| 唯一实现所有者 | 14：driver_implementation | 同一工作者负责框架、驱动、集成、运行产物和 harness，按机制推进 |
| 绑定与验证 | 15–16：artifact_preparation、public_qemu_validation | 准备齐全时复用已有工作/receipt，不必再开模型；有实际缺口才继续 |
| 独立验收 | 17：final_evidence_review | 检查当前代码、行为要求、产物身份与实际证据，实质缺陷定向返修 |

关键实现：orchestration/migration.py、migration/analysis_delivery.py、
migration/implementation.py、migration/prepared_recovery.py。

当前主线可概括为：

输入与环境 → 联合路线分析 → 准备度审查 → 统一实现循环 → 完整交付验收。

### 2.2 已经具备的能力

- 删除了独立 target_framework_enablement 节点；全部源码修改由统一实现快照覆盖。
- analysis-task 已要求提前解决“答错会推翻路线”的问题，局部 API 细节在使用处查。
- delivery-task 已要求有意义的机制一起实现其失败/资源清理，再拿最小有效观察。
- implementation_basis 从已接受报告提取原文，startup 12k 字符、repair 4k，整段保留并声明遗漏；不是另开模型总结。
- problem_packet 可一次取契约、源、目标、测试的相关片段，可选域；已有充分上下文时跳过检索。
- current_work 从同一交付报告恢复当前问题与下一步，最多 2,400 字符，同一内容去重；这是工作者状态，不是验收结论。
- 上下文策略支持分析→实现时换会话；默认仍是 persistent，不应误称所有运行都自动清空。
- 中途可按 case 子集执行；最终完整验证没有子集豁免。
- receipt 按内容身份复用；失败不冒充成功，报告文字不参与执行身份。
- 已有 Git 输入 checkpoint、日志、成本记录；checkpoint 不是精确复制模型内部状态。
- 已有开发模式证据修订路径，不能把“跨阶段永远不能修”当当前事实。
- 已有按需 Clang 查询和词法导航；它们不是完整程序语义证明。
- 已有显式 ccache；只覆盖支持的 C/C++ 编译对象，不是 Rust/Cargo 跨项目构建缓存。

### 2.3 仍有的结构差距

提示词定义了机制循环，控制器主要记录阶段、报告、整体源码和执行身份。
因而“本机制哪些事实已足够、哪个假设刚被推翻、哪一小块需要重做”仍较依赖工作者在长会话里自行维护。
目前 execution identity 仍包含整个修改文件清单；case helper 可缩小范围，但不是源码依赖闭包。
这种保守设计保护正确性，却限制了安全的局部复用。

## 3. 最值得大改的三个方向

### A. 将平台接入与运行设施做成可复用的程序化能力

这是近期优先级最高的方向。过去很多时间花在反复发现目标系统如何构建、如何接入、如何启动测试客户端，以及产物到底绑定到哪里。
这些内容多数在同一目标平台/版本间共享，不应每个驱动由模型重新发明。

建议把平台适配器变成一等能力，由小型可执行接口提供：

- 固定工具链/配置下的 build、package、run 入口及实际身份。
- 注册入口、执行上下文、资源生命周期的少量关键事实及原始引用。
- 已验证的刺激接口和观察方式；“存在 nc”与“UDP echo 可实际运行”必须区别。
- 编译日志、运行日志和退出原因的统一返回；环境失败不要伪装成驱动失败。
- 可恢复的独占构建目录/缓存和精确的进程、容器所有权。

模型只补本次驱动的差异和真实能力缺口。适配器不能隐含所有驱动都有 DMA、IRQ 或网络。
按目标平台提供基础能力，再按实际设备行为选择插件；未知平台允许一次引导后登记结果。

复用条件包含目标 commit、工具链、配置、架构、镜像和必要依赖。
保存“证据证实了什么”，不能把一次成功启动复用成所有设备的功能结论。
Rust 工程优先研究平台原生增量构建与隔离缓存；现有 ccache 很可能覆盖不到主成本。

风险：提前开发万能适配框架反而变贵。先从反复使用的 2 种目标路线抽取最小接口，
在一个非网络设备场景验证，出现重复需求再抽象。

### B. 将核心调度单位从报告变为“行为—问题—代码—观察”

不要再增设“每个机制一个模型节点”。保持同一实现所有者，但用可版本化的小型事实记录辅助它：

| 记录 | 最小内容 |
| --- | --- |
| 必需行为 | 来源、适用配置、可观察结果 |
| 关键未知项 | 当前问题、答错影响、最便宜的区分性观察 |
| 机制 | 实际相关代码、依赖机制、仍未解决的限制 |
| 观察 | 哪个输入版本、执行了什么、结果、不能证明什么 |
| 设计决定 | 所依赖事实、适用条件、被哪个反例推翻 |

这是建议中的设计，不是已存在的完整“语义图”。
大多数记录应从现有报告、编译输出、源码变更、receipt 自动派生。
保留原文证据与不确定性；无法可靠解析时照常提供可读报告，不要求模型填完几十个字段才能继续。

依赖默认保守。只有真实编译依赖/执行输入能够支持时，才缩小失效范围；
不能相信模型一句“无关”就复用旧 PASS。共用锁、宏配置、DMA 生命周期等跨界变化扩大检查范围。

设计决定允许因新证据改变，需求范围与独立验收条件保持受控；
不要把“原始要求”“当前实现方案”“某次测试结果”冻结成同一不可修改的东西。
现有 evidence revision 已走了一部分，下一步是让修订范围更精确，而不是再增加审批层。

同时加入轻量停滞观察：相同输入、相同诊断、无有效新观察的重复循环提示收束；
不能按固定工具次数或墙钟时间判失败，合法长构建不是模型空转。
提示只用于调整现场调查，不自动拉起另一个昂贵审查模型。

风险：维护图比读源码更贵。先只支持关键路线、共享资源及执行 receipt，
不做每函数节点，不把记录完整度设为质量门槛。

### C. 把翻译拆为确定性部分、可局部验证部分和平台语义部分

最有潜力超越 skill 的地方，是让模型少承担“工具更擅长且可重复”的工作：

1. 有明确前提的机械提取：常量、枚举、当前配置下的布局/偏移、函数签名、寄存器位定义。
2. 可隔离的纯逻辑：长度/索引计算、描述符编码解码、状态转换，适用时做 C/Rust 差分或性质测试。
3. 平台相关语义：所有权、并发、IRQ、DMA、错误恢复、生产调用链，由模型结合平台证据设计并实际验证。

机械路径必须明确语言/ABI/配置前提；宏多次求值、整数提升、位域、volatile、别名、UB 都不能靠正则猜。
Clang 不支持的内核扩展/构建配置应明确退回人工或模型处理，不伪造完整结果。
也不应该默认把整个驱动先转成一大坨 unsafe Rust 再交给模型重写，可能增加理解和验证成本。

测试必须触达实际生产 Rust 代码。独立写一个简化“驱动模型”通过测试，不能证明最终实现。
纯逻辑差分不证明真实设备的中断和时序；跨平台也不要求逐行轨迹完全相同，
需要定义允许的差异与共同可观察行为。

风险：为每个很小函数造 harness 会反噬成本。
只对高返工风险、可复用或语义密集的机制启用，成本上限包括适配 C 环境本身。
如果隔离费用接近直接设备验证，就放弃隔离。

## 4. 横向改进：记忆、验证、调度与学习

### 4.1 记忆应保留已验证的限制，舍弃失效的推理过程

建议分成三层，而不是在“全留”和“全清空”之间选择：

- 长期事实：带版本、原文和适用条件的平台能力、源行为、已验证经验，磁盘保留。
- 当前工作：本机制限制、当前源码、尚未解决问题、最近有效观察，进入活跃上下文。
- 完整档案：历史对话、失败猜测、旧实现，按问题查，不默认内联。

现有 implementation_basis/problem_packet/current_work 是这条路线的起点。
下一步提升内容选择和失效处理，不是再叠加一个常驻记忆代理。

局部修复通常保留热上下文；任务转向、错误假设积累或长诊断结束时才考虑新会话。
不能仅按 token 下降检测“失忆”，也不能仅按 token 增长触发重置。
重置会损失 prompt cache，并带来重读成本；比较实际账单、延迟、重复检索和缺陷，
不是只看输入 token 总数。静态前缀保持稳定，动态差异靠后；缓存命中须实测。

### 4.2 验证应围绕关键反例，不能围绕“步骤齐全”

把每项检查看成一个实验：它能排除什么错误？结果会改变什么行动？
例如先区分“客户端根本没启动”“请求未进驱动”“完成事件未交付”，再选相关修复。
避免在观察不到设备行为时反复改驱动。

已有公开测试与关键不变量优先；不要默认再让模型生成一整套相似测试。
测试生成不是独立性保证，同一个错误理解可能同时污染实现与断言。
对高风险逻辑，选少量有意义的错误变体检查 oracle 是否能发现问题；
这种 mutation 检验也按机制做，不按每行、每函数做。

最终独立检查保留，重试以实际变化和未解决 finding 为主，同时覆盖跨机制关键约束。
“少看变化之外的细节”不能变成“永不检查全局组合”。
形式化工具从孤立纯逻辑起步，不能把整驱动等价性证明放成所有运行的前置门槛。

### 4.3 并行是减少关键路径，不是多开代理

优先并行独立读/索引，以及已证明资源隔离的构建和检查。
同一工作树/镜像的修改串行。模块划分只有在共享状态和接口足够明确时才适合并行实现。
多模型投票、通用辩论、MCTS 整树搜索都可能成倍增加费用；只对有客观筛选器的局部难点考虑候选分支。
保持同一模型是第一阶段对照的合理选择；贸然模型降级会混淆工作流优化与能力损失。

### 4.4 从日志离线学经验，在线只消费相关结果

适合离线提炼的是“条件 → 错误模式 → 证据 → 最小修复 → 不适用情形”。
例如经验可以是“目标不提供某类用户接口时，不应拿该接口当设备就绪 oracle”，
不能是“所有目标都不能用 ping”或“所有中断都采用 E1000 的设置”。

对候选经验做少量可执行反例和跨驱动验证，再进入共享知识。
不在每次编译失败后都启动反思、整理、审查三个模型。
按多条历史轨迹批量离线改 harness，先在未用于设计改动的任务上验证；
别用一条 E1000 成功轨迹反复调参，最后宣称通用。

## 5. 公开研究提供了哪些启发

本次实时核对了下列 arXiv 页面；ACE、AutoSaddler、TRAIL、Translation Tag Team
另读取了 HTML 正文的机制/局限相关内容，其余主要核对摘要。
下面是方向性借鉴，不是复现实验，也不是完整文献综述。
2026 年条目多为近期预印本，不预设同行评议结论；未引用检索到的晚于本次日期的条目。
部分厂商工程博客访问返回 403，因此没有据此编造内容。

| 来源 | 可借鉴内容 | 对本项目的边界 |
| --- | --- | --- |
| Agentless，2024 [1] | 简单定位、修复、验证链可以很有竞争力 | 仓库修复不等于跨平台驱动移植；不应据此去掉自主调试 |
| SWE-agent，2024 [2]；CodeAct，2024 [3] | 工具接口与可组合动作能改变效率 | 提供一批完整证据优于多轮碎片查询；不能无限输出 |
| Repoformer，2024 [4] | 检索可能无益甚至有害，选择性检索 | 代码补全实验不能直接给迁移收益；先用当前证据是否足够这一简单规则 |
| Lost in the Middle，2023 [5] | 长上下文并不保证有效利用信息 | 旧模型/任务研究不能证明 gpt-5.6-sol 一定退化，需本项目测量 |
| ACE，2025/2026 [6] | 增量更新经验，避免反复全量总结丢细节 | 不照搬多个常驻角色；详细经验存档，活跃上下文按需选择；还需注意缓存 |
| SWE-Pruner，2026 [7]；SWE-Pruner Pro，2026-07 [8] | 按当前目标裁剪上下文/工具输出 | Pro 需要开放模型内部表示，不能直接接到托管闭源模型；裁剪不能切断关键分支 |
| VERT，2024 [9] | 候选翻译与可执行/形式化 oracle 结合 | 适合可隔离逻辑；跨 OS、MMIO、DMA 不是直接套用 Wasm 等价检查 |
| Translation Tag Team，2026-08 [10] | 确定性规则先处理适用部分，LLM 处理剩余 | 论文研究宏翻译，不能扩张成任意驱动机械翻译保证 |
| AutoSaddler，2026-08 [11] | 从失败轨迹离线优化 harness，并以验证选择修改 | 我们先做小规模固定失败集和留出集，不新建昂贵自动调参农场 |
| TRAIL，2026-09 [12] | 用反例检验经验的适用条件与组合 | 作者也说明测试通过不是语义等价证明；借鉴离线经验校验，不默认双代理在线对打 |
| TRACTOR benchmark，2026-09 [13] | 正确性、安全性、可维护性、性能分别评估 | 通用 C-to-Rust 基准补充局部任务；还需真实跨平台驱动证据 |
| SWE-smith，2025 [14] | 用可执行任务构造大量低成本训练/验证实例 | 先构造少量真实失败回归，不因“合成容易”就制造大批无用测试 |

研究并不支持“越少上下文越好”或“越多代理越聪明”这种单调结论。
更一致的启发是：信息与当前行动相关，反馈能真正区分错误，复杂机制带来的收益必须覆盖其成本。

## 6. 分阶段落地与比较

| 顺序 | 改动 | 成功标准 | 暂不做 |
| --- | --- | --- | --- |
| 第一批 | 可执行平台接入包、可靠客户端/产物绑定、已有构建路线复用 | 减少非驱动调试与重复构建，实际设备证据不减弱 | 万能平台插件体系 |
| 第一批 | 机制状态与受影响证据的小型记录 | 首次有效观察提前，遗漏关键限制和重复调查减少 | 全库每函数语义图、额外报告门槛 |
| 第二批 | 编译器事实与少量机制级差分检查 | 相同故障在便宜层被提前发现，隔离开销小于返工收益 | 所有函数独立测、整驱动默认形式证明 |
| 第二批 | 选择性上下文更新/切换、依赖明确的局部复用 | 含缓存后的总费用下降、漏检不增加 | 机械定时清空、模型自报无关就跳过验证 |
| 第三批 | 经反例验证的跨项目经验、离线 harness 优化 | 留出驱动也受益，经验有适用范围 | 把单例修复写成全局 prompt |

评价单位应该是“达到同一验收标准的迁移”，包含失败尝试，
而不是最便宜的一次成功截图。建议同时记录：

- 总模型费用：未缓存输入、缓存输入、输出分别计价；未知用量单独列出。
- 墙钟时间与构建/QEMU/模型等待分解；适配器开发等一次性成本单列，并报告摊销条件。
- 首次真实操作成功的时间；首次成功不是最终正确率。
- 返工原因与影响范围：已知限制遗漏、环境/客户端、产物绑定、真正新发现的语义问题。
- 独立保留测试的行为覆盖与残余缺陷；unsafe 使用应解释边界，不单纯数行数。
- 可运行性、性能回归、维护复杂度；系统论文不能只报 token 下降。

实验顺序：
1. 已完成的 305 项离线回归作为底线，增加测试只针对新机制的实际风险。
2. 从历史失败构造小型可执行案例；至少有一组非网络/非 DMA 场景和一个跨机制资源问题。
3. 同一 Git 输入、相同模型与验收的局部对照；另外单独研究上下文重置。
4. 少量完整迁移验证组合效应。局部节点没有完整历史，对照结果不能冒充全程节省。
5. 固定开发任务与留出驱动，随机化冷热缓存/运行顺序并记录；有多个重复样本后才报告分布与收益。

不把上述事项全部在线执行。廉价回归离线跑，公共迁移只做当前需要的验证，
独立留出评估在明确的实验轮次运行。

## 7. 建议的科研主线

可以围绕一个可检验的假设组织系统：

“跨平台驱动迁移的主要可避免成本，来自把不确定性过晚暴露、把已解决信息反复送入模型、
以及对局部变化进行过宽的重新分析。以带来源的行为/证据依赖组织执行，可在保持独立行为质量的同时降低成本。”

这不是已证明的结论。需要分别消融平台接入复用、机制级提前验证、选择性上下文、局部失效和经验复用，
避免把全部技巧打包后无法解释收益来源。
真正有价值的贡献是上述机制如何在宏、并发、生命周期和真实硬件接口存在时仍可靠，
不是“我们写了一个更长的 agent prompt”。
