# 图 1：OS 驱动翻译顶层流程

位置：报告第一节的现有总览图。可附上[SVG 草图](../figures/leadership-workflow.svg)作为结构参考。

## 可直接复制的 Prompt

绘制面向操作系统技术负责人的“OS 驱动翻译工作流”顶层图。横版 2.4:1，建议 2880×1200。
统一视觉要求：白底，深灰文字 #243444，辅助灰 #667788，分组使用淡蓝 #EAF1F7、淡青 #EDF5F2、淡灰 #F4F6F8；反馈线才使用低饱和橙色 #B57937。中文简体无衬线，类似思源黑体，标题与节点字号统一。规整矩形、细边框、直角连接线、充分留白，接近工程架构文档或论文插图。禁止机器人、人物、大脑、装饰芯片、照片、3D、渐变、阴影、霓虹、徽章、无依据的通过标记和百分比。不画宣传海报。只使用指定节点文字，箭头只表达指定关系。

从左到右画三个等高大分组，宽度约为 28%、37%、35%，分组之间以单向箭头连接。

第一组标题“01 明确翻译对象”。内部从上到下放：“设备、总线与源码入口”“版本与功能范围”“代码资料与实验路线”。底部用细横线分隔，写“交付：范围与研究材料”。

第二组标题“02 理解双方框架”。内部两个并列小框：“来源：设备行为与 OS 依赖”“目标：接口能力与驱动链路”。两个小框汇合到下方同一框“行为映射 · 能力缺口 · 测试约定”。底部写“交付：翻译方案”。

第三组标题“03 补全能力并翻译”。内部从上到下用箭头连接：“补齐目标接口”→“Rust 实现与系统集成”→“构建、自测与公开验证”。底部写“交付：代码、制品与运行证据”。

三组下方画一条浅灰支撑带，文字“贯穿全程：证据检索｜程序执行｜分层检查｜局部返修｜成本记录”。支撑带不是第四阶段，不接顺序箭头。

不要将来源 OS 直接连接到 Rust 代码而绕过框架研究，不增加第四大阶段，不添加英文标语或整段说明，不标注功能全部通过。

## 图注

图 1　先收敛翻译对象，再建立双方框架映射，最后补齐能力并完成翻译与验证；每一阶段提供下一阶段所需输入。
