# 当前行为内的日志检查优化

本次优化处理真实 pvpanic 运行中的三项开销：目标不支持 dmesg、串口颜色符打断字符串、
失败输出藏在长日志里。保持当前行为检查后再推进，不把首次正确性验证推迟到最终验收。

## 模型接口

启动日志使用现有 case 中的一个动作：

```json
{"assert_boot_log":"pvpanic: claimed PCI device"}
```

控制器忽略颜色显示符，匹配的原始字节仍保留。采集窗口在配置的 shell 就绪标记出现或首次
发送 guest 命令时关闭，不把随后命令的回显和输出当作启动证据。窗口已结束且消息不存在时
直接返回 BOOT_LOG_NOT_FOUND，避免空等完整 case 超时。实际 shell 状态检查继续使用
`guest_assert`；QMP 事件、值、错误路径仍需各自对应的真实观察，日志出现不代表它们成立。

同一行为中、状态和设备配置允许共存的多个断言可以写在同一个 case 中。不同配置的用例
仍分别运行；不跨行为延后当前所需的首次验证。实现的改动仍按已有制品身份规则重建并检查。

guest 命令失败直接返回命令、退出码、相关输出摘要及原始 serial.log 位置。
例如 `dmesg: klogctl: Function not implemented` 会进入反馈，不再只有 grep 的退出码 1。
输出摘要是有长度上限的诊断材料，不替代完整日志，不证明失败原因已被语义裁定。

## 只重新判读已存的启动事实

运行后控制器返回短引用，例如 `T1`。如果只是正向启动日志断言写错，可以调用：

```json
{"action":"check_boot_log","capture":"T1","contains":["pvpanic: claimed PCI device"]}
```

控制器读取自己保存的不可变运行记录，核对现有构建/源码/环境身份，用与实时断言相同的
颜色处理规则检查这些消息；不启动 QEMU、不重新构建、不调用模型。返回
BOOT_LOG_OBSERVED 或 BOOT_LOG_MISSING，并显示原运行状态及原设备配置。
修改工作目录里的日志不能改变保存的观察。改过代码、制品或环境，旧观察不能用于当前候选。

这不是新的整例 PASS。原失败记录保持 FAIL，新的日志判定单独登记，不能把缺少记录解释为
“事件未发生”，不能重新执行 shell/QMP，也不能为更换设备后的候选提供证据。
信息不足时仍须在当前行为重跑必要检查。最终驱动验收要求保持原样。

## 实现与验证状态

- `platform/guest.py`：启动窗口、颜色处理、命令失败输出。
- `platform/log_checks.py`：不可变捕获和正向日志判读。
- `platform/service.py`、`platform/worker.py`：现有 platform 工具接入。
- `behavior-execution.md`：模型使用说明，可独立审阅。

新增测试使用本地真实 shell 子进程及合成平台 fixture，覆盖颜色分片、命令回显误通过、
失败原因、旧记录重判不启动执行器、日志篡改和源码变化拒绝。不是 Docker/QEMU 真驱动实验。
不热更新当前冻结实验；新的平台适配器仅用于后续新任务。尚未用 luna 测量成功率或实际降本。
