# Knowledge-Guided Kernel Driver Port

Keep the model context small without weakening evidence: consume phase state and evidence IDs first, query the knowledge base with domain/path filters, retrieve compact locators before exact chunks, and pass file paths, line ranges, hashes, and statuses between phases. Read full source or logs only for the current decision or first causal failure.

Port a kernel driver as a hardware-and-platform migration, not as syntax conversion. The user supplies `source_platform` and `target_platform`. The source language is C, the target language is Rust, and the simulator is QEMU; do not ask the user to choose those. A local knowledge-base skill—user-supplied or generated by an upstream bootstrap Skill—is mandatory and remains the evidence interface throughout the task.

## Authority and change boundary

- Read repository instructions and the supplied knowledge-base skill before planning or editing. Follow that skill's integrity checks, retrieval method, citation format, and trust boundary.
- Prefer new driver/module files and migrated tests or local harnesses. Pre-existing target-platform files may be changed only when required for integration or correctness and only under [references/target-changes.md](references/target-changes.md).
- Use the lowest sufficient change level: driver-owned code, then minimal integration wiring, then a narrowly evidenced target API/framework change. Never modify unrelated target code or weaken safety and validation guarantees.
- Keep source code, source tests, fetched evidence, and prior run records immutable. Put translations and adaptations in provenance-tracked paths.
- In blind-candidate mode, treat upstream tests, migrated tests, and migration-authored tests as public developer evidence. Never access, request, reconstruct from feedback, or execute the evaluator's private assertions.
- Use Git locally for inspection and small phase checkpoints. Do not change frozen upstream revisions during migration. Any necessary read-only evidence acquisition must return through the upstream bootstrap/acquisition gate. Never push, publish, open a PR, modify remote state, or design a remote build workflow. Preserve unrelated user changes and never checkpoint them.

## Required intake

Proceed once both platform names, a confirmed concrete driver identity, frozen local source inputs, and a discoverable local knowledge-base skill are available. Infer repository paths, driver closure, build entry points, and QEMU configuration from the workspace and knowledge base. Ask one focused question only when a required item cannot be discovered or when the answer changes scope. Freeze exact revisions, compile configuration, device identity/subset, initially expected change paths, target baseline, and success criteria before implementation.

If no knowledge-base skill is supplied or discoverable, stop before design or translation. When invoked by a bootstrap Skill, return control so it can construct the local knowledge base; otherwise ask the user to provide one or invoke the package's entry Skill. Do not substitute memory or web search for the required local evidence base.

## Workflow

Read [references/workflow.md](references/workflow.md) before starting. It defines the phase gates and repair loop.

Do not reread completed phase records or repeat broad searches after a checkpoint. If a failure repeats without a changed causal variable, stop the loop, preserve the log, and report the existing root cause.

At each non-trivial decision:

1. State the question.
2. Query the local knowledge base for hardware semantics, source behavior, target API/rules, and QEMU behavior as applicable.
3. Open the cited original file, line range, or PDF page; retrieval snippets alone are not sufficient.
4. Record evidence, inference, assumptions, and unresolved conflicts in the decision or coverage record.
5. Convert the evidence into a concrete Rust invariant, API mapping, test assertion, or explicit blocker.

Read [references/knowledge-contract.md](references/knowledge-contract.md) when establishing or auditing evidence. Read [references/translation.md](references/translation.md) before producing Rust. Read [references/target-changes.md](references/target-changes.md) before editing any pre-existing target file. Read [references/test-porting.md](references/test-porting.md) before selecting or adapting tests. Read [references/qemu-evidence.md](references/qemu-evidence.md) before compilation or runtime work. When the handoff declares `BLIND_CANDIDATE`, read [references/blind-candidate-mode.md](references/blind-candidate-mode.md) before planning tests or implementation.

## Mandatory target-platform study

Read [references/target-platform-study.md](references/target-platform-study.md) and complete its profile and API evidence table before migration contracts or implementation. Directly inspect the downloaded target OS source tree and original documentation. The local knowledge base must lead back to those originals; it is not acceptable to rely only on retrieval snippets, generic platform experience, model memory, or the source platform's abstractions.

If target retrieval is weak or misses an expected API, framework, analogous driver, coding rule, or artifact path, search the pinned target source/documents directly, add the missing originals or source closure to the controlled corpus, rebuild the index, and repeat the query. Do not interpret a poor search result as proof that the target lacks the capability.

## Runnable-experiment requirement

Compilation and full target source builds are conditional mechanisms, not universal gates. Discover the target's evidenced artifact/run model and use an official runner, development container, SDK, prebuilt image, supported module/component packaging, image overlay/repack, CI-derived command, or source build as appropriate. Missing build documentation is a recovery trigger. Do not end in environment analysis without attempting the applicable alternatives and executing at least one relevant QEMU/source/model experiment when the confirmed device is emulatable.

Only a run proven to contain the current migrated driver can validate the port. A source baseline, target baseline, qtest, or standalone device-model run remains separately useful evidence and must be executed rather than abandoned when full integration is temporarily blocked.

## Non-negotiable distinctions

- Separate hardware protocol, source-platform framework behavior, target-platform integration, and QEMU model behavior. Never use one as proof of another.
- A compilable Rust skeleton is not a translated driver. A successful API return is not device behavior. A QEMU result is not a real-hardware guarantee.
- Translate the full behaviorally required C closure, including shared cores, headers, macros, callbacks, configuration, and generated facts; do not assume the named source file is the whole driver.
- Use typed AST/CPG/CFG, compile commands, layouts, call targets, globals, effects, and source spans for C semantics. Never infer semantics from names or regex over source text. Missing structured facts are blockers, not permission to guess.
- Prefer an idiomatic Rust reconstruction of evidenced contracts over line-by-line transliteration. Keep unsafe and raw-pointer regions minimal and attach explicit safety obligations.
- Every target-facing API, callback, type, feature, manifest entry, and lifecycle assumption used by the implementation must map to the target-platform profile and an inspected original definition or call site.
- Do not claim dynamic load/unload support when the target platform has no such mechanism. Validate the closest evidenced lifecycle—registration, probe, start, stop, reset, detach, reboot—and mark unsupported source-only lifecycle operations `NOT_APPLICABLE`.

## Completion

Complete only when the evidence and result records distinguish `VERIFIED`, `INFERRED`, `PLANNED`, `NOT_RUN`, `NOT_APPLICABLE`, `BLOCKED`, `FAIL`, and `PASS`; retained public tests map to driver requirements; discarded tests have source-platform-specific reasons; the Rust driver and every necessary target change pass the available affected checks; and QEMU runs cover the agreed public functional and failure paths with reproducible artifacts. Report the artifact mode and prove runtime artifact identity. If full driver integration remains blocked, preserve and report the QEMU/source/model experiments that did run plus a precise `BLOCKED_FULL_INTEGRATION` or `BLOCKED_TARGET_CHANGE` boundary.

For `BLIND_CANDIDATE`, completion additionally requires an immutable first-attempt candidate bundle with public task digest, source and target revisions, build inputs, source/patch/artifact hashes, public-test results, PMC capability map, session provenance, human interventions, and transfer record. Report official private tests as `NOT_RUN_BY_MIGRATOR`; only an independent evaluator may produce their result.

Do a final knowledge-base-driven compliance review after implementation and again after runtime fixes. Recheck target coding, safety, concurrency, lifecycle, error, observability, compatibility, and build rules; revise only evidenced migration-related changes and rerun the affected gates.
